micrograd 是什么

micrograd 是一个自动求导引擎，名字里的 autograd 是 automatic gradient 的缩写，它做的事就是实现反向传播（backpropagation）。反向传播能高效地算出损失函数对神经网络每个权重的梯度，有了梯度就能一步步调整权重、让损失下降。PyTorch、JAX 这类深度学习库的数学核心都是它。

README 里的例子：把 −4 和 2 包进 Value 对象当作输入 a、b，经过加、乘、幂、ReLU、除法等一串运算得到 g。micrograd 在背后记下整张表达式图，比如它知道 c 是 a 和 b 相加的结果、c 的子节点是 a 和 b。

前向传播得到 g.data = 24.7；调用 g.backward() 就从 g 出发沿图往回走，递归地套用链式法则，算出 g 对每个中间节点和输入的导数：a.grad = 138，b.grad = 645。

a.grad = 138 的意思是：把 a 往正方向轻轻推一点，g 会以 138 的斜率增长。这个例子本身没有意义，只是展示支持哪些运算。神经网络也是一种数学表达式，输入是数据和权重，输出是预测或损失；反向传播则更一般，它不关心表达式是不是神经网络。

为什么只在标量上做

micrograd 是标量自动求导引擎，它把神经网络拆到单个数字和每一个加号、乘号，生产环境里不会这么做。这样做是为了教学：不用一上来就处理 n 维张量。真要训练大网络就得用张量，也就是把标量打包成数组，在大数组上做运算以利用计算机的并行能力，跑得更快，但数学完全不变。

GitHub 上的 micrograd 只有两个文件：engine.py 是反向传播引擎，约 100 行，它对神经网络一无所知；nn.py 是建在上面的神经网络库，定义神经元、一层神经元、多层感知机（一串层），他说这部分简单得「像个玩笑」。理解这 150 行，就理解了神经网络训练。

单输入函数的导数

先确认导数到底告诉我们什么。随手写一个标量函数 f(x) = 3x2 − 4x + 5，f(3.0) = 20，画出来是一条抛物线。课本上会把表达式按规则求导，但没人会对神经网络这么做，展开后有成千上万项，所以这里不走符号求导，回到定义：f′(x) = limh→0 (f(x + h) − f(x)) / h。

它测的是：在 x 处往正方向推一个很小的 h，函数以多大的灵敏度响应，是上升还是下降、斜率多大。取 h = 0.001 在 x = 3 处数值估计，结果约 14，和手算 6x − 4 = 14 一致；在 x = −3 处斜率是 −22；在 x = 2/3 处斜率为 0，推一下函数几乎不动。h 也不能取得太小，浮点数精度有限，零加多了会算错。

多输入函数：分别扰动每个输入

换成三个输入一个输出：a = 2，b = −3，c = 10，d = a·b + c = 4。固定这组输入，每次只给其中一个加 h，看 d 怎么变。

推 a：b 是负数，a 变大意味着加到 d 上的量变少，d 从 4 降到 3.9996，斜率 −3，正好等于 b（d 对 a 求导就是 b）。推 b：斜率是 a 的值 2。推 c：a·b 不受影响，c 加多少 d 就加多少，斜率是 1。这就是之后每个节点要算的东西：输出对它的灵敏度。

写 Value 类

神经网络是非常大的数学表达式，需要一个数据结构把表达式存下来。Value 包住一个标量 data；用 Python 的双下划线方法 __add__、__mul__ 定义加法和乘法，a + b 在内部就是调用 a.__add__(b)，返回一个新的 Value；__repr__ 只是让打印好看一点。

为了记住表达式图，构造时多传两样东西：_children（由哪些值算出来，存成集合 _prev）和 _op（哪种运算，字符串 "+" 或 "*"）。叶子节点这两项为空。这样 d 就知道自己是由 a·b 的结果和 c 相加得到的。

class Value:
    def __init__(self, data, _children=(), _op='', label=''):
        self.data = data
        self.grad = 0.0
        self._prev = set(_children)
        self._op = _op
        self.label = label

    def __add__(self, other):
        return Value(self.data + other.data, (self, other), '+')

    def __mul__(self, other):
        return Value(self.data * other.data, (self, other), '*')

把表达式图画出来

表达式很快会变大，他贴了一段用 graphviz 画图的代码 draw_dot：先遍历出所有节点和边，每个 Value 画成一个方框，再为每个运算额外画一个圆形的运算节点连在中间，这些圆圈只是画图用的，不是真的 Value。再给每个节点加 label 方便认。

表达式再加深一层：e = a·b，d = e + c，f = −2，L = d·f = −8。现在有 a、b、c、f 四个输入，一个输出 L，图上画的就是前向传播。

反向传播要算什么

反向传播从末端开始往回走，给每个中间值算出 L 对它的导数。L 对 L 的导数是 1，然后依次求 L 对 f、d、c、e、b、a 的导数。在神经网络里，L 是损失函数，叶子节点有一部分是权重，另一部分是数据。数据是固定的，一般用不到它的梯度；权重要靠梯度信息迭代调整。

给 Value 加一个属性 grad，初始化为 0，表示默认假设这个值不影响输出。draw_dot 里把 grad 也显示出来。

手工反向传播 1：最后两层

先做 L 本身：L 变 h，L 就变 h，所以 L.grad = 1。为了核对，他写了个小函数 lol()，在里面重算一遍表达式、给某个输入加 h，打印 (L2 − L1)/h。放在函数里是为了不污染全局变量。

L = d·f，按导数定义展开 ((d + h)·f − d·f)/h = f，所以 dL/dd = f = −2；对称地 dL/df = d = 4。用 lol() 分别扰动 d 和 f，数值结果是 −2 和 4。这种用很小步长估计导数来核对解析结果的做法叫梯度检查（gradient check）。

关键一步：链式法则

他说这是最重要的一个节点，弄懂它就弄懂了整个反向传播：要算 dL/dc。已知 L 对 d 的灵敏度 dL/dd = −2，也知道 c 怎么影响 d：d = c + e，按定义求得 dd/dc = 1，dd/de 也是 1。这叫局部导数，加法节点只知道自己把 c 和 e 加成了 d，对它所在的整张大图一无所知。

把局部信息和全局信息拼起来靠微积分里的链式法则：dz/dx = (dz/dy)·(dy/dx)。维基百科上有个直观的说法：汽车速度是自行车的 2 倍，自行车是步行的 4 倍，汽车就是步行的 2 × 4 = 8 倍，变化率要相乘。

于是 dL/dc = dL/dd × dd/dc = −2 × 1 = −2，dL/de 同理也是 −2。加法节点的局部导数都是 1，所以它就是把上游传来的梯度原样分发给每个输入。扰动 c 和 e 数值核对，都是 −2。

乘法节点

再往回一步：e = a·b，乘法节点的局部导数是「另一个输入」，de/da = b，de/db = a。所以 a.grad = dL/de × b = −2 × −3 = 6，b.grad = −2 × 2 = −4。数值核对通过。

整个过程就是逐个节点局部地套链式法则：总是已知 L 对这个节点输出的导数，看这个输出是由哪个运算、从哪些子节点产生的，把局部导数乘上去，再传给子节点。反向传播就是沿计算图往回递归地应用链式法则。

沿梯度走一步

想让 L 变大，就让每个叶子节点沿自己梯度的方向走一小步：a.data += 0.01 * a.grad，b、c、f 同样处理，然后重做前向传播。L 从 −8 变成约 −7，变大了。这就是之后优化时要反复做的一步，梯度让我们知道怎么影响最终结果。

手工反向传播 2：一个神经元

换一个更有用的例子。多层感知机由一层层神经元组成，相邻层之间全连接。神经元的数学模型：输入 xi 经过突触，以乘法方式和权重 wi 相互作用，进入细胞体的是各个 wixi 的和，再加一个偏置 b（神经元本身「容不容易被激活」），最后过一个激活函数。

激活函数一般是 sigmoid、tanh 这类挤压函数，这里用 tanh：输入为 0 时输出 0，越往正方向越平滑地逼近 1，负方向逼近 −1。

写一个两输入的神经元：x1 = 2，x2 = 0，w1 = −3，w2 = 1，分步算 x1w1、x2w2、相加、加 b 得到 n，再过 tanh 得到输出 o。tanh 需要指数运算，而现在只有加和乘，于是直接把 tanh 实现成一个运算。他借这个说明：运算可以定义在任意抽象层级上，复杂函数也行，只要知道它的局部导数。

偏置特意取成 6.8813735870195432，让 n = 0.8814，o = tanh(n) = 0.7071，后面的数字都很整。

往回推这个神经元

o.grad = 1。tanh 的导数查维基百科：1 − tanh2(x)，而 tanh(n) 就是 o，所以 do/dn = 1 − o2 = 1 − 0.5 = 0.5。接下来两个加法节点把 0.5 原样分给 b、x1w1、x2w2。

乘法节点：x2.grad = w2 × 0.5 = 0.5，w2.grad = x2 × 0.5 = 0。w2 的梯度为 0 是对的，因为 x2 是 0，怎么调 w2 都乘没了，输出不变。

x1.grad = w1 × 0.5 = −1.5，w1.grad = x1 × 0.5 = 1。在神经网络里最关心的是对权重的导数，它告诉我们想让输出变大该怎么调 w1、w2。

把局部求导写进每个运算

手工反向传播「显然很荒唐」，现在把例子里看到的规律写进 Value。每个节点多存一个 _backward 函数，负责把输出的梯度按链式法则传给输入；叶子节点的 _backward 默认什么都不做。

加法：self.grad = 1.0 * out.grad，other.grad = 1.0 * out.grad。乘法：self.grad = other.data * out.grad，反过来同理。

tanh：self.grad = (1 - t**2) * out.grad，t 是前向算出的输出。这个函数存在闭包里，前向创建 out 时就挂上。

按顺序手动调用：先把 o.grad 设成 1（否则乘上去全是 0），再调 o._backward()、n._backward()……结果和手算一样。

中间出了个错，NoneType object is not callable，因为写成了 out._backward = _backward()，把函数的返回值 None 存了进去，应该存函数本身。他说这个错太好笑了，就留在了视频里。

def __mul__(self, other):
    out = Value(self.data * other.data, (self, other), '*')
    def _backward():
        self.grad += other.data * out.grad
        other.grad += self.data * out.grad
    out._backward = _backward
    return out

注这段代码已经是修完下面那个 bug 之后的写法（+=）。

拓扑排序：自动按顺序反向传播

最后一个手工步骤是按什么顺序调用 _backward。原则是：一个节点在它后面所有节点都处理完之前，不能调用它的 _backward，因为依赖它的那些节点的梯度还没传过来。满足这个条件的顺序由拓扑排序给出：把有向无环图排成一列，所有边都从左指向右。

实现是一个递归：从根节点 o 出发，没访问过就标记，先对所有子节点递归，子节点都进了列表，自己才进列表。这样每个节点都排在它的所有子节点之后，最后一个是输出 o。反向传播就是把 o.grad 设成 1，然后按反序对每个节点调用 _backward。把这段收进 Value.backward()，以后一行 o.backward() 就够了。

def backward(self):
    topo, visited = [], set()
    def build_topo(v):
        if v not in visited:
            visited.add(v)
            for child in v._prev:
                build_topo(child)
            topo.append(v)
    build_topo(self)
    self.grad = 1.0
    for node in reversed(topo):
        node._backward()

一个节点用两次，梯度要累加

现在有个严重的 bug。最简单的例子：a = 3，b = a + a，b 对 a 的导数应该是 2，算出来却是 1。因为加法里 self 和 other 是同一个对象，先把 a.grad 设成 1，再设成 1，覆盖掉了。

复杂一点：d = a·b，e = a + b，f = d·e，a、b 各被用了两次，e 反向时把梯度写给 a、b，轮到 d 时又覆盖掉。只要一个变量被用了不止一次就会出问题。多元链式法则的结论是这些梯度要相加，所以把所有 _backward 里的 = 改成 +=。梯度初始化是 0，各条路径的贡献依次加上去就对了。

把 tanh 拆成更基本的运算

前面说过 tanh 可以用 exp 表示：tanh(x) = (e2x − 1)/(e2x + 1)。拆开一是为了证明结果一样，二是借机多实现几种运算。

先做几处方便性改动：a + 1 会报错，因为 1 不是 Value，在 __add__、__mul__ 里把非 Value 的数包一层。

2 * a 也不行，Python 调的是 int.__mul__，它不认识 Value；定义 __rmul__，Python 找不到左边的乘法时会回头调右边的 __rmul__，在里面交换顺序就行。

exp 的局部导数就是它自己：self.grad += out.data * out.grad。除法写成更一般的幂：a/b = a·b−1，实现 __pow__，只接受 int 或 float 当指数，局部导数用幂法则 n·xn−1。减法写成加上一个乘了 −1 的数。

把神经元里的 tanh 换成这一串运算，图变长了许多，但前向结果仍是 0.7071，w1、w2、x1、x2 的梯度仍是 1、0、−1.5、0.5。在哪个粒度上实现运算完全由你决定，只要能写出前向和局部导数，就能把梯度接着传下去。

同样的事用 PyTorch 写

micrograd 的 API 是仿照 PyTorch 设计的。PyTorch 里一切都是张量，也就是标量组成的 n 维数组，比如 torch.Tensor([[1,2,3],[4,5,6]]) 的 shape 是 2×3。

这里只需要单元素张量：torch.Tensor([2.0]).double()，转成 double 是因为 Python 的浮点数是 float64，而 PyTorch 默认是 float32。

叶子节点默认不需要梯度（大多数时候输入数据确实不需要，这样更省），要显式写 requires_grad = True。之后算术、torch.tanh、.backward() 都和 micrograd 一样，.data、.grad 也都在，.item() 把单元素张量里的数取出来。

结果 0.7071 和 0.5、0、−1.5、1，和 micrograd 一致。区别只在 PyTorch 用张量并行处理大量运算，快得多。

搭神经网络：Neuron、Layer、MLP

接口也照 PyTorch 的 nn.Module 来设计。Neuron(nin)：为每个输入建一个 −1 到 1 之间的随机权重，再加一个偏置；__call__(x) 里用 zip 把权重和输入配对，算 Σ wixi + b（sum 的起始值直接设成 b），再过 tanh。

Layer(nin, nout)：一层就是一组互相独立的神经元，都和输入全连接，调用时分别算出来。MLP(nin, nouts)：nouts 是各层大小的列表，相邻两两建层，调用时依次通过。

照 CS231n 那张图建一个 3 输入、两个 4 神经元隐藏层、1 输出的网络 MLP(3, [4, 4, 1])。最后一层只有一个神经元时直接返回那个值而不是列表。画出来的图已经很大了，没人会手推它的导数，但 micrograd 能一路反向传播到每个权重。

class Neuron:
    def __init__(self, nin):
        self.w = [Value(random.uniform(-1, 1)) for _ in range(nin)]
        self.b = Value(random.uniform(-1, 1))
    def __call__(self, x):
        act = sum((wi * xi for wi, xi in zip(self.w, x)), self.b)
        return act.tanh()

class Layer:
    def __init__(self, nin, nout):
        self.neurons = [Neuron(nin) for _ in range(nout)]
    def __call__(self, x):
        outs = [n(x) for n in self.neurons]
        return outs[0] if len(outs) == 1 else outs

class MLP:
    def __init__(self, nin, nouts):
        sz = [nin] + nouts
        self.layers = [Layer(sz[i], sz[i+1]) for i in range(len(nouts))]
    def __call__(self, x):
        for layer in self.layers:
            x = layer(x)
        return x

小数据集和损失函数

造一个四个样本的数据集，每个样本 3 维输入，目标分别是 1、−1、−1、1，相当于一个二分类器。随机初始化的网络输出 0.91、0.88、0.88、0.88，后三个都不对。

深度学习的办法是用一个数概括整个网络表现得怎么样，这个数叫损失（loss）。这里用均方误差：每个样本的预测减目标再平方，平方是为了去掉正负号（取绝对值也可以），只有预测等于目标时才是 0，差得越远越大；四项加起来，此时约 7。

调用 loss.backward() 后，每个神经元的每个权重都有了 grad。比如第一层第 0 个神经元的第 0 个权重梯度是负的，说明把它调大一点损失会下降。draw_dot(loss) 画出的图非常大，因为它包含四次完整的前向传播再加上损失。输入数据也有梯度，但数据是给定的，不会去改它。

收集参数

要对所有参数统一更新，给每个类加 parameters()：神经元返回 self.w + [self.b]，层和网络用嵌套的列表推导式把下面的参数摊平。PyTorch 的 nn.Module 也有同名方法，返回参数张量。这个网络一共 41 个参数（3×4 + 4、4×4 + 4、4 + 1）。因为类定义改了，网络要重新初始化，数字和刚才不一样了。

梯度下降

梯度可以看成一个指向损失增大方向的向量，所以要往反方向走：p.data += -0.01 * p.grad。他特意用刚才那个梯度为负的权重核对符号：0.854 变成 0.857，往大调了，损失应该下降。重算前向，损失从 4.84 降到 4.36。

之后就是循环：前向、反向、更新，损失一路 3.9、3.66、3.47 往下走，预测越来越接近 1、−1、−1、1。

步长调大会收敛更快，但太大会「过度自信」：我们只知道损失在当前点附近的局部信息，一步迈太远可能落到损失地形完全不同的地方，训练不稳甚至发散。视频里有一步确实迈过了头，碰巧又落进了好位置，损失到了 7×10−9。学习率太小收敛太慢，太大会爆，调它是门手艺。

最后把它写成规范的训练循环：重新初始化网络，0.01 太慢、0.1 有点危险，学习率取两者之间，跑 20 步，损失平稳地降到很低。

忘了清零梯度

训练循环里其实有个很常见的 bug，他说自己第 20 次犯了，干脆留在镜头里。他以前发过一条推特列举神经网络最常见的错误，这里犯的是第 3 条：.backward() 之前忘了把梯度清零。

每个参数的 grad 从 0 开始，反向时 += 上去，更新完 grad 还留着；下一轮反向又往上加，梯度越积越大。修法是每轮反向前把所有 p.grad 设回 0，对应 PyTorch 里的 zero_grad()。

修完下降变慢了，要多走几步才到同样低的损失。之前那个有 bug 的版本之所以能工作，是因为问题太简单，累加的梯度等于用了很大的步长。复杂一点的问题上这个 bug 会让损失降不下去。代码有 bug 网络照样能跑，这是写神经网络麻烦的地方。

总结：神经网络在做什么

神经网络是数学表达式，输入是数据和参数。前向传播之后接一个损失函数，衡量预测的准确程度，损失低说明网络在做你想让它做的事。对损失做反向传播得到梯度，知道怎么局部地调整每个参数让损失下降，再用梯度下降反复迭代。

这个网络只有 41 个参数，同样的方法可以训练几十亿乃至上万亿参数的网络。GPT 也是这样：拿互联网上的大量文本，让网络读几个词、预测下一个词，训练到这个规模会出现很多涌现能力，但原理完全一样。区别在细节：更新规则会比这里的随机梯度下降复杂一点，损失函数用交叉熵而不是均方误差。

这一集记住这几条

  • 导数测的是把输入往正方向推一点时输出的响应灵敏度；数值估计 (f(x + h) − f(x))/h 是核对解析梯度最简单的办法。
  • 反向传播 = 从输出往回，在每个节点把局部导数乘上上游梯度（链式法则），按拓扑排序的逆序执行。
  • 加法节点把梯度原样分下去，乘法节点给每个输入乘上「另一个输入」，tanh 乘 1 − t2。
  • 一个值被用了不止一次时，各条路径的梯度要累加，所以 _backward 里写 +=，每轮训练前要把梯度清零。
  • 运算可以定义在任意粒度上，只要能写出前向和局部导数；神经网络只是一类数学表达式，训练就是前向、反向、沿负梯度更新的循环。
  • 张量和 PyTorch 只是为了效率，数学和 micrograd 的标量版本完全相同。

makemore 和字符级语言模型

数据集 names.txt 有约 32000 个名字，他说是从一个政府网站上随手找来的。训练好的模型会生成 dontell、irot、zendy 这类听起来像名字的新词，给孩子起名时说不定用得上。

字符级语言模型把每一行当作一个样本，每个样本是一串字符，比如 r、e、e、s、e，模型学的是给定前面的字符时下一个字符的分布。

系列会依次实现 bigram、词袋、多层感知机、循环神经网络，一直到现代 Transformer，最后那个 Transformer 基本等同于 GPT-2。之后还打算做词级别的文档生成，再往后是图像和图文模型，比如 DALL·E、Stable Diffusion。

读数据，看一个名字里有多少信息

读入文件、splitlines() 得到一个字符串列表，开头是 emma、olivia、ava，看着像是按频率排的。共 32033 个，最短 2 个字符，最长 15 个。

一个名字其实打包了好几个训练样本。比如 isabella 告诉我们：i 很可能出现在名字开头，s 很可能跟在 i 后面，a 很可能跟在 is 后面，以此类推；最后还有一条，isabella 之后名字很可能结束。bigram 模型每次只看两个字符：给定一个字符，预测下一个。它只建模这种局部结构，丢掉了更早的上下文，很弱，但适合起步。

列出 bigram 并计数

for ch1, ch2 in zip(w, w[1:]) 能方便地列出相邻字符对：emma 和 mma 配对，zip 在短的那个用完时停下，得到 em、mm、ma。为了记下「开头」和「结尾」的信息，在名字前后各加一个特殊标记 <S>、<E>，emma 就有 5 个 bigram。

最简单的学法是计数：用字典 b，b[bigram] = b.get(bigram, 0) + 1。全数据集统计完按次数排序，最常见的是 n 结尾、a 后面跟 n 这类。

改用二维张量

把计数存成二维数组更方便：行是第一个字符，列是第二个字符。PyTorch 的 torch.tensor 可以高效地创建和操作多维数组，计数用 dtype=torch.int32。26 个字母加两个特殊标记，是 28×28 的数组 N。

需要把字符映射成整数下标：把所有名字拼成一个大字符串，用 set 去重，排序得到 a 到 z，再建 stoi（a 是 0，z 是 25，<S> 是 26，<E> 是 27）。然后 N[ix1, ix2] += 1。

用 matplotlib 画出来，每格标上 bigram 和次数，比如 a 后面跟 j 出现了 175 次。从张量里取出的元素还是张量，.item() 才拿到 Python 整数。

只用一个特殊字符

这张表浪费了不少空间：<E> 永远不会是 bigram 的第一个字符，整行是 0；<S> 永远不会是第二个字符，整列是 0。所以只保留一个特殊标记「.」，放在下标 0，字母依次从 1 开始，表变成 27×27。

新表的第 0 行是每个字母作为名字开头的次数，第 0 列是每个字母作为结尾的次数，中间是字母之间的接续关系。「..」是 0，因为没有空名字。这张表已经包含了从 bigram 模型采样所需的全部信息。

从模型采样

从「.」开始：取第 0 行的计数，转成 float 再除以总和，得到首字母的概率分布。采样用 torch.multinomial：给它概率，它按概率返回下标。为了结果可复现，用一个固定种子（2147483647）的 torch.Generator 当随机源。replacement=True 要显式写，默认是 False。

第一次采到 13，也就是 m，m 开头的名字有约 2500 个，概率不到 10%。接着取 m 那一行再采，循环直到采回「.」。采出来的名字很差，比如单独一个 h。

他也一度怀疑自己写错了，后来想通：模型只知道上一个字符是 h，并不知道这是名字的第一个字符，h 后面结束的概率不低，于是就结束了。换成 27 个字符完全均匀的分布对照一下，那才是彻底的乱码，bigram 至少有点名字的样子。

预先归一化：广播

每次采样都把一整行转 float、求和、相除，太浪费，干脆先算好概率矩阵 P。也借此练习张量操作，尤其是广播（broadcasting），后面做 Transformer 时会有很复杂的数组运算。

P.sum() 会把整张表加成一个数，要按行求和得用 P.sum(1, keepdim=True)，结果是 27×1 的列向量；按维度 0 求和得到 1×27 的行向量。keepdim=False 时被求和的那一维会被挤掉，只剩形状 27。

27×27 能不能除以 27×1，由广播规则决定：从最右边的维度往左逐一比较，每一维要么相等、要么其中一个是 1、要么其中一个不存在。这里满足，于是 27×1 的列向量被复制 27 份，逐元素相除，正好把每一行归一化。检查第 0 行的和是 1。

keepdim 引出的 bug

他说想「吓唬一下」大家：去掉 keepdim=True，求和结果的数值完全一样，只是形状从 27×1 变成 27。按广播规则这仍然能运行，因为缺的那一维会在左边补 1，变成 1×27 的行向量，再沿竖直方向复制 27 份。结果是在用列的和去除每一列，归一化的是列不是行，P[0].sum() 变成了 7，第一列的和反而是 1。

问题出在广播悄悄补维度的方向。他强烈建议认真读广播语义、找教程练习，因为这种 bug 很隐蔽、很难查。另外 P /= ... 这种原地操作不新建张量，可能更快。

用一个数评估模型：负对数似然

训练好了（就是计数再归一化，矩阵 P 里的数就是这个 bigram 模型的参数），现在要用一个数概括模型的好坏。先看模型给训练集里每个 bigram 的概率：27 个字符均匀分布时每个约 4%，这里有的到了 40%，说明学到了东西。理想模型给正确的下一个字符的概率接近 1。

统计里用似然（likelihood）衡量：模型给整个数据集的概率，也就是所有这些概率的乘积，越大越好。概率都在 0 到 1 之间，乘起来是个极小的数，所以通常取对数：log 是单调函数，概率为 1 时 log 为 0，概率越小越负，乘积的 log 等于各项 log 之和。

损失函数要求越低越好，所以取负号得到负对数似然（negative log likelihood），最低是 0；再除以 bigram 的个数取平均。前三个名字上约是 2.4，整个训练集上是 2.45。最大化似然、最大化对数似然、最小化平均负对数似然，这几个优化问题是等价的。

可以拿任意名字测：andrej 的平均损失约 3，因为 ej 很少见；andrejq 的损失是无穷大，因为数据里 j 后面从没出现过 q，概率为 0，log 0 是负无穷。

模型平滑

解决办法叫模型平滑（model smoothing）：给每个计数加上一些假计数，比如都加 1，再重新算概率。加得越多分布越均匀，加得越少分布越尖锐。加 1 是个不错的选择，这样概率矩阵里不会再有 0，jq 的概率很小但不再是 0，损失不会无穷大。加 1 后整个训练集的平均损失是 2.4765。

第二部分：把 bigram 写成神经网络

刚才的模型是凭直觉拼出来的：计数再归一化。现在换个框架，最后会走到几乎同一个地方。神经网络仍然是 bigram 模型：输入一个字符，经过带参数 W 的网络，输出下一个字符的概率分布。因为有损失函数（负对数似然），可以看模型给正确的下一个字符多大概率，再用基于梯度的优化调 W。

先建训练集：两个列表，输入 xs 是 bigram 的第一个字符下标，目标 ys 是第二个。只用 emma 的话有 5 个样本：输入 0 时希望 5（e）的概率高，输入 5 时希望 13（m）高，等等。

插一句 API 的坑：torch.tensor（小写）和 torch.Tensor（大写）都能用，文档也说不清区别。实际差别是小写的会自动推断数据类型，大写的总是返回 float32。他建议用小写的，也借此提醒要习惯读大量文档和问答帖。

one-hot 编码

整数下标不能直接喂进神经网络，神经元的权重是乘在输入上的，乘一个整数下标没有意义。常用的编码是 one-hot：13 编码成一个第 13 位是 1、其余都是 0 的向量。

torch.nn.functional.one_hot(xs, num_classes=27) 一次编码所有输入，得到 5×27 的矩阵；类别数要显式给，否则它可能只猜到 14 类。

注意数据类型：one_hot 返回 int64，而且不接受 dtype 参数，要手动 .float() 转成 float32 才能喂进网络。

一层线性神经元

用 torch.randn 从标准正态分布初始化权重。先做一个神经元：W 是 27×1，xenc @ W 得到 5×1，五个输入同时算出这个神经元的激活值。

改成 27 个神经元：W 是 27×27，xenc @ W 是 5×27，第 (3, 13) 个元素就是第 3 个输入和 W 第 13 列的点积，矩阵乘法把许多输入和许多神经元的点积一次并行算完。

这一层没有偏置，也没有 tanh 这类非线性，就是最简单的单层线性网络。

logits 和 softmax

要把这 27 个有正有负的数解释成下一个字符的概率。概率要非负、和为 1，计数又必须是非负整数，都不能直接让网络输出。办法是把它们解释成对数计数（log counts），也叫 logits；取 exp 后负数变成小于 1 的正数、正数变成大于 1 的数，相当于计数；再按行归一化，得到概率。

后两步（exp 再归一化）就是 softmax：把一层的任意实数输出变成和为 1 的正数，可以加在任何线性层上面让网络输出概率。整个前向过程都由可微运算组成：乘、加、exp、求和、除，都能反向传播。

xenc = F.one_hot(xs, num_classes=27).float()   # 输入做 one-hot
logits = xenc @ W                               # 预测对数计数
counts = logits.exp()                           # 相当于计数 N
probs = counts / counts.sum(1, keepdims=True)   # 下一个字符的概率

逐个样本看损失

他把 emma 的 5 个样本逐个打印：第一个是「.e」，输入 0，网络输出 27 个概率，正确答案是下标 5，对应概率只有约 1%，负对数似然约 4，很高。其余几个也大多在 1% 到 2%，只有 ma 碰巧到了 7%。5 个样本的平均负对数似然是 3.76。

换几个随机种子重新采样 W，有的损失低一些（3.37），有的更高。这种随机猜参数再看效果的办法他称为「业余做法」，正确做法是固定一个随机初始值，然后利用损失对 W 的梯度去优化。

向量化的损失和反向传播

流程和 micrograd 最后那段几乎一样，只是网络换成了单层线性加 softmax，损失从均方误差换成负对数似然，因为这是分类，不是回归。

要从 5×27 的 probs 里一次取出每行正确答案的概率：probs[torch.arange(5), ys]，再取 log、求平均、加负号，得到损失 3.76，和逐个算的一样。

反向前先把梯度清零，PyTorch 里可以直接设成 W.grad = None，比设成 0 更省。W 要在创建时声明 requires_grad=True。调用 loss.backward() 后，PyTorch 和 micrograd 一样，前向时已经在背后记下了完整的计算图，于是把梯度一路填回 W。

W.grad 也是 27×27，每个元素表示那个权重对损失的影响。更新就是 W.data += -0.1 * W.grad，损失从 3.76 降到 3.74、3.72。

loss = -probs[torch.arange(num), ys].log().mean()
W.grad = None        # 清零梯度
loss.backward()
W.data += -50 * W.grad

用全部数据训练

换成全部名字，有 228146 个 bigram，代码一行都不用改。这个问题很简单，学习率可以开得很大，50 都行。迭代几百步后损失到了 2.46、2.45 附近，和计数法的结果差不多。

这说得通：两种做法用的信息一样，都只看前一个字符。bigram 情形太简单，直接计数就能把损失优化得很好；但基于梯度的方法灵活得多，后面要输入多个前面的字符、网络越来越复杂，最后一直到 Transformer，输出仍然是 logits，后面的 softmax、负对数似然、梯度优化都不变，变的只是前向怎么算出 logits。计数法扩展不了：输入前 10 个字符时，所有组合根本放不进一张表。

两点观察

第一，one-hot 向量乘 W，按矩阵乘法的规则就是取出 W 的对应一行，logits 就是 W 的那一行。这和计数法里用第一个字符去查表、取出一行，完全是一回事。所以 W 就是那张表，准确地说 W.exp() 对应计数表：计数法是一个个数出来的，梯度法是从随机初始化开始，在损失的引导下一点点走到同一张表。

第二，平滑在梯度框架里也有对应物。计数上加得越多，概率越均匀；而 W 全为 0 时 logits 全为 0，exp 后全是 1，概率正好均匀。所以鼓励 W 接近 0 就相当于平滑。

办法是在损失里加一项正则化损失，比如 0.01 * (W**2).mean()：W 有非零元素就要付出代价，像一根把 W 往 0 拉的弹簧。系数越大，越接近均匀预测，对应计数法里加的假计数越多。

loss = -probs[torch.arange(num), ys].log().mean() + 0.01 * (W**2).mean()

从神经网络采样

把采样代码里的「取 P 的第 ix 行」换成：把 ix 做 one-hot，乘 W（其实就是取出 W 的第 ix 行），exp、归一化，再采样。用同一个随机种子，采出的名字和计数模型完全一样，因为这就是同一个模型，W 就是之前那张表的对数计数，只是来路和解释不同。

这一集记住这几条

  • 字符级语言模型的任务：给定前面的字符，输出下一个字符的概率分布；bigram 只看前一个字符。
  • 评估用平均负对数似然：模型给正确下一个字符的概率取 log、取负、求平均，越低越好，最低为 0。bigram 在这份数据上约 2.45。
  • 张量广播从最右边的维度往左对齐，缺的维度在左边补 1；按行求和要 keepdim=True，否则会悄悄变成按列归一化。
  • 神经网络版本：one-hot 输入、线性层输出 logits、softmax 得到概率、负对数似然当损失、梯度下降优化，结果和计数法相同。
  • one-hot 乘矩阵等于取一行；在损失里加 W 的平方当正则项，作用等同于计数法里的平滑。
  • 之后各集只把「怎么算 logits」换得越来越复杂，softmax、损失和优化的部分不再变。

计数表的问题

上一集的 bigram 模型只用一个字符当上下文，生成的东西不太像名字。想多看几个字符，计数表的大小会随上下文长度指数增长：一个字符 27 种上下文，两个字符 729 种，三个字符约 2 万种。行数太多，每一行分到的计数太少，整件事就崩了。所以这一集改用多层感知机预测下一个字符。

Bengio 等 2003

这篇论文不是第一个用神经网络预测下一个词的，但在那个时期影响很大，常被当成这个想法的代表引用。论文 19 页，他建议读一读，可读性很好、想法很多。论文做的是词级模型，词表 1.7 万个词；这里沿用同样的建模方法，只是换成字符。

核心想法：给每个词分配一个比如 30 维的特征向量，1.7 万个点放在 30 维空间里。一开始随机放置，训练中通过反向传播调整，意思相近的词会被挪到相近的位置。训练目标和上一集一样，最大化训练数据的对数似然。

论文里的直觉例子：要补全「A dog was running in a ___」，这句话训练集里从没出现过，严格说已经超出了训练分布。

但如果见过「The dog was running in a ___」，而网络学到 a 和 the 经常可以互换、把它们的嵌入放得很近，知识就能通过嵌入空间迁移过来。猫和狗经常出现在相似的语境里，walking 和 running 也一样。

网络结构

以三个前面的词预测第四个为例。每个词是 0 到 16999 之间的下标，查一张 17000×30 的查找表 C，取出那一行当作这个词的嵌入；三个词共用同一张 C，输入层一共 90 个神经元。

隐藏层的大小是超参数，也就是由设计者决定的选项，比如 100 个神经元，和 90 个输入全连接，后面接 tanh。输出层有 17000 个神经元，和隐藏层全连接，参数和计算量主要都在这里。

17000 个 logits 过 softmax 得到下一个词的概率，训练时用正确答案的下标取出它的概率，最大化这个概率。要优化的参数是输出层和隐藏层的权重、偏置，以及嵌入表 C，全部靠反向传播。图里的虚线是一种变体，这里不讲。

重建数据集

block_size 是上下文长度，用几个字符预测下一个，这里取 3。从全是 0（「.」）的上下文开始，逐个字符滑动：emma 生成 5 个样本，「...」预测 e，「..e」预测 m，「.em」预测 m，「emm」预测 a，「mma」预测「.」。

block_size 可以改成 4、5、10，不够的地方都用「.」补齐。前五个名字得到 32 个样本，X 是 32×3 的整数，Y 是 32 个标签。

block_size = 3
X, Y = [], []
for w in words:
    context = [0] * block_size
    for ch in w + '.':
        ix = stoi[ch]
        X.append(context)
        Y.append(ix)
        context = context[1:] + [ix]   # 滑动窗口

嵌入查找表

论文把 1.7 万个词放进 30 维，这里只有 27 个字符，先用 2 维：C = torch.randn((27, 2))。嵌入整数 5 有两种看法：直接取 C[5]；或者像上一集那样先做 one-hot（要传张量而不是 int，还要转成 float，否则报 long 和 float 不能相乘），再乘 C，因为 0 把其他行都屏蔽掉了，结果一样。

所以嵌入可以看成神经网络的第一层：线性神经元、没有非线性、权重矩阵就是 C，输入是 one-hot。两种理解等价，实际用索引，因为快得多。PyTorch 的索引很灵活，可以用列表、一维整数张量（还可以重复），也可以直接用二维整数张量：C[X] 的形状是 32×3×2，每个整数都换成了它的嵌入。

隐藏层和 view

隐藏层输入是 3×2 = 6 维，取 100 个神经元：W1 是 6×100，b1 是 100。问题是嵌入的形状是 32×3×2，不能直接乘 6×100，要先把三个嵌入拼成 32×6。

他借这个说明 PyTorch 函数多、同一件事有很多写法。可以用 torch.cat([emb[:,0,:], emb[:,1,:], emb[:,2,:]], 1)，但改了 blocksize 就得改代码；torch.cat(torch.unbind(emb, 1), 1) 不依赖长度。最好的办法是 emb.view(32, 6)。

view 极快，因为张量在内存里永远是一维的存储（storage），形状只是解释它的方式：一个 0 到 17 的向量可以看成 2×9、9×2、3×3×2，只要元素总数相同。

调用 view 时内存不复制、不移动，只改 storage offset、strides、shape 这几个属性；cat 则要新建一块内存。他推荐 Edward Yang 的博客《PyTorch internals》。写成 emb.view(-1, 6) 让 PyTorch 自己推断第一维。

加偏置时检查广播：32×100 加 100，右对齐后 100 被当成 1×100 的行向量，竖直复制到每一行，同一个偏置加到每个样本上，是对的。再过 tanh，得到 32×100、值在 −1 到 1 之间的隐藏层激活。

输出层和损失

输出层 W2 是 100×27，b2 是 27，logits = h @ W2 + b2 是 32×27。和上一集一样 exp、按行归一化得到概率，用 prob[torch.arange(32), Y] 取出每个样本正确字符的概率，有的 0.2，有的极小，取 log、求平均、取负，损失是 17。

整理一下：用固定种子的生成器初始化，所有参数放进一个列表，一共 3481 个参数。

为什么用 F.crossentropy

分类太常见了，PyTorch 有现成的 F.cross_entropy(logits, Y)，结果和自己写的三行一样。自己写只是为了教学，实际不会这么做，原因有三。

第一，前向更高效：PyTorch 不会为中间结果一个个新建张量，而是把这串运算合并成融合 kernel（fused kernel）一次算完。第二，反向也更简单：合在一起的表达式，求导后常常能化简，就像 micrograd 里 tanh 的反向直接写 1 − t2，不必逐个穿过 exp、乘 2、减 1、除法。

第三，数值上更稳定。logits 是 −2、3、−3、0、5 时一切正常；有一个变成 −100 也没事，exp 出来接近 0；但如果有一个是 +100，e100 超出浮点数范围变成 inf，结果是 nan。因为要归一化，给所有 logits 加减同一个常数，概率不变；PyTorch 内部先减去最大值，最大的变成 0，其余都是负数，exp 永远不会溢出。

训练循环，先过拟合一个小批量

前向用 F.cross_entropy，反向前把每个参数的 p.grad 设为 None，loss.backward()，再 p.data += -lr * p.grad。参数要设 requires_grad = True。

只用前五个名字的 32 个样本训练，损失从 17 很快降得很低，这是在过拟合一个批次：3400 个参数拟合 32 个样本当然容易。但到不了 0：看 logits.max(1) 的预测下标，大多和标签一致，个别不同。

比如「...」这个输入，在这五个名字里要预测 e、o、a、s 等不同字符，同一个输入对应多个答案，损失不可能为 0；输入唯一对应一个输出的地方就完全拟合了。

全部数据和小批量

换成全部数据，有 22.8 万个样本，每一步前向和反向都要处理全部样本，很慢。通常的做法是每一步随机取一小部分，叫小批量（minibatch），只在它上面做前向、反向和更新：ix = torch.randint(0, X.shape[0], (32,))，然后用 X[ix]、Y[ix]。

这样几乎是瞬间完成一步。代价是梯度只是近似值，方向没那么可靠，但足够有用；用近似梯度多走几步，比用精确梯度少走几步好得多。打印的损失只是当前小批量的，要评估得在全部 X、Y 上算，此时约 2.7，继续训练降到 2.5 附近。

怎么找学习率

学习率是猜的，不知道快了还是慢了。他的办法：先手动试，0.001 时损失几乎不动，太低；1 时在下降但上下抖动；10 完全不行。于是合理范围在 0.001 到 1 之间。

用 lre = torch.linspace(-3, 0, 1000)、lrs = 10**lre，让学习率在指数上均匀地从 0.001 增长到 1，跑 1000 步，每步换一个学习率，记下学习率和损失。以学习率的指数为横轴画出来：开头太低没动静，中间有一段好区域，后面开始不稳定。谷底大约在指数 −1 处，也就是 0.1，正好是之前凭感觉用的值。

然后用 0.1 跑 1 万步，到 2.48，再 1 万步 2.46，此时已经超过 bigram 的 2.45；再把学习率降为十分之一，也就是学习率衰减，到了约 2.3。粗糙，但流程大致如此：先找到合适的学习率，训练一阵，最后衰减学习率再走一些步。

训练集、验证集、测试集

损失 2.3 比 2.45 低，并不能直接说模型更好。模型越大，越能过拟合训练集：训练损失可以低到接近 0，但那只是逐字记住了训练数据，采样时只会生成训练集里原有的名字，在没见过的名字上损失会很高。

标准做法是把数据分成三份：训练集约 80%，用梯度下降优化参数；验证集（也叫 dev 集）约 10%，用来选超参数，比如隐藏层大小、嵌入维度、正则化强度；测试集约 10%，只在最后评估模型性能，而且要用得很少，因为每看一次测试损失并据此做决定，就等于在拿测试集训练。

代码改成一个 build_dataset(words) 函数，先把名字随机打乱，前 80% 的名字做训练集，80% 到 90% 做验证集，剩下做测试集。按名字切开后得到的样本数大约是 18.2 万、2.3 万、2.3 万。以后只用训练集训练，用验证集评估。

欠拟合，加大隐藏层

训练后验证损失约 2.3，训练集上也约 2.3，两者差不多，说明没有过拟合，网络太小，记不住数据，这叫欠拟合。通常的预期是加大网络会有提升。

隐藏层从 100 加到 300，参数从约 3400 增加到约 1 万。画出损失曲线，很「厚」，因为小批量带来了噪声；批量太小时梯度噪声大，可以考虑加大批量。训练了一阵、衰减了学习率，到了 2.23 左右，提升不大。他猜瓶颈可能是只有两维的嵌入，27 个字符挤在两维里，网络用不好。

二维嵌入画出来

嵌入是二维的，正好能把 27 个字符画在平面上，C 的两列当坐标。结果有明显结构：元音 a、e、i、o、u 聚在一起，说明网络把它们当成相似、可互换的字符；q 被单独放得很远，像个例外；「.」这个特殊字符也在很远的地方。不是随机的，训练让嵌入学到了东西。

加大嵌入维度

嵌入改成 10 维，隐藏层输入就是 3×10 = 30，隐藏层减到 200 个神经元，共 11897 个参数。原来代码里写死了 6，现在要改成 30；他提醒生产代码里不要写死这类魔数。另外把损失取 log10 再画，原始损失曲线常是曲棍球杆的形状，取 log 后好看一些。

为什么还要停在多层感知机

接下来想做循环神经网络和它的变体 GRU、Long Short-Term Memory。循环网络很有表达力，理论上是万能逼近器，但用我们手里的一阶梯度方法很难优化。要理解为什么，关键是理解训练时激活值和梯度怎么变化，后来的许多变体都是为了改善这一点。所以这一集先把这些看清楚。

起始代码就是上一集的网络，只是把魔数提成了变量：嵌入维度 n_embd = 10、隐藏层 n_hidden = 200，约 1.1 万个参数，批量 32，训练 20 万步，训练和验证损失约 2.12、2.16。

评估函数加了 @torch.no_grad() 装饰器，告诉 PyTorch 这里不会调用 .backward()，不必记录计算图，省内存也更快。

问题一：初始损失太高

第 0 步的损失是 27，很快就掉到 2 左右。训练神经网络时，通常能根据损失函数和问题设定估出初始损失应该是多少。这里刚初始化时没理由偏向任何字符，输出应该接近 27 个字符的均匀分布，损失是 −log(1/27) = 3.29，远低于 27。

用四个类别的小例子说明：logits 全接近 0 时 softmax 是均匀分布，不管标签是哪个，损失都是 1.38；logits 取值越极端，越可能「很自信地错了」，损失很高甚至无穷大。logits 不必全为 0，全部相等就行，但对称起见取 0。

修法：输出层偏置 b2 乘 0，权重 W2 乘 0.01，初始损失就到了 3.32 附近。不直接设成 0，是因为他对把权重精确设为 0 很警惕，后面会看到原因；留一点小的随机性用于打破对称。

修完后损失曲线没有了「曲棍球杆」的形状：之前前几千步都在做一件容易的事，就是把过大的 logits 压下来，现在把这些步数省下来做真正的训练，验证损失从 2.17 降到 2.13。

问题二：tanh 饱和

损失看起来正常了，隐藏层里还有更深的问题。画出隐藏层激活 h 的直方图，绝大多数值是 −1 或 1；再看进入 tanh 之前的预激活，分布在 −15 到 15 之间，太宽了，tanh 把它们都压到了两端。

为什么要紧：tanh 的反向是 self.grad += (1 - t**2) * out.grad。t 接近 ±1 时 1 − t2 接近 0，梯度在这里被「杀掉」，反向传播停在这个神经元。

直观上这个神经元处在 tanh 平坦的尾部，改它的输入几乎不影响输出，所以对损失没有影响。t = 0 时梯度原样通过。经过 tanh 的梯度只会变小，越靠近尾部变得越小。

把 h.abs() > 0.99 画成一张 32×200 的黑白图，白色表示饱和。白的很多，但没有一整列是白的。如果某一列全白，就是死神经元：无论输入什么样本，它都处在平坦区，永远得不到梯度，永远不学习。

死神经元也会出现在别的激活函数上

sigmoid 也是挤压函数，有同样的问题。ReLU 在负半轴完全平坦，梯度是精确的 0，如果一个 ReLU 神经元对数据集里任何样本都不激活，它就是死的，权重和偏置永远不变。

这可能在初始化时碰巧发生，也可能在训练中发生：学习率太高时，某个神经元一次拿到很大的梯度，被推出数据流形，从此没有样本能激活它，他比喻成网络的「永久性脑损伤」。训练完把整个训练集过一遍，常能找到从不激活的神经元。Leaky ReLU 没有平坦区，基本不受影响；ELU 在负半轴也有平坦的部分。

修饱和

预激活是 embcat @ W1 + b1，太大，就让它小一些：偏置乘 0.01 留一点多样性，权重先乘 0.1，预激活就落在 −1.5 到 1.5，图上没有白点了；再试 0.2，分布也不错。这样训练完，验证损失从 2.13 降到 2.10。

初始化越好，越多步数花在有效的训练上，而不是梯度为 0 或者在压缩过自信的 softmax。这个网络只有一层隐藏层，优化问题很宽容，初始化很糟也能学会，只是结果差一点。换成 50 层的深网络，这些问题会叠加，初始化太差可能根本训练不动。

初始化尺度怎么算：Kaiming 初始化

0.2 这种数是看直方图猜出来的，大网络里没法这么干。示例：输入 x 是 1000×10 的标准高斯，权重 w 是 10×200 的标准高斯，y = x @ w 的均值仍是 0，标准差却变成了 3，分布被拉宽了。

w 乘 5 标准差到 15，乘 0.2 降到 0.6。数学上要保持标准差为 1，应该除以 √fanin，fanin 是输入个数，这里 10。

何恺明等的《Delving Deep into Rectifiers》仔细研究过这个问题，他们研究的是卷积网络和 ReLU。

ReLU 把负半轴全截成 0，丢掉一半分布，所以要乘一个增益来补偿：权重用标准差 √(2/fanin) 的零均值高斯初始化。论文也分析了反向传播，结论是前向初始化得当时，反向也大致得当，只差一个和各层大小有关的常数，实践中影响不大。

PyTorch 里的 torch.nn.init.kaiming_normal_ 就是它，他认为这大概是现在最常用的初始化方式。

mode 选按前向（fanin，默认）还是按反向归一化，大多数人不改；nonlinearity 决定增益：线性是 1，ReLU 是 √2，tanh 是 5/3。增益是因为 tanh 和 ReLU 都是收缩变换，会把分布的尾部往里挤，要把权重放大一点抵消。

为什么不用太较真

他说这部分故意讲得快。这篇论文 2015-02 写出来的时候，得非常小心激活值和梯度的范围、直方图、增益，网络越深越脆弱。

后来有几项进展让训练稳定得多，精确的初始化不再那么重要：残差连接；各种归一化层，比如 Batch Normalization、Layer Normalization、Group Normalization；更好的优化器，比如 RMSprop，尤其是 Adam。

他自己实际的做法就是把权重除以 √fanin。照 Kaiming 写：标准差应为增益除以 √fanin。W1 的 fanin 其实是 n_embd * block_size = 30，所以是 (5/3)/√30 ≈ 0.3，而之前凭直方图猜的是 0.2。用 0.3 训练，验证损失仍是 2.10，但不再需要魔数，可以推广到更大的网络。

Batch Normalization

2015 年 Google 团队的 Batch Normalization 影响很大，它让很深的网络能可靠地训练。想法很直接：我们希望预激活大致是单位高斯，太小 tanh 不起作用，太大 tanh 饱和，那就直接把它标准化成单位高斯。标准化是可微的运算，可以照常反向传播。他说第一次读到时「大受震撼」。

hpreact 是 32×200：沿批次维求均值和标准差（keepdim=True，得到 1×200），减均值、除以标准差，每个神经元在这 32 个样本上就变成了单位高斯。名字里的 batch 就是这个意思。

但只这样做效果不好，因为我们只希望初始化时是高斯，不想永远强制它是高斯，网络应该能根据反向传播把分布调宽、调窄、调偏。所以论文加了缩放和平移：可学习的增益 bngain（初始为 1）和偏置 bnbias（初始为 0），形状都是 1×200。初始化时输出正好是单位高斯，之后由梯度决定怎么变。这两个要放进参数列表。

bnmeani = hpreact.mean(0, keepdim=True)
bnstdi = hpreact.std(0, keepdim=True)
hpreact = bngain * (hpreact - bnmeani) / bnstdi + bnbias

它在这里没有提升，为什么还常用

训练完验证损失约 2.10，和之前差不多。这在预料之中：只有一层隐藏层，前面已经算出了能让预激活大致高斯的权重尺度。但网络一深、运算种类一多，再加上残差连接，想手工把每处激活都调成高斯基本不可能，而在每个线性层或卷积层后面加一个 Batch Normalization 要容易得多，也让训练稳定很多。

代价是一件「非常奇怪、不自然」的事：以前每个样本独立前向，批次只是为了效率；现在一个样本的隐藏状态和 logits 还取决于同一批里碰巧有哪些其他样本，因为均值和标准差是按批算的。换一批样本，h 和 logits 就会抖动。

奇怪的是，这种抖动对训练反而有好处：相当于给每个输入加了点噪声，类似数据增强，让网络更难过拟合具体样本，起到了正则化作用。

正因为这个副作用，大家虽然都不喜欢样本之间的耦合（它会导致各种怪结果和 bug），一直想换成 Layer Normalization、Instance Normalization、Group Normalization 这些不耦合样本的方法，却很难彻底去掉它。

推理时怎么办

训练完要部署，只想送进一个样本拿到预测，但网络现在要按批算均值和标准差。论文的办法是训练后再跑一个阶段：在整个训练集上算一次均值和标准差，固定下来，推理时用它们。这样单个样本也能前向，结果和之前基本一样。

没人想多跑一个阶段，所以论文还提了一个办法：训练时顺便维护滑动平均。bnmean_running 初始为 0，bnstd_running 初始为 1（初始化后预激活大致是单位高斯），每步在 torch.no_grad() 下更新：running = 0.999 * running + 0.001 * 当前批的值。

它们不参与梯度优化，只是在训练旁边跟着更新。训练结束后，滑动估计和全训练集上算的结果非常接近，验证损失基本不变。PyTorch 的 Batch Normalization 层也是这么实现的。

两个细节

公式分母里的 ε（默认 1e−5）是为了防止某批方差恰好为 0 时除以 0，这里他省略了。

第二个细节：Batch Normalization 前面那个线性层的偏置 b1 没用了。加上的任何偏置都会在减均值时被减掉，b1.grad 全是 0，它永远不会学习。所以只要后面跟着 Batch Normalization，前面的线性层或卷积层就不要偏置，偏置由 Batch Normalization 自己的 β 负责。留着也不会出大错，只是浪费。

小结，以及 ResNet 里的写法

Batch Normalization 用来控制网络中激活值的统计量，通常放在线性层或卷积层之后。它有两组参数 γ、β，靠反向传播训练；还有两个缓冲区（buffer）：滑动均值和滑动方差，不靠反向传播，而是用滑动平均更新。它对每批计算均值和标准差，标准化成单位高斯，再用学到的 γ、β 缩放平移，同时记下滑动统计量，推理时就用它们，可以单样本前向。

看 PyTorch 里 ResNet 的 Bottleneck 块：卷积层就是在图像的重叠小块上做 Wx + b 的线性层，后面跟 BatchNorm2d，再跟 ReLU，这个「权重层、归一化层、非线性」的组合反复堆叠，就是深度网络。

ResNet 里用 ReLU，这里用 tanh，二者可以互换，很深的网络里 ReLU 经验上更好一点。注意其中的卷积层都写了 bias=False，原因就是上面说的。

nn.Linear 和 nn.BatchNorm1d 的参数

nn.Linear(in_features, out_features, bias)：要知道 fanin 和 fanout 才能建权重，后面接归一化层时可以关掉偏置。默认初始化是从 −1/√fanin 到 1/√fanin 的均匀分布，和这里的做法一个道理，只是用均匀分布而不是高斯，增益是 1。

nn.BatchNorm1d(num_features, eps, momentum, affine, track_running_stats)：numfeatures 这里是 200；eps 默认 1e−5；momentum 默认 0.1，用于滑动平均。

这里用的是 0.001，因为批量只有 32，每批估出来的均值方差波动大，momentum 太大会让滑动统计量来回跳，收敛不到整个训练集的值；批量很大时用 0.1 没问题。affine 决定有没有 γ、β，几乎总是 True；trackrunningstats 可以关掉，比如打算训练后单独估统计量的时候。

这一集小结

这一集讲的是理解神经网络中激活值和梯度统计量的重要性，网络越大越深越重要。输出层太自信会导致曲棍球杆形状的损失曲线，修好后训练不做无用功，最终损失更低。激活值不能被压到 0，也不能爆到无穷，最好整个网络里都大致是高斯分布。浅网络里可以算好权重尺度，深网络里做不到，于是有了归一化层。

Batch Normalization 的复杂之处在于：标准化之外还要 γ、β，样本被耦合后推理要用统计量，又为了省掉第二阶段改成滑动估计。

他说自己被这个层坑过很多次，建议能不用就不用，Group Normalization、Layer Normalization 这些替代品在近年的深度学习里更常见。但它在 2015 年出现时影响很大，那是第一次能可靠地训练很深的网络。循环网络展开后就是非常深的网络，所以这些分析对它们很重要。

附赠：改写成 PyTorch 风格的模块

他说「我骗了你们」，还有一段总结。把代码整理成和 torch.nn 一样接口的模块。Linear(fan_in, fan_out, bias=True)：权重用高斯初始化再除以 √fanin，偏置初始为 0，__call__ 算 x @ W + b，parameters() 返回参数。

BatchNorm1d(dim, eps=1e-5, momentum=0.1)：有一个 training 标志，因为训练时用当前批的均值方差并更新滑动统计量，推理时用滑动统计量且不更新。这次照论文记滑动方差而不是标准差。

参数只有 γ、β，滑动均值和方差是缓冲区，不在 parameters() 里；更新它们要在 torch.no_grad() 下，否则 PyTorch 会为它们建计算图、白占内存。另外每层把输出存到 self.out，方便画图，这是 PyTorch 里没有的。Tanh 没有参数。

有了模块，搭网络就是排一个列表：嵌入表之后是 Linear、Tanh 交替的 6 层，共约 4.6 万个参数。初始化时最后一层权重乘 0.1 让 softmax 不那么自信，其余线性层乘增益 5/3。前向依次过每一层再接交叉熵；反向前对每层输出调用 retain_grad()，好把中间梯度也画出来。

class Linear:
    def __init__(self, fan_in, fan_out, bias=True):
        self.weight = torch.randn((fan_in, fan_out), generator=g) / fan_in**0.5
        self.bias = torch.zeros(fan_out) if bias else None
    def __call__(self, x):
        self.out = x @ self.weight
        if self.bias is not None:
            self.out += self.bias
        return self.out
    def parameters(self):
        return [self.weight] + ([] if self.bias is None else [self.bias])

诊断图：前向激活值和反向梯度

训练一步后，画出每个 tanh 层输出的直方图，并打印均值、标准差和饱和比例（|t| > 0.97 的比例）。增益 5/3 时第一层饱和约 20%，后面各层稳定在标准差约 0.65、饱和约 5%。

增益设成 1，标准差一层层缩小、饱和趋于 0：线性层本身按 1/√fanin 能保持标准差，但夹在中间的 tanh 每次都挤一下分布，需要一点增益抵消。增益设成 3，各层都过度饱和。

他说其实不知道 PyTorch 里 5/3 是怎么来的，没查到推导，但经验上它让线性加 tanh 的堆叠稳定在合理范围。

梯度也画同样的图。增益合适时各层梯度分布差不多，没有一路缩小或放大；增益 0.5 时激活缩向 0，梯度反而一层层扩散；增益 3 时也出现明显的不对称。没有 Batch Normalization 的时候，就得这么小心地调增益，前向和反向才都正常。

纯线性的情形，以及为什么需要 tanh

把 tanh 全去掉、增益仍为 5/3，激活值一层层扩散，梯度一层层衰减，这时正确的增益是 1。在归一化层、Adam、残差连接出现之前，训练神经网络就是这样一场「平衡游戏」，要精心安排一切才可能训练起来，非常深的网络基本训不动。

那为什么要 tanh。一堆线性层无论叠多少层，表示能力都只等于一个线性层，所有 Wx + b 会合并成一个。不过有意思的是，虽然前向会合并，反向传播的动力学并不一样，一层线性和十层线性的训练过程不同，有专门的论文分析无限多层线性网络。tanh 这类非线性才让这个堆叠变成原则上能逼近任意函数的神经网络。

诊断图：权重和它的梯度

只看二维参数（各线性层的权重，略过偏置和 γ、β），画梯度的直方图，并算梯度与数据之比：梯度的标准差除以参数值的标准差。更新是学习率乘梯度加到数据上，如果梯度比数据大太多就有麻烦。

大部分层的梯度约是数据的千分之一，最后一层是例外，大了约 10 倍。在简单的随机梯度下降下，这意味着初始化时最后一层的训练速度比其他层快 10 倍。训练 1000 步后会自己缓和一些，但用 Adam 这类现代优化器时问题会小得多。

诊断图：更新量与数据之比

真正要紧的是每一步实际改变了参数多少，所以他更常看更新量与数据之比：每步记录 log10(学习率 × 梯度的标准差 / 参数的标准差)，对每个权重画成随时间的曲线。经验上这个值应该在 −3 左右，也就是每步更新约为参数大小的千分之一。远高于 −3 说明更新太猛，远低于 −3 说明学得太慢。

图上最后一层一开始是离群的，因为初始化时人为把它乘了 0.1，参数值太小，比例暂时偏高，学一阵就稳定了。把学习率改成 0.001，所有曲线都掉到 −4 以下，一看就知道训练太慢，所以这张图也能用来定学习率。当前设置略高于 −3、约在 −2.5，可以接受。

再演示一个错误配置：线性层忘了除以 √fanin。激活图显示严重饱和，梯度图和权重图都乱了，更新比例各层差别很大，有的到了 −1、−1.5，学得太快。这些图能把各种配置错误摆到眼前。

加回 Batch Normalization

在每个线性层之后、tanh 之前加 BatchNorm1d，这是标准位置，放在非线性之后效果也差不多；最后一个线性层后面也可以放一个，这时让 softmax 不自信的办法是把那层的 γ 调小，而不是缩权重。

这下激活图必然好看，因为每个 tanh 前面都做了标准化：各层标准差约 0.65、饱和约 2%，很均匀；梯度、权重、更新比例也都正常。

好处是对增益不再敏感：增益改成 0.2，前向反向基本不受影响，但更新比例会变，因为 Batch Normalization 的反向和输入尺度有关，所以改了尺度可能要重调学习率。甚至可以不除以 √fanin，直接用标准高斯初始化，一切仍然正常，只是更新比例掉到 −3 以下，学习率要调大约 10 倍。

真正的小结

这一节想做到三件事。一是介绍 Batch Normalization 这项帮助稳定深层网络训练的现代技术。

二是把代码整理成 Linear、BatchNorm1d、Tanh 这样的模块，它们的接口和 PyTorch 一样，前面加上 nn. 就能直接换成 PyTorch 的层。三是介绍判断网络状态的诊断工具：前向激活、反向梯度、权重及其梯度的统计和直方图，以及随时间变化的更新与数据之比，经验值是 log 尺度上 −3 左右。

没打算做到的事：加了 Batch Normalization 他也试过用找学习率的办法训练，结果和之前非常接近，因为现在的瓶颈不在优化，而在上下文长度，只用 3 个字符预测第 4 个，要用循环网络、Transformer 这类更强的架构才能继续降低损失。

也没有完整解释改增益为什么要改学习率，那要深入每一层的反向传播。初始化和反向传播远没有被「解决」，仍是活跃的研究方向，但至少有了判断是否走在正轨上的工具。

这一集记住这几条

  • 训练前先估出初始损失应该是多少（这里是 −log(1/27) = 3.29）；远高于它说明输出层太自信，把最后一层权重缩小、偏置置零。
  • tanh、sigmoid、ReLU 的平坦区会杀掉梯度；预激活太宽会让大量神经元饱和，整列都饱和的是死神经元。
  • 权重按 增益 / √fanin 初始化（Kaiming），tanh 的增益是 5/3、ReLU 是 √2；有了归一化层、残差连接和 Adam，精确初始化没那么关键了。
  • Batch Normalization：按批标准化预激活，再乘可学习的 γ 加 β；训练时维护滑动均值方差，推理时用它们；前面的线性层不要偏置。
  • Batch Normalization 让同一批的样本互相耦合，带来正则化效果，也带来很多 bug；Layer Normalization 等不耦合样本的方法是替代品。
  • 诊断时看四样东西：各层激活和梯度的直方图、权重梯度与数据之比、更新量与数据之比随时间的曲线（log10 约 −3 为宜）。

为什么要手写反向传播

大家可能都急着看循环神经网络，但他还想在多层感知机上停一集，因为他对 loss.backward() 这一行有意见：用 PyTorch 的 autograd 算所有梯度，自己不知道里面发生了什么。

他的博客举过几个例子：平坦区饱和导致梯度消失、死神经元、循环网络里的梯度爆炸和消失。还有一段在网上随便找到的代码，作者想裁剪梯度的最大值，实际写成了裁剪损失，结果异常值的梯度被置为 0，等于被悄悄忽略了。这说明他不懂反向传播。

历史上手写反向传播曾经是常态。他展示了 2006 年 Hinton 和 Salakhutdinov 在《Science》上训练受限玻尔兹曼机的论文，以及自己 2010 年左右用 MATLAB 写的训练库：那时深度学习主要用 MATLAB，用对比散度估计梯度，再手动更新参数。

还有他 2014 年做图文片段对齐（fragment embeddings，有点像词和图像局部层面的 CLIP）的 NumPy 代码，损失和反向传播都是手写的，再用梯度检查核对数值梯度。他说现在大家都只调 loss.backward()，「我们失去了一些东西」。

起始代码

数据和网络都和上一集一样：嵌入表、第一个线性层、Batch Normalization、tanh、第二个线性层，隐藏层 64 个神经元。

有两处故意的改动：偏置不初始化为 0 而是小随机数，因为全 0 有时会让错误的梯度公式碰巧算对，掩盖 bug；第一层留着偏置 b1，虽然后面有 Batch Normalization 用不着它，但可以检验它的梯度是否也算对了。

前向被拆得很长：交叉熵不用 F.cross_entropy，而是显式写出减最大值、exp、求和、取倒数、乘、取 log、取平均；Batch Normalization 也拆成求均值、做差、平方、求方差、取倒数平方根等若干步。

每个中间张量 x 都对应一个要求的 dx，即损失对它的梯度。所有中间张量都调用了 retain_grad()，以便用 cmp 函数核对：它打印是否完全相等、是否近似相等（torch.allclose）以及最大差值。

logprobs 和 probs

dlogprobs 的形状和 logprobs 一样，32×27。损失是 -logprobs[range(n), Yb].mean()：每行取出正确字符那一列，32 个数取平均再取负。

用小例子想：loss = −(a + b + c)/3，对每一项的导数是 −1/3。推广开，被取出的 32 个位置梯度是 −1/n，其余没参与计算的位置梯度是 0。实现：torch.zeros_like(logprobs)，再把那些位置设为 -1.0/n。核对完全一致。

logprobs = probs.log() 是逐元素运算，log 的导数是 1/x，所以 dprobs = (1.0 / probs) * dlogprobs。直观上，正确字符的概率接近 1 时梯度基本原样通过；概率很低时 1/p 很大，这些预测得差的样本梯度被放大。

广播的反向是求和

先回顾前向：logits 每行减去最大值（为了数值稳定），exp 得到 counts，按行求和得到 counts_sum，取倒数（用 **-1，他说 PyTorch 对除法的反向有点问题），乘回去得到 probs。

probs = counts * counts_sum_inv，counts 是 32×27，countssuminv 是 32×1。这里有隐式的广播，实际是两步：先把这一列复制 27 份，再逐元素相乘。

乘法的局部导数是另一个因子，所以对复制后的那个矩阵，梯度是 counts * dprobs；而复制意味着同一个变量被用了 27 次，按 micrograd 里学过的，多次使用的变量梯度要相加，所以再按行求和、保留维度：(counts * dprobs).sum(1, keepdim=True)。

counts 的一个分支是 counts_sum_inv * dprobs（这里广播没问题）。但 counts 还通过 countssum 影响损失，这只是第一部分，要等另一支算完再用 += 加上。counts_sum_inv = counts_sum**-1，局部导数是 −countssum−2。

counts_sum = counts.sum(1, keepdim=True)：加法把梯度原样分发，b1 的梯度流到它所在那一行的每个元素，所以把 32×1 的 dcounts_sum 横向复制 27 份加到 dcounts 上，用 torch.ones_like(counts) * dcounts_sum 让广播完成复制。

他总结了一个对偶关系：前向里的求和，反向里变成沿同一维度的复制（广播）；前向里的复制（广播），反向里变成沿同一维度的求和。

normlogits 和 logitmaxes

counts = norm_logits.exp()，exp 的导数是它自己，正好就是 counts：dnorm_logits = counts * dcounts。

norm_logits = logits - logit_maxes，又有广播：logitmaxes 是 32×1。对 logits 的梯度原样复制（.clone()），对 logitmaxes 的梯度取负再按行求和。logits 也还有另一支，先记着。

他停下来看了看 dlogit_maxes：减去最大值只是为了数值稳定，给每行加减同一个数不改变 softmax，也就不改变损失，所以它的梯度理应是 0。

结果确实是 1e−9 量级的数，有些行正好是 0，差别来自浮点误差。即使把一切拆到原子级、按数值稳定的方式计算，也能得到正确结果。用 F.cross_entropy 这类合并实现时，可以直接跳过这一支。

logits 的第二支来自 logits.max(1)：max 同时返回值和下标，反向要把 dlogit_maxes 送回最大值所在的位置。

他用 F.one_hot(logits.max(1).indices, num_classes=27) 构造每行只有一个 1 的矩阵，乘以 dlogit_maxes（广播），再 += 到 dlogits 上。

线性层：矩阵乘法的反向

logits = h @ W2 + b2，h 是 32×64，W2 是 64×27，b2 是 27（广播成行向量后竖直复制 32 份）。不需要查矩阵微积分，回到基本原理：写一个 2×2 的小例子 D = AB + C，把每个元素展开，比如 d11 = a11b11 + a12b21 + c1，全是乘法和加法。

例如 a11 出现在 d11 和 d12 里，所以 ∂L/∂a11 = (∂L/∂d11)·b11 + (∂L/∂d12)·b12。把所有元素写齐，会发现整体正好是一个矩阵乘法：∂L/∂A = (∂L/∂D)·BT。同理 ∂L/∂B = AT·(∂L/∂D)，∂L/∂C 是 ∂L/∂D 按列求和。矩阵乘法的反向还是矩阵乘法。

他透露了个秘诀：这些公式他从来记不住，靠的是形状必须对上。dh 必须是 32×64，它一定是 dlogits（32×27）和 W2（64×27）的某种矩阵乘法，唯一能凑出 32×64 的写法是 dlogits @ W2.T；dW2 必须是 64×27，只能是 h.T @ dlogits；db2 是 27，只能是 dlogits 沿第 0 维求和。

dh  = dlogits @ W2.T
dW2 = h.T @ dlogits
db2 = dlogits.sum(0)

tanh 和 Batch Normalization 的参数

tanh 的导数用输出表示：a = tanh(z) 时 da/dz = 1 − a2，a 是输出 h，所以 dhpreact = (1.0 - h**2) * dh。

hpreact = bngain * bnraw + bnbias，这里是逐元素乘法，不是矩阵乘法，但 bngain、bnbias 是 1×64，会被竖直复制。

所以 dbngain = (bnraw * dhpreact).sum(0, keepdim=True)，dbnraw = bngain * dhpreact（广播方向和前向一致，不用求和），dbnbias = dhpreact.sum(0, keepdim=True)。

Batch Normalization 内部

前向拆成：bnmeani 是均值，bndiff = hprebn - bnmeani，bndiff2 = bndiff2，bnvar 是平方和除以 n − 1，bnvar_inv = (bnvar + 1e-5)-0.5，bnraw = bndiff * bnvar_inv。

bnraw = bndiff * bnvar_inv：dbndiff = bnvar_inv * dbnraw；dbnvar_inv 要按第 0 维求和、保留维度，因为 bnvarinv 是 1×64。

此时核对 dbndiff 会显示不对，这是预期的：bndiff 还通过 bndiff2、bnvar 影响损失，另一支还没算。也说明 cmp 确实能发现错误。

幂 −0.5 的局部导数按幂法则是 −0.5·(bnvar + ε)−1.5。bnvar 是 bndiff2 按列求和再乘 1/(n − 1)，反向是把 1×64 的梯度竖直复制并乘 1/(n − 1)。bndiff2 = bndiff**2 的导数是 2·bndiff，+= 到 dbndiff 上，这下 dbndiff 对了。

bndiff = hprebn - bnmeani：对 hprebn 的梯度原样复制；对 bnmeani 是取负再按第 0 维求和。hprebn 的另一支来自 bnmeani = hprebn.sum(0)/n：梯度乘 1/n 再竖直复制，+= 上去。Batch Normalization 层就推完了。

插曲：Bessel 校正

方差这里他除以 n − 1，而论文里是除以 m（批量大小）。估计方差有两种：除以 n 的有偏估计，除以 n − 1 的无偏估计。样本少时，有偏估计几乎总是低估方差；小批量正是从整个训练集里抽的小样本，所以建议用无偏估计。

论文在这点上写得不清楚：训练时用有偏估计，推理时估计滑动方差却用无偏估计，造成训练和测试不一致。PyTorch 的 BatchNorm1d 照搬论文，文档还说错了，已经有人在 issue 里指出。

他把这种不一致看成 bug，自己在训练和测试中都统一用 n − 1。批量较大时问题不明显，但他就是「不喜欢」。torch.var 的 unbiased 参数默认是 True，文档里却没写清。

第一个线性层、view 和嵌入表

第一个线性层 hprebn = embcat @ W1 + b1：embcat 32×30，W1 30×64，b1 64，照形状写出 dembcat = dhprebn @ W1.T、dW1 = embcat.T @ dhprebn、db1 = dhprebn.sum(0)。

embcat = emb.view(32, 30) 只是换一种方式解释同一块数据，反向就是把梯度再 view 回原来的形状：demb = dembcat.view(emb.shape)。

最后是 emb = C[Xb]：Xb 是 32×3 的整数，每个整数指定从 C 里取哪一行，取出的行拼成 32×3×10。反向要把每个 10 维梯度送回它来自的那一行；同一行会被取用很多次，梯度要累加。他说想不出更好的向量化写法，就用了两层 for 循环。到此整张图推完，全部和 PyTorch 一致。

dC = torch.zeros_like(C)
for k in range(Xb.shape[0]):
    for j in range(Xb.shape[1]):
        ix = Xb[k, j]
        dC[ix] += demb[k, j]

练习二：交叉熵一步到位

练习一做了太多工作。把损失的数学式写出来直接求导，很多项会相消，结果比逐行反向简单得多，前向和反向都快得多。F.cross_entropy(logits, Yb) 算出的损失和拆开的版本完全一样。

对单个样本，损失 = −log pᵧ，p 是 softmax。对第 i 个 logit 求导，要分 i 等于标签 y 和不等于两种情况，化简后结果非常简单：i ≠ y 时是 pi，i = y 时是 pi − 1。批量的损失是平均值，所以还要除以 n。和 PyTorch 的结果不是逐位相等，最大差约 5e−9，是浮点误差。

dlogits = F.softmax(logits, 1)
dlogits[range(n), Yb] -= 1
dlogits /= n

dlogits 的直观含义

把 dlogits 画出来是 32×27，就是概率矩阵，只是每行正确字符的位置减了 1（图上的黑格）。取第一行乘以 n：等于那一行的概率，只有正确位置减了 1，整行加起来正好是 0。

可以把每个格子里的梯度想成一个力：把错误字符的概率往下拉，把正确字符的概率往上拉，上拉和下拉的总量相等。整个网络像一套复杂的滑轮系统，顶端的拉力最终传到每个权重和偏置上，每次更新参数就顺着拉力让一点。

拉力大小正比于预测错的程度：预测完全正确（正确位置为 1、其余为 0）时这一行全是 0，不拉也不推；如果非常自信地预测错了某个字符，它会被狠狠往下拉，正确字符被往上拉同样多。这就是交叉熵损失在反向传播中的作用。

练习三：Batch Normalization 的反向

同样把 Batch Normalization 当成一个整体，从 dhpreact 直接算 dhprebn（这里先忽略 γ、β，它们的梯度很简单）。

按论文写出 μ、σ2、x̂i、yi 的定义（方差用 Bessel 校正），画出计算图：μ 和 σ2 是标量，x、x̂、y 是向量，有很多个节点，这一点要特别注意。建议按拓扑序倒着推：先 x̂，再 σ2，再 μ，最后 x。

∂L/∂x̂i = γ·∂L/∂yi。σ2 扇出到所有 x̂i，所以 ∂L/∂σ2 要对所有 i 求和。μ 有 32 条边连到各个 x̂i，还有一条边连到 σ2，共 33 条，梯度都要相加；有意思的是，当 μ 恰好是 xi 的平均值时，∂σ2/∂μ 化简后正好是 0，那一整项消失了。

每个 xi 有三条出边：到 μ、到 σ2、到它自己的 x̂i（x̂i 只依赖 xi，32 条边平行互不干扰），三条路径的贡献相加。把前面的结果代进去时要小心：求和用的下标要从 i 改成 j，以免和外面的 i 混淆。

提取出 (σ2 + ε)−3/2 并拆成三个 (σ2 + ε)−1/2，分配到不同的项里，有些项正好凑成 x̂，最后得到一个很紧凑的公式，只用到上游梯度和前向算过的 x̂。

这个公式是对单个神经元、32 个样本推的，代码里要对 64 个神经元并行计算，还要保证里面那些求和能正确广播。他说把纸上的式子写成这一行代码本身就是个不小的练习。结果和 PyTorch 近似一致，最大差约 9e−10。

dhprebn = bngain*bnvar_inv/n * (n*dhpreact - dhpreact.sum(0)
                                - n/(n-1)*bnraw*(dhpreact*bnraw).sum(0))

练习四：用自己的梯度训练

把前面推出的梯度代码（用的是交叉熵和 Batch Normalization 的简化版本）拼在一起，替换掉 loss.backward()：交叉熵、第二个线性层、tanh、Batch Normalization、第一个线性层、嵌入表，一共二十行左右。

先跑 100 步后停下，和 PyTorch 核对，差约 1e−9；确认无误后去掉核对和 loss.backward()，更新时不再用 p.grad，而是把参数和自己算的梯度配对：p.data += -lr * grad。

既然不再需要 autograd，可以把整个训练循环放进 torch.no_grad()，PyTorch 就不会记录计算图。训练结束后单独校准 Batch Normalization 的统计量（训练时没有维护滑动均值），评估得到的损失和以前差不多，采样出的名字也一样像样。区别在于这次完全没有用 PyTorch 的 autograd。

他的结论：每一层的反向也就三行左右，除了 Batch Normalization，大多相当直接。实际工作中当然还是用 autograd，但希望大家对梯度如何从损失出发、流过每个中间变量有了直觉。下一集终于要讲循环神经网络和 Long Short-Term Memory 了。

这一集记住这几条

  • 反向传播是有漏洞的抽象：不懂内部就会写出裁剪损失代替裁剪梯度这类 bug，也没法调试梯度消失、死神经元。
  • 前向里的求和对应反向里沿同一维度的复制，前向里的广播（复制）对应反向里沿同一维度的求和，还要保留维度。
  • 矩阵乘法 D = AB 的反向：dA = dD·BT，dB = AT·dD；记不住就靠形状凑，形状只有一种对得上的写法。
  • 一个变量被用在多处（counts、logits、bndiff、hprebn），各支的梯度用 += 累加；嵌入表的反向是把梯度加回被取出的行。
  • 交叉熵对 logits 的梯度：(softmax(logits) − onehot(y)) / n，相当于把错误字符往下拉、正确字符往上拉，力度正比于预测错的程度。
  • Batch Normalization 的反向可以合成一行公式；训练时有偏、推理时无偏的方差估计是论文和 PyTorch 里的训练测试不一致。

这一集要做什么

上几集搭到的是一个字符级的多层感知机：输入前 3 个字符，经过一层 tanh 隐藏层，预测第 4 个。现在要让它更复杂：输入更多字符；而且不想把所有字符一下子压进一个隐藏层，那样信息压缩得太快，想要一个更深的模型，逐步融合信息。

WaveNet 是 DeepMind 2016 年的论文，其实也是一个语言模型，自回归地预测下一个元素，只是对象是音频。它预测下一个元素时用的是一种树状的层级结构，这一集就要实现这个结构。

起始代码

起始代码来自第三部分（第四部分手推反向传播算是个插曲）：数据处理不变，有 18.2 万个「给定 3 个字符预测第 4 个」的样本。层模块沿用上一集写的 Linear、BatchNorm1d、Tanh，接口和 torch.nn 对应的层一致。

他再次吐槽 Batch Normalization 是个「很怪的层」：滑动均值方差不靠反向传播，而是在前向里用指数滑动平均更新；有个 training 标志，训练和评估时行为不同，忘了切换就会出 bug；还把同一批的样本耦合在一起；滑动统计量还得等它收敛到稳态。

「状态通常是有害的。」另外随机数生成器改成在外面全局设一次种子。网络是嵌入表加 Linear、BatchNorm1d、Tanh、输出 Linear，约 1.2 万参数，验证损失 2.10，采样出 ivon、kilo、pros、alaya 这类名字。

把损失曲线画清楚

原来的损失曲线非常「厚」，批量只有 32，每批运气好坏差别很大，他说看着「刺眼」。办法是用 view 把 20 万个损失值排成 200×1000，每行是连续的 1000 步，按行取平均再画：torch.tensor(lossi).view(-1, 1000).mean(1)。

新曲线清楚多了，还能看到学习率衰减那一下让损失明显下了一个台阶，网络沉到了一个局部最小值里。

整理成模块

前向里还有两件事在层列表外面：用索引查嵌入表，以及用 view 拼接嵌入（几乎没有代价，不复制内存）。给它们各写一个模块：Embedding(num_embeddings, embedding_dim)，权重就是原来的 C，前向是索引；Flatten，前向是 view。

这两个名字在 PyTorch 里都有对应的层，只是那边参数更多。这样嵌入表也进了层列表，前向直接把整数张量 Xb 送进第一层。

再进一步，PyTorch 有容器（container）的概念，把层组织成列表或字典。Sequential 保存一个层列表，前向时依次通过，参数就是所有子模块的参数。

写一个自己的 Sequential 以后，就有了一个 model，参数是 model.parameters()，前向是 logits = model(Xb)，评估和采样的代码也大大简化。

class Embedding:
    def __init__(self, num_embeddings, embedding_dim):
        self.weight = torch.randn((num_embeddings, embedding_dim))
    def __call__(self, IX):
        self.out = self.weight[IX]
        return self.out
    def parameters(self):
        return [self.weight]

class Sequential:
    def __init__(self, layers):
        self.layers = layers
    def __call__(self, x):
        for layer in self.layers:
            x = layer(x)
        self.out = x
        return self.out
    def parameters(self):
        return [p for layer in self.layers for p in layer.parameters()]

又被 Batch Normalization 坑了一次

改完采样，结果出错了。原因是改了评估那个单元格却忘了运行，模型还处在训练模式，而采样时送进去的批次只有一个样本，Batch Normalization 用这一个样本算方差，一个数的方差是 nan，后面全被污染了。

评估损失时也会出同样的问题，只是不报错，会算出一个错的数，因为它用的是这一批的统计量，而不是滑动均值方差。又是一个因为没维护好训练状态引入的 bug。

重新跑完：训练损失 2.05，验证 2.10。两者接近，说明没怎么过拟合，可以通过加大网络继续提升。问题是现在的结构没法有效地加大：就算加层、加神经元，所有字符还是在第一步被压进一层。

WaveNet 的思路，以及简单的基线

WaveNet 里，预测下一个元素依赖前面的元素，但不是一下子压进一层：先把相邻两个字符融合成类似 bigram 的表示，再把相邻两个 bigram 融合成 4 字符的块，以此类推，信息随着网络加深慢慢融合。论文里画的是一叠膨胀因果卷积（dilated causal convolution）层，听着吓人，其实想法很简单，卷积只是为了算得快，后面再说。

先把 block_size 从 3 改成 8，用 8 个字符预测第 9 个。网络什么都不改就能跑，只是第一个线性层变大了，参数多了 1 万，约 2.2 万。这个结构不太合理，但先跑一下看基线：验证损失从 2.10 降到 2.02，采样的名字也明显更好。

矩阵乘法可以有多个批维度

临时取 4 个样本看各层的形状：Xb 是 4×8；嵌入层输出 4×8×10；Flatten 后是 4×80，相当于把 8 个 10 维向量拼成一行；线性层把 80 变成 200。

一个可能让人意外的事实：PyTorch 的矩阵乘法 @ 不要求输入是二维的。(4, 5, 80) @ (80, 200) 得到 (4, 5, 200)，矩阵乘法只作用在最后一维，左边的所有维度都当作批维度并行处理。

这正是需要的：不想一下子把 80 个数乘进权重矩阵，而是把相邻两个字符分成一组（1 和 2、3 和 4、5 和 6、7 和 8），每组 20 个数乘同一个权重矩阵，4 个组当作第二个批维度并行算。也就是让 Flatten 输出 4×4×20，第一个线性层只接收 20 个输入。

FlattenConsecutive

怎么从 4×8×10 得到 4×4×20：可以显式地取出偶数位置 e[:, ::2, :] 和奇数位置 e[:, 1::2, :]，沿最后一维拼接；但直接 e.view(4, 4, 20) 得到的结果完全一样，所以还是用 view。

新写一个 FlattenConsecutive(n)，表示把 n 个相邻元素拼到最后一维。因为 PyTorch 的 torch.flatten 参数和行为都不一样，所以换了名字。

输入形状记作 B×T×C，输出 x.view(B, T//n, C*n)；他不喜欢用 −1，宁可写明预期的形状，不对就报错。如果中间那维是 1（比如 n 等于整个块长），就 squeeze(1) 去掉，返回二维张量，和原来的行为一致。

用 FlattenConsecutive(8) 能复现原来的网络。改成层级结构：FlattenConsecutive(2)、Linear(n_embd*2, n_hidden)、BatchNorm1d、Tanh，这一组重复三次（后两组的输入是 n_hidden*2），最后接输出层。

形状依次是 4×4×20、4×4×200、4×2×400、4×2×200、4×400、4×200，最后一次 Flatten 去掉了长度为 1 的那一维，logits 形状和原来一样。这对应 WaveNet 图里三层的那一块；图里是四层、感受野 16 个字符。

class FlattenConsecutive:
    def __init__(self, n):
        self.n = n
    def __call__(self, x):
        B, T, C = x.shape
        x = x.view(B, T//self.n, C*self.n)
        if x.shape[1] == 1:
            x = x.squeeze(1)
        self.out = x
        return self.out
    def parameters(self):
        return []

第一次训练

把隐藏单元设成 68，这样参数正好也是约 2.2 万，和扁平的基线一样多，看相同参数量下层级结构能不能更有效地利用参数。结果验证损失 2.029，基线是 2.027，没有提升。他说这里还没怎么折腾这个结构，参数怎么分配给各层有很多可以搜的；另外 Batch Normalization 里可能还有 bug。

BatchNorm1d 遇到三维输入

它确实能跑，但做对了吗。Batch Normalization 现在收到的输入是 32×4×68，而当初写它时假设输入是 N×D 的二维张量，只沿第 0 维求均值方差。因为广播都合法，所以不报错，但结果不对：均值形状是 1×4×68，滑动均值也是 1×4×68。也就是说它给 4 个位置各自独立维护了 68 个通道的统计量，每个只用 32 个数估计。

想要的是把这个 4 也当成批维度，对每个通道用 32×4 个数估计。torch.mean 的 dim 参数可以是元组，沿 (0, 1) 两维同时求平均，得到 1×1×68。修法：x.ndim == 2 时沿 0 维，x.ndim == 3 时沿 (0, 1)，其他情况报错。

这和 PyTorch 的 BatchNorm1d 不一样：PyTorch 接受 N×C 或 N×C×L，通道在第 1 维，三维输入时沿 0 和 2 求平均；这里接受 N×C 或 N×L×C，通道在最后一维。

他更喜欢这种约定，就保留了。修完后滑动均值是 1×1×68，重新训练验证损失从 2.029 到 2.022，可能有一点提升，未必显著；用更多的数估计统计量会更稳定。

if x.ndim == 2:
    dim = 0
elif x.ndim == 3:
    dim = (0, 1)
xmean = x.mean(dim, keepdim=True)
xvar = x.var(dim, keepdim=True)

和卷积的关系

卷积在 WaveNet 里纯粹是为了效率，不改变这里实现的模型。拿训练集里的 deandre 举例：7 个字母对应 8 个独立样本，每一行可以单独送进模型（Xtr7 多套一层列表，形状变成 1×8，补出批维度），8 行就是 8 次独立调用。

卷积做的是把这个模型高效地在输入序列上滑动：这个 for 循环不在 Python 里，而是在 CUDA kernel 里完成。卷积可以看成一个在序列上滑动的线性滤波器。

论文图里黑色高亮的那棵树就是这里实现的东西，算一个输出；卷积把这棵树沿序列滑过去，同时算出所有位置的输出。更快的另一个原因是复用：某个中间节点既是一个节点的右孩子，又是旁边节点的左孩子，朴素做法要重复计算，卷积只算一次。之后的视频会讲卷积。

语言模型和 Transformer

让 ChatGPT 写一首关于「人们理解 AI 有多重要」的俳句，同一个提示跑两次会得到不同的结果，它是一个概率系统。网上有很多有趣的例子，比如「写一篇关于树叶从树上掉下来的突发新闻」。它是一个语言模型：对词、字符或更一般的 token 序列建模，知道在英语里它们怎么接续；从它的角度，它在做的是补全序列。

数据和分词

在 Google Colab 里下载 tiny Shakespeare，读成一个约 100 万字符的字符串。用 sorted(list(set(text))) 得到所有出现过的字符，共 65 个（空格、标点、大小写字母），这就是词表大小。

分词（tokenize）就是按某个词表把原始字符串转换成整数序列。这里是字符级：建 stoi、itos 两张表，encode 把字符串逐字符转成整数，decode 反过来。

实践中用的多是子词级的：Google 的 SentencePiece，OpenAI 的 tiktoken（GPT 用的字节对编码）。tiktoken 的 GPT-2 编码有 50257 个 token，「hi there」只编码成 3 个整数。词表大小和序列长度此消彼长：词表小则序列长，词表大则序列短。这里为了简单用字符级。

把整个文本编码后放进 torch.tensor，前 90% 作训练集，后 10% 作验证集，用来判断过拟合程度：我们不想要一字不差地记住莎士比亚，而是能生成像莎士比亚的文本。

按块取数据

不会把整个文本一次送进 Transformer，太贵了，而是随机取出一小块一小块地训练。块的最大长度叫 block_size（也叫上下文长度），先取 8。

取 blocksize + 1 = 9 个字符，里面其实藏着 8 个训练样本：在 18 之后预测 47，在 18、47 之后预测 56……x 是前 8 个，y 是错开一位的 8 个，作为每个位置的目标。

训练时包含从 1 到 blocksize 所有长度的上下文，这不只是为了效率，也是为了让 Transformer 习惯各种长度的上下文，这样生成时从一个字符开始也能预测；超过 blocksize 以后就得截断，因为它从没见过更长的输入。

再加一个批维度：一次处理多个块，块之间完全独立，只是为了让 GPU 并行。get_batch 随机生成 batch_size 个起点，取出 x 和错开一位的 y，用 torch.stack 堆成 4×8 的张量。这一批里共有 32 个独立的样本。

def get_batch(split):
    data = train_data if split == 'train' else val_data
    ix = torch.randint(len(data) - block_size, (batch_size,))
    x = torch.stack([data[i:i+block_size] for i in ix])
    y = torch.stack([data[i+1:i+block_size+1] for i in ix])
    return x, y

bigram 基线

最简单的语言模型是 bigram，makemore 里讲过，这次直接写成 nn.Module。构造函数里建一个 vocab_size × vocab_size 的 nn.Embedding，前向时每个整数取出对应的一行，排成 B×T×C（4×8×65）的 logits：只根据当前 token 自己的身份预测下一个，token 之间还没有交流。

损失用 F.cross_entropy，但它要求多维输入时通道在第二维（B×C×T），所以把 logits view 成 (B·T)×C、targets view 成 B·T。初始损失 4.87，理论上均匀分布应是 −ln(1/65) ≈ 4.17，说明初始预测不够分散。

generate(idx, max_new_tokens) 把 B×T 的上下文一步步延长：前向得到 logits，只取最后一个时间步，softmax 后用 torch.multinomial 采一个，拼到序列后面。

targets 设为可选，没有时不算损失。从一个 0（换行符）开始生成 100 个字符，因为模型是随机的，结果全是乱码。对 bigram 来说把整个上下文送进去很可笑，只用到最后一个字符，但这样写之后接 Transformer 不用改。

训练用 AdamW 优化器，比 makemore 里用的随机梯度下降先进得多，常用学习率约 3e−4，这种小网络可以用 1e−3 甚至更大。批量改成 32，训练 1 万步后损失约 2.5，生成的东西开始有点样子，当然离莎士比亚还远。

让 token 互相交流：先取平均

在写自注意力之前，先用一个 B×T×C = 4×8×2 的玩具例子熟悉一个数学技巧。现在 8 个 token 互不交流，想让它们交流，但方式有约束：第 5 个位置只能和第 4、3、2、1 个交流，不能看第 6、7、8 个，因为那是要预测的未来。

最简单的交流是对过去（含自己）取平均，得到一个概括「我和我的历史」的特征向量。这是非常弱的交互，丢掉了位置排列的信息，但先这样。用两层 for 循环写出来叫 xbow（bag of words，词袋，即只做平均）：第一个位置就是它自己，第二个是前两个的平均，以此类推。

技巧：下三角矩阵乘法

3×3 全 1 矩阵 A 乘 3×2 的 B，C 的每个元素是 B 对应列的和。把 A 换成 torch.tril(torch.ones(3, 3))（下三角），C 的第一行就是 B 的第一行，第二行是前两行之和，第三行是三行之和。再把 A 的每行归一化使其和为 1（1；0.5、0.5；1/3、1/3、1/3），C 就变成了 B 前若干行的递增平均。

于是 wei = torch.tril(torch.ones(T, T))，每行归一化，xbow2 = wei @ x：(T, T) @ (B, T, C)，PyTorch 会自动补出批维度做批量矩阵乘法，得到 B×T×C，和循环版本完全一致。这就是用矩阵乘法做加权聚合，权重写在 T×T 的矩阵里，下三角保证每个位置只从之前的位置拿信息。

第三种写法用 softmax：wei 先全为 0，用 masked_fill 把 tril == 0 的位置填成 −∞，再按行 softmax。exp(0) = 1，exp(−∞) = 0，归一化后得到同样的矩阵。

这种写法在自注意力里更有意思：可以把 wei 里的 0 看成 token 之间的亲和度（affinity），现在是我们设成的常数，接下来它会和数据相关，token 会互相「看」，觉得有的更有意思；−∞ 表示未来的 token 不能参与。视频描述里有一处更正：他在这一段口误说成了「过去的 token 不能交流」，应该是未来的。

tril = torch.tril(torch.ones(T, T))
wei = torch.zeros((T, T))
wei = wei.masked_fill(tril == 0, float('-inf'))
wei = F.softmax(wei, dim=-1)
xbow3 = wei @ x

准备工作：嵌入维度和位置编码

把嵌入表改成输出 n_embd = 32 维的 token 嵌入（他说这个数也是 GitHub Copilot 建议的），再接一个线性层 lm_head 映射到词表大小得到 logits，中间多了一层间接。

除了 token 的身份，还要编码它的位置：加一张 block_size × n_embd 的位置嵌入表，用 torch.arange(T) 取出 T×C 的位置嵌入，和 B×T×C 的 token 嵌入相加（广播到每个批次）。对 bigram 模型来说位置还没用，有了自注意力就有用了。

核心：自注意力

这是整个视频最重要的部分。现在 wei 是均匀的，但不同的 token 会对不同的其他 token 更感兴趣，而且应该取决于数据：比如我是一个元音，也许想在过去找辅音，并让那些信息流向我。自注意力就是解决这个问题的。

每个位置的 token 发出两个向量：query（大致是「我在找什么」）和 key（「我包含什么」）。亲和度就是我的 query 和其他所有 token 的 key 的点积，两者对得上，交互就强，我就会从那个 token 学到更多。

实现一个头（head）：key、query 是两个不带偏置的线性层，headsize 取 16；所有位置并行、独立地算出 k、q（B×T×16），这时还没有交流；然后 wei = q @ k.transpose(-2, -1)，(B, T, 16) @ (B, 16, T) 得到 B×T×T 的亲和度。

现在每个批次元素的 wei 都不一样了，因为内容不同。比如第 8 个 token 知道自己的内容和位置，据此生成 query：「我是元音，在第 8 位，我在找 4 号位以前的辅音」；所有节点发出 key，其中某个通道也许表示「我是辅音，在 4 号位以前」，点积就会很大。

去掉掩码和 softmax 看原始点积，值在 −2 到 2 之间；加上上三角掩码后未来位置不参与，再 exp、归一化，得到一个和为 1 的分布。

最后一部分：聚合的不是 x 本身，而是再过一个线性层得到的 value：out = wei @ v，输出是 16 维的。可以把 x 看成 token 的私有信息；对这个头来说，query 是「我感兴趣什么」，key 是「我有什么」，value 是「如果你觉得我有意思，我告诉你这些」。

key = nn.Linear(C, head_size, bias=False)
query = nn.Linear(C, head_size, bias=False)
value = nn.Linear(C, head_size, bias=False)
k, q = key(x), query(x)                  # (B, T, 16)
wei = q @ k.transpose(-2, -1)            # (B, T, T)
wei = wei.masked_fill(tril == 0, float('-inf'))
wei = F.softmax(wei, dim=-1)
out = wei @ value(x)                     # (B, T, 16)

关于注意力的几点说明

一，注意力是一种通信机制：有向图里每个节点有一个信息向量，以数据相关的权重对指向它的所有节点做加权求和。这里的图结构是：第 1 个节点只被自己指向，第 2 个被第 1 个和自己指向……第 8 个被所有之前的节点和自己指向，这是自回归语言建模的情形，但注意力可以用在任意有向图上。

二，注意力没有空间概念，只作用在一组向量上，节点不知道自己在哪，所以要显式加上位置编码。这和卷积不同，卷积的滤波器本身就在空间上作用。

三，批维度上的样本永远不交流，批量矩阵乘法在各批次上独立地并行计算。所以与其说有 32 个节点，不如说是 4 组各 8 个节点，每组内部交流。

四，编码器块和解码器块：语言建模里未来的 token 不能和过去交流，否则就泄露了答案。但在情感分析这类任务里，可以让所有 token 充分交流，那就去掉掩码那一行，这叫编码器块；保留三角掩码的叫解码器块，因为它以自回归的方式「解码」语言。

五，叫自注意力是因为 key、query、value 都来自同一个 x。更一般的是交叉注意力：query 来自 x，key 和 value 来自另一个外部来源，比如编码器块编码的、我们想作为条件的上下文。

为什么除以 √headsize

论文里的公式还要除以 √dk，dk 是 headsize，叫缩放点积注意力。如果 k、q 是单位高斯，直接点积得到的 wei 方差约为 headsize（这里是 16）；乘以 1/√headsize 后方差回到 1。

这很重要，因为 wei 要进 softmax，尤其在初始化时 wei 应该比较分散。softmax 的输入取值很极端时，输出会趋向 one-hot：把一组接近 0 的数乘以 8 再 softmax，结果明显向最大值收拢。

那样每个节点只会从一个其他节点聚合信息，初始化时不希望这样。所以缩放是为了控制初始化时的方差。（视频描述里的另一处更正：后面代码里他用 C 做了归一化，应该用 headsize。）

接进网络，再做成多头

把单个头写成 Head 模块。下三角矩阵不是参数，按 PyTorch 的命名惯例叫缓冲区（buffer），用 register_buffer 注册。语言模型里在 token 嵌入加位置嵌入之后接一个自注意力头（headsize 先等于 nembd），再接 lm_head。

生成时要把上下文截到最后 blocksize 个 token，否则位置嵌入表会越界。自注意力受不了太大的学习率，所以调低学习率、增加迭代次数。验证损失从 2.5 降到 2.4。

论文的多头注意力就是并行跑多个注意力，再把结果拼起来。用 nn.ModuleList 建若干个头，输出沿通道维拼接。原来是一个 32 维的通信通道，现在是 4 个各 8 维的通道，拼起来仍是 32 维，有点像分组卷积。损失降到 2.28。多个独立的通道有好处，因为 token 之间要交流的东西很多：找辅音、找元音、找某些位置上的元音等等。

前馈层

论文里每个块还有一个按位置独立计算的前馈网络，就是一个小的多层感知机。之前 token 互相看过之后，立刻就去算 logits 了，没时间「思考」看到的东西。加一个线性层加 ReLU 的 FeedForward，放在自注意力之后。它对每个 token 独立地计算：自注意力负责通信，收集到数据后各自思考。损失从 2.28 降到 2.24。

接下来要把通信和计算交替起来：一个 Block 里先做多头自注意力（通信），再做前馈（计算）。nembd 为 32、头数为 4 时，每个头的大小是 8，这是 Transformer 通常的安排。把几个块串起来以后，效果反而不好，因为网络开始变深，深网络有优化上的困难。论文里有两个办法。

残差连接

第一个是图里的那些箭头：残差连接（skip connection），来自 2015 年的《Deep Residual Learning for Image Recognition》。他喜欢这样想：有一条从上到下的残差通路，可以从通路分叉出去做一些计算，再通过加法投回通路。从输入到输出只经过一连串加号。

反向传播时，micrograd 里讲过，加法把梯度原封不动地分给两个分支，于是损失的梯度沿着这条「梯度高速公路」畅通无阻地一直传到输入，同时也分进各个残差块。残差块通常初始化得在一开始几乎不起作用，像不存在一样，训练过程中才逐渐「上线」开始贡献。这大大帮助了优化。

实现：x = x + self.sa(x)，x = x + self.ffwd(x)。多头注意力拼接之后再加一个线性的投影层投回残差通路，前馈网络末尾也加一个。

另外照论文，前馈网络内层的维度是输入输出的 4 倍（论文里是 512 和 2048）。这样训练，验证损失到了 2.08，网络开始足够大，训练损失领先于验证损失，出现一点过拟合；生成的文本开始有点像英语了。

class Block(nn.Module):
    def __init__(self, n_embd, n_head):
        super().__init__()
        head_size = n_embd // n_head
        self.sa = MultiHeadAttention(n_head, head_size)
        self.ffwd = FeedForward(n_embd)
        self.ln1 = nn.LayerNorm(n_embd)
        self.ln2 = nn.LayerNorm(n_embd)
    def forward(self, x):
        x = x + self.sa(self.ln1(x))     # 通信
        x = x + self.ffwd(self.ln2(x))   # 计算
        return x

Layer Normalization

第二个是图里的「Norm」，指 Layer Normalization。它和 makemore 第三部分写的 Batch Normalization 非常像：Batch Normalization 让每个神经元在批维度上是单位高斯，也就是归一化每一列。

把均值方差的维度从 0 改成 1，归一化每一行，就是 Layer Normalization：每个样本自己的向量被归一化。因为计算不再跨样本，不需要滑动统计量的缓冲区，训练和测试没有区别，也不需要 momentum，只保留 γ、β。他调侃说「非常复杂」。

这里有一处和原论文不同的地方，也是五年来 Transformer 为数不多的变化之一：原论文在变换之后做 Add & Norm，现在更常见的是在变换之前做 Layer Normalization，叫 pre-norm。

实现时每个块两个 nn.LayerNorm(n_embd)，分别作用在进自注意力和前馈之前的 x 上；归一化在 32 个特征上做，批和时间维都当批维度，相当于逐 token 的变换。

验证损失从 2.08 到 2.06，网络更深更大时帮助会更明显。最后在 Transformer 末尾、解码到词表的线性层之前通常还有一个 Layer Normalization，也加上了。

放大模型和 dropout

加了层数 n_layer 和头数 n_head 两个变量。还加了 dropout：放在残差连接加回通路之前、多头注意力的投影之后，以及注意力权重 softmax 之后（随机阻止一些节点之间的通信）。

dropout 来自 2014 年左右的论文，每次前向反向随机把一部分神经元置零，因为每次的掩码都不同，相当于训练了一组子网络的集成，测试时全部启用、合成一个集成。这里只把它当正则化手段，因为马上要把模型放大，担心过拟合。

新超参数：批量 64；blocksize 256，也就是用 256 个字符的上下文预测第 257 个；模型变大所以学习率调低一点；nembd 384，6 个头，每个头 64 维（标准设置）；6 层；dropout 0.2。

在他的 A100 上训练约 15 分钟，验证损失 1.48，之前是 2.07。他提醒没有 GPU 就别在 CPU 或 MacBook 上跑这个设置，要把层数和维度调小。

生成 1 万个字符写进文件，格式已经很像输入文本：总有人以某种方式说话，只是读起来毫无意义。一个只在 100 万个字符上训练的字符级 Transformer，能做到这样已经不错了。

解码器、编码器和交叉注意力

为什么论文的图和这里写的不一样：这里实现的是只有解码器的 Transformer，没有左边的编码器，块里也没有中间那个交叉注意力。只用解码器，是因为只是在生成文本，不以任何东西为条件。使它成为解码器的，是注意力里的三角掩码，这让它具有自回归性质，可以采样，可以用来做语言建模。

原论文是机器翻译，所以是编码器加解码器：读入比如一句法语，再解码出英语翻译。解码部分和这里做的一样，从一个特殊的开始 token 生成「neural networks are awesome」，再到结束 token；不同在于它以法语句子为条件。

编码器读入法语 token，用没有三角掩码的 Transformer 让所有 token 充分交流，编码出内容；解码器的每个块里多一个交叉注意力，query 来自解码器的 x，key 和 value 来自编码器顶部的输出。这样解码不只看自己已生成的部分，还看完整编码的法语提示。这里没有要编码的东西，只想模仿一个文本文件，所以和 GPT 一样只用解码器。

nanoGPT

nanoGPT 有两个关键文件。train.py 是训练的样板代码，比这里复杂：存取检查点、加载预训练权重、学习率衰减、编译模型、多节点多 GPU 的分布式训练。

model.py 和这里写的几乎一样：CausalSelfAttention 生成 query、key、value，点积、掩码、softmax、可选的 dropout、聚合 value。区别是这里把单个头单独写、再显式拼接，nanoGPT 把所有头放进一个模块批量计算，张量多出一个「头」的维度，变成四维，数学上等价，但更高效。

多层感知机用 GELU 而不是 ReLU，因为 OpenAI 用的是它，这样才能加载他们的检查点。块、GPT 主体（位置编码、token 编码、若干块、末尾的 Layer Normalization、最后的线性层）都一样。

还多了把参数分成要做权重衰减和不做权重衰减的两组，generate 也很相似。（视频描述里的练习一就是把 Head 和 MultiHeadAttention 合成一个类、把头当批维度，答案在 nanoGPT 里。）

回到 ChatGPT

自己训练一个 ChatGPT 大致分两个阶段：预训练和微调。预训练就是在互联网的一大块数据上训练一个只有解码器的 Transformer，让它「胡说八道」，和这里做的一样，只是这里是个婴儿版。这里的模型约 1000 万参数，数据约 100 万字符；OpenAI 用约 5 万个子词 token 的词表，序列更紧凑，莎士比亚大约相当于 30 万个 token。

GPT-3 论文里最大的模型有 1750 亿参数，训练了 3000 亿 token，大约是这里的百万倍，按今天的标准这都不算大，现在会到一万亿以上。架构几乎和这里一样，难在基础设施：成千上万张 GPU 要协同训练。

预训练完得到的是文档补全器，它胡说的不是莎士比亚，是互联网：会生成任意的新闻和文档；你问问题，它可能用更多的问题回答，或者无视问题去补全一篇新闻，行为不可预期，也就是没有对齐。

第二阶段把它对齐成助手，按 OpenAI 的 ChatGPT 博客大约三步：收集「上面是问题、下面是回答」格式的训练数据，大约几千条，远不到互联网的量级，用来微调；这么大的模型在微调时样本效率很高，这居然管用。

然后让模型回答，评分员对多个回答排序，用排序训练一个奖励模型；最后用 PPO（一种策略梯度强化学习优化器）微调采样策略，让生成的回答在奖励模型那里得高分。这些数据大多不公开，这一阶段难复现得多。nanoGPT 关注的是预训练阶段。

总结

照《Attention Is All You Need》训练了一个只有解码器的 Transformer，基本上就是 GPT，在 tiny Shakespeare 上得到了说得过去的结果，训练代码大约 200 行。他会发布这个代码库（ng-video-lecture，附带一路构建过来的 git 提交记录）和 Colab。

GPT-3 这类模型在架构上基本相同，只是大一万到一百万倍。这里没讲上面的那些微调阶段：如果不只想要文档补全器，而是想让它完成任务、按特定方式对齐、做情感检测，就得接着做监督微调，或者像 ChatGPT 那样训练奖励模型再跑 PPO。

这一集记住这几条

  • 语言模型的数据管线：分词成整数，随机取长为 blocksize 的块，一块里藏着 blocksize 个不同长度上下文的样本；批维度上的样本彼此独立。
  • 自注意力的骨架：用下三角掩码加 softmax 得到对过去的加权平均，权重来自 query 和 key 的点积，聚合的是 value；再除以 √headsize 控制初始化时的方差。
  • 注意力是有向图上的通信机制：没有空间概念所以要加位置编码；去掉三角掩码就是编码器块；key、value 来自别处就是交叉注意力。
  • Transformer 块 = 多头自注意力（通信）+ 前馈网络（逐 token 计算），各自通过残差连接加回通路，前面各有一个 Layer Normalization（pre-norm）。
  • 残差连接给梯度一条加法组成的高速公路；Layer Normalization 是按行归一化的 Batch Normalization，不跨样本，训练测试一致。
  • 放大到 6 层、384 维、上下文 256、dropout 0.2，验证损失从 2.5 降到 1.48；GPT-3 架构几乎一样，只是大百万倍，要成为 ChatGPT 还要监督微调和 RLHF。

  • EX2：用你自己选的数据集训练这个 GPT。进阶：让它学两数相加 a+b=c，把 c 的数字倒过来预测会更容易，因为竖式加法也是从右往左算；数据加载器可以直接随机出题，输入 a+b 那部分的损失用 ignore_index 屏蔽掉。学会以后再试试做一个支持加减乘除的计算器，这不容易，可能需要思维链。

训练配方的全貌

他强调这一切都很新、还在快速变化，但目前的配方大致是四个依次进行的阶段：预训练、监督微调、奖励建模、强化学习。每个阶段有一个数据集、一个训练目标（算法），得到一个模型。这张图不按比例：预训练占了 99% 的训练算力和时间，用互联网规模的数据、超级计算机里的数千张 GPU、可能训练数月；后面三个都是微调阶段，只需要少量 GPU，训练几小时到几天。

预训练：数据和分词

先收集大量数据。他以 Meta 发布 LLaMA 基础模型的论文为例：数据混合里有 Common Crawl（网页抓取）、C4（也来自 Common Crawl），以及 GitHub、维基百科、书籍、arXiv、Stack Exchange 等高质量数据集，按一定比例采样，组成训练集。

训练前还要分词：把原始文本无损地转换成整数序列，这是 GPT 处理的原生表示。常用算法比如字节对编码（byte-pair encoding），反复合并小的文本片段，组成 token。

规模

GPT-4 的训练细节没有公开，所以用 GPT-3 和 LLaMA 的数字说明量级。词表通常几万个 token；上下文长度通常是 2000、4000，现在甚至 10 万，决定了 GPT 预测下一个整数时最多看多少个整数。

LLaMA 有 650 亿参数，GPT-3 有 1750 亿，但 LLaMA 强得多，因为训练得久得多：1.4 万亿个 token，GPT-3 只有 3000 亿。所以不能只看参数量判断模型强弱。训练 65B 的 LLaMA，Meta 用了约 2000 张 GPU、约 21 天、数百万美元。

预训练在做什么

把 token 排成 B×T 的批次，T 是上下文长度（2000、4000……），文档首尾相接排进一行，用特殊的文本结束 token 隔开。对每个位置，Transformer 看到它之前的所有 token，预测下一个 token。

词表大小是 50257 时，每个位置输出 50257 个数，构成下一个 token 的概率分布；真实的下一个 token 就是监督信号。所有位置并行计算，不断换批次训练。

他展示了《纽约时报》在莎士比亚文本上训练小 GPT 的例子：刚初始化时输出完全随机，训练越久越连贯，最后学会了单词、空格和逗号放在哪。预训练时主要看的就是损失随时间下降的曲线。

从微调到提示

大家发现，语言建模的过程中模型学到了非常强的通用表示，可以高效地微调到任意下游任务。以前做情感分类要收集正负样本训练专门的 NLP 模型；新做法是先做大规模语言模型预训练，再用少量样本微调。原因是为了预测下一个 token，Transformer 被迫理解文本的结构和其中的各种概念，相当于同时做了大量任务。这是 GPT-1 的时代。

到 GPT-2 时，人们发现比微调更好的是直接给模型提示。语言模型想补全文档，所以可以伪造一份文档骗它完成任务：放一段文章，接几组问答，最后只写问题，它为了补全文档就会回答。这就是 few-shot 提示，开启了「提示胜过微调」的时期。

基础模型不是助手

此后出现了一整棵基础模型的进化树。不是所有都公开：GPT-4 的基础模型从未发布，API 里的 GPT-4 是助手模型；GPT-3 的基础模型可以通过 API 用，名字叫 davinci；GPT-2 的权重在 GitHub 上。他说当时最好的可用基础模型大概是 Meta 的 LLaMA 系列，但不能商用。

基础模型不是助手，不会回答问题，只会补全文档。让它「写一首关于面包和奶酪的诗」，它可能用更多问题来回应。换个写法，比如「下面是一首关于面包和奶酪的诗：」，它就能正确补全。也可以构造一份人类和助手对话的 few-shot 文档，把问题放在最后，诱导基础模型扮演助手，但不太可靠。

监督微调

要得到真正的助手，走的是另一条路。监督微调收集少量但高质量的数据：请人工标注员写「提示和理想回答」，通常几万条。算法完全不变，仍然是语言建模，只是把训练集从数量大、质量低的互联网文档换成了数量少、质量高的问答数据。训练后得到 SFT 模型，可以部署，确实是助手，效果尚可。

他展示了一条示例：提示是「简短介绍一下 monopsony（买方垄断）这个术语」，标注员写出理想回答。标注员要遵循很长的标注文档，要求回答有帮助、真实、无害。

奖励建模

可以接着做 RLHF，它包括奖励建模和强化学习两步。奖励建模的数据是比较：同一个提示（比如「写一个判断字符串是否回文的函数」），用 SFT 模型生成多个回答，请人排序。比较这些回答很难，一组可能要花好几个小时。

训练时把提示和每个回答排成一行，在末尾加一个特殊的奖励读出 token，只在这个 token 上监督 Transformer，让它输出一个分数，表示这个回答对这个提示有多好。有了人给的排序，就能要求某些分数比另一些高，写成损失函数，让奖励模型的打分和人的比较一致。奖励模型本身不能当助手用，但对接下来的强化学习很有用：它可以给任意提示的任意回答打分。

强化学习

再收集一大批提示，对着奖励模型做强化学习。把一个提示排成几行，用要训练的模型（从 SFT 模型初始化）生成回答，末尾加奖励 token，用固定不变的奖励模型读出分数。

然后仍用语言建模的损失，只训练模型生成的那些 token，按奖励加权：第一行奖励高，这一行采样出的所有 token 以后会得到更高的概率；第二行奖励是 −1.2，这一行的 token 以后概率会降低（演讲中他口误说成了「略高」）。反复在大量提示上这样做，得到的策略生成的回答在奖励模型那里都能得高分。

ChatGPT 是 RLHF 模型；Vicuna-13B 等则是 SFT 模型。所以现在有三类：基础模型、SFT 模型、RLHF 模型。

为什么要做 RLHF

一个不那么激动人心的答案：效果更好。InstructGPT 论文的实验里，人们更喜欢 PPO（也就是 RLHF）模型的输出，其次是 SFT 模型，再次是被提示成助手的基础模型。

至于为什么更好，社区没有公认的答案。他给了一个可能的原因：比较比生成容易。让标注员给「关于回形针的俳句」写一个好答案很难，但给几首俳句让他挑哪首好，容易得多。比较能更好地利用人的判断力。

RLHF 模型也不是全面更好，它们会失去一些熵，输出更集中、多样性更低。基础模型熵高，输出多样。所以给出 n 个东西、想生成更多类似东西的任务，他还是喜欢用基础模型：比如给 7 个宝可梦名字，让基础模型补全，得到一串很酷的新名字（他查过，都不是真的宝可梦）。

伯克利的一个团队给当时可用的助手模型做了 Elo 排名：GPT-4 遥遥领先，其次是 Claude、GPT-3.5，然后是 Vicuna、Koala 等可下载权重的模型。前三名都是 RLHF 模型，其余据他所知都是 SFT 模型。

一句话背后的思考

第二部分讲怎么用。假设你在写博客，最后写下一句「加利福尼亚的人口是阿拉斯加的 53 倍」。

这一句话背后有很多事：意识到自己不知道两州的人口，去维基百科查（3920 万和 74 万）；知道 39.2 除以 0.74 心算不靠谱，用计算器算出约 53；检查一下合不合理，加州人口最多，说得过去；写的时候觉得「53 倍大」措辞别扭，删掉重写。写作时有一个单独的过程在检查写出来的东西。

但在 GPT 看来，这只是一串 token，它一块一块地读或生成，每个 token 的计算量大致相同。Transformer 大约 80 层，不算很深，只能尽力模仿。训练数据里，人的内心独白全被去掉了。

它是「token 模拟器」：不知道自己不知道什么，不知道自己擅长什么，不会在循环中反思、检查、纠错，没有独立的内心独白。它也有认知优势：几百亿参数存了大量事实；上下文窗口相当于一个容量有限但完美的工作记忆，自注意力能直接、无损地访问里面的一切。提示工程很大程度上就是在弥补人脑和这种「大模型大脑」之间的认知差异。

给它更多 token 去思考

需要推理的任务，不能指望每个 token 里完成太多推理，要把推理分散到更多 token 上。复杂问题不能指望它在一个 token 里答对，「Transformer 需要 token 来思考」。

办法有：给几个展示解题过程的 few-shot 例子，它会模仿这个模板；或者加一句「let's think step by step」，让它进入展示过程的模式，每个 token 的计算负担变小，更容易成功。

自洽性（self-consistency）：人写不顺可以重来，多试几次挑最好的。模型预测时也可能运气不好，采到一个不太好的 token，走进推理的死胡同，而且它不会回头，只能硬着头皮写下去。所以可以多采样几次，用某种方式挑出好的，或者多数投票。

模型其实知道自己搞砸了。让它写一首不押韵的诗，它可能写出了押韵的；但问 GPT-4「你完成要求了吗」，它很清楚没有，只是采样时运气不好，会说「没有，我再试一次」。可你不问，它不会自己回头检查，要在提示里替它做这件事。

重建「系统 2」

更一般地，这些技巧都是在重建人的系统 2。系统 1 是快速自动的过程，对应模型逐个采样 token；系统 2 是慢速、审慎、会规划的部分。

他提到 2023-05-17 刚发表的 Tree of Thoughts 论文：对一个提示维护多个补全，边走边打分，保留进展好的。这不只是一个提示，而是提示加上 Python 胶水代码，要维护多个提示、做树搜索决定扩展哪个。

他觉得这很像 AlphaGo：AlphaGo 的落子策略最初是模仿人训练出来的，此外还做蒙特卡洛树搜索，在脑中推演多种可能，只保留好的。Tree of Thoughts 有点像文本版的 AlphaGo。

还有 ReAct：把回答组织成「思考、行动、观察」的循环，行动可以调用工具。AutoGPT 当时很火，让模型维护任务列表、递归地拆解任务，他认为目前效果不好，不建议用在实际应用里，但值得从中找灵感，看清未来的方向。

模型不想成功，只想模仿

大模型有个近乎心理上的怪癖：它们不想成功，只想模仿。训练数据里同一道物理题，可能有完全错误的学生答案，也有完全正确的专家答案，模型知道两者都存在，但语言建模让它把这些都模仿下来。所以测试时你得主动要求好的表现。

有篇论文试了各种提示：「let's think step by step」很有效，但「let's work this out in a step by step way to be sure we have the right answer」更好，因为它是在以「得到正确答案」为条件，模型就不必把概率分给低质量的解法。

所以尽管要求一个强的答案，比如说「你是这个领域的顶尖专家」「假装你的 IQ 是 120」。但别要求太高的 IQ，说 400 可能超出数据分布，甚至落进科幻小说的分布里开始角色扮演。他猜这里有一条 U 形曲线。

工具和检索

人解决问题时知道自己擅长什么、不擅长什么，会借助工具。模型也可以用计算器、代码解释器、搜索。但它默认不知道自己不知道什么，所以要在提示里明说：「你不擅长心算，遇到大数加法乘法就用计算器，用法是……」。

从只靠检索的世界，钟摆摆到了只靠记忆的大模型，其实中间有一大片检索增强的空间，实践中效果非常好。上下文窗口是模型的工作记忆，把和任务相关的信息放进去，模型能立刻用上。

LlamaIndex 这类工具把各种数据接进来、建好索引。流程是：把相关文档切成块、算出嵌入向量、存进向量库；测试时用查询去向量库里取出可能相关的块，放进提示，再生成。就像人做题时会翻教材、查文档，虽然有记忆，查一下总是更好。

约束采样

还有一类技术是强制输出遵循某种模板。微软的 Guidance 就是一个例子：强制输出 JSON。它直接干预 Transformer 输出的各个 token 的概率，把模板部分钳死，模型只填空，还可以对填空的内容加额外限制。他觉得这种约束采样很有意思。

微调

提示工程能走很远，但也可以考虑微调，也就是真正改模型的权重。现在微调容易多了：LoRA 这类参数高效微调只训练模型的一小部分，其余部分固定在基础模型上，效果不错，成本低得多；固定的部分不需要梯度更新，还能用很低的精度做推理。另外也有了高质量的开源基础模型，比如 LLaMA（他说当时还不能商用）。

但微调的技术门槛高得多：需要人工标注员或复杂的合成数据流程，会大大拖慢迭代。SFT 还算可行，因为只是继续做语言建模；RLHF 则非常偏研究，很不稳定、难训练，对新手不友好，而且可能还会快速变化，他不建议自己从头实现。

默认建议

把任务分两步：先做到最好的效果，再优化成本，顺序不要反。第一步，用当时最强的 GPT-4；提示要非常详细，包含任务背景、相关信息和指令，想象成你在给一个没法回邮件问你的外包人员写说明，但要记得外包人员是人，有内心独白、很聪明，大模型没有，所以要考虑大模型的「心理」去写提示。

把相关上下文检索进来；多试 few-shot 示例，能展示就别只是描述；用工具和插件分担模型不擅长的事；不只是一问一答，考虑链式调用、反思、多次采样。

如果确信提示工程已经做到头了（他认为应该坚持一阵），再考虑微调，但要预期慢得多、复杂得多；再往后是专家才能玩的、脆弱的研究区域 RLHF，能跑通的话效果比 SFT 好一点。第二步优化成本：试更小的模型、更短的提示。

适用场景

大模型有很多局限，这本身能讲一整场：可能有偏见、编造信息（幻觉）、推理出错、在某些类别的应用上表现很差；有知识截止日期，比如不知道 2021 年 9 月以后的事；容易受各种攻击，比如提示注入、越狱、数据投毒，推特上每天都有新的。

所以他建议目前用在低风险的场景，始终配合人工监督，把它当成灵感和建议的来源，当作副驾驶，而不是完全自主地完成任务的智能体，模型现在还不到那一步。

最后他说 GPT-4 是个了不起的成果，知识横跨很多领域，能做数学、写代码，周围还有一个蓬勃的生态，这一切几行代码就能调用。他让 GPT-4「给 Microsoft Build 2023 的观众说几句鼓舞人心的话」，当场念了它的回答，还说没想到主题演讲已经用过这一招了，他还以为自己很聪明。

这一集记住这几条

  • GPT 助手的训练分四步：预训练（99% 的算力）、监督微调、奖励建模、强化学习，后两步合称 RLHF。
  • 模型强弱不只看参数量：LLaMA 65B 训练了 1.4 万亿 token，比 1750 亿参数、3000 亿 token 的 GPT-3 强。

  • 给模型工具（计算器、代码解释器、搜索）并告诉它什么时候用；检索增强把相关文档放进上下文这块「工作记忆」。

分词是什么

上一集的分词很朴素：莎士比亚文本里出现了 65 个字符，建一张查找表把每个字符映射成一个整数，1000 个字符就是 1000 个 token。

token 再通过嵌入表查出一个可训练的向量送进 Transformer，Transformer 就是这样「感知」每个 token 的。实际的大模型用复杂得多的方案，不是在字符级别，而是在字符块级别，块由字节对编码这类算法构造。

把字节级 BPE 引入大模型分词的大概是 GPT-2 论文，它在「Input Representation」一节讨论了分词想要的性质，最后用了 50257 个 token 的词表、1024 个 token 的上下文（GPT-1 是 512）。

token 是大模型的原子，一切都以 token 为单位，LLaMA 2 论文里搜「token」有 63 处，比如训练了 2 万亿个 token。

他列出了一串由分词引起的问题：不会拼写、简单的字符串处理困难、非英语差、简单算术差、GPT-2 写 Python 特别吃亏、提示末尾有空格时的奇怪警告、问到「SolidGoldMagikarp」时模型发疯、结构化数据建议用 YAML 而不是 JSON。结尾会逐个回来解释。

在 tiktokenizer 上看分词

tiktokenizer 这个网页在浏览器里实时分词，选 GPT-2 的分词器，一段文本被切成 300 个 token，每个 token 着不同的颜色。「tokenization」是两个 token；空格是 token 的一部分，比如「 at」「 the」各是一个 token。

数字的切分很随意：127 是一个 token，677 却是「 6」和「77」两个，四位数有时一个、有时两个、有时更多。「Egg」在句首是两个 token，「 Egg」（前面有空格）是一个，「egg」小写又是另一个，大小写敏感。同一个概念因为位置和大小写不同变成完全不同的 token，模型得从互联网数据里自己学会它们其实是一回事。

非英语更费 token：ChatGPT 的一段韩语自我介绍被切得很碎。不只是模型的训练数据英语多，分词器的训练数据也是英语多，英语有更多更长的 token，同一句话翻成韩语或日语，token 数会多得多，文档被拉长，很快就用完了上下文窗口。

一段 FizzBuzz 的 Python 代码里，缩进的每个空格都是单独的 token 220，非常浪费，这是 GPT-2 不擅长 Python 的一个重要原因，和编程能力本身无关。

换成 GPT-4 的分词器 cl100kbase，同一段文本从 300 个 token 降到 185 个，因为词表从约 5 万扩到约 10 万；而且 GPT-4 刻意把多个空格合成一个 token，Python 变得更紧凑，能看到的代码更多。

GPT-2 到 GPT-4 编程能力的提升，有相当一部分来自分词器的设计。当然词表不是越大越好，嵌入表和输出层的 softmax 都会变大，有个合适的中间点。

Unicode 和 UTF-8

要支持各种语言和表情符号。Python 的字符串是Unicode 码位的不可变序列。Unicode 由 Unicode 联盟定义，目前约 15 万个字符、覆盖 161 种文字，最新的 15.1 版是 2023-09 发布的。

ord("h") 是 104，表情符号是 128000 多。为什么不直接用码位当 token：词表约 15 万太大，而且标准一直在变，不是稳定的表示。

Unicode 定义了三种编码，把文本转成字节流：UTF-8、UTF-16、UTF-32。UTF-8 最常用，每个码位编码成 1 到 4 个字节，变长；它是唯一兼容 ASCII 的，他推荐《UTF-8 Everywhere》宣言。看字节就知道 UTF-16、UTF-32 对英文有多浪费：一堆 0。所以用 UTF-8。

但直接用 UTF-8 的字节当 token，词表只有 256，所有文本都会被拉成很长的字节序列，而注意力的上下文长度有限，这很低效。想要的是词表大小可以当超参数调、又基于 UTF-8 字节，答案就是字节对编码，把字节序列压缩到可变的程度。

他很希望能直接把原始字节送进语言模型。2023-05-12 的论文 MEGABYTE 提出了层级结构的 Transformer，直接处理原始字节，结论说这证明了「无分词」的大规模自回归序列建模可行。但他认为还没被足够多的团队在足够大的规模上验证，有人做成的话会非常棒。

字节对编码

维基百科上的例子：词表只有 a、b、c、d 四个，序列「aaabdaaabac」有 11 个元素。找出出现次数最多的相邻对 aa，造一个新 token Z 替换所有 aa，序列变成 9 个元素、词表变成 5 个；再把最常见的 ab 换成 Y；再把 ZY 换成 X。

最后序列只有 5 个元素，词表 7 个。对字节做同样的事：从 256 个字节开始，反复找最常见的字节对、造新 token、替换，就得到压缩后的训练数据，以及对任意序列编码、解码的算法。

实现：取一篇他喜欢的讲 Unicode 的博客的第一段，text.encode("utf-8") 后转成整数列表，533 个码位变成 616 个字节（复杂字符占多个字节）。get_stats(ids) 用字典统计所有相邻对的次数，最常见的是 (101, 32) 出现 20 次，chr 一下是「e 」和空格，很多词以 e 结尾。

merge(ids, pair, idx) 从左到右扫，遇到这一对就换成新 id、跳两格，否则原样复制；要注意别在最后一个位置越界。把 (101, 32) 换成 256 后，长度从 616 变成 596，正好少了 20。

def get_stats(ids):
    counts = {}
    for pair in zip(ids, ids[1:]):
        counts[pair] = counts.get(pair, 0) + 1
    return counts

def merge(ids, pair, idx):
    newids, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i+1] == pair[1]:
            newids.append(idx); i += 2
        else:
            newids.append(ids[i]); i += 1
    return newids

训练分词器

合并多少次是超参数：步数越多，词表越大、序列越短，中间有个经验上最好的点，GPT-4 用约 10 万个 token。为了统计更有代表性，改用整篇博客。

目标词表大小设 276，也就是在 256 个字节之上做 20 次合并。merges 字典记录「两个子 token 合成哪个新 token」，从底层的 256 个字节两两往上合，形成的不是一棵树，而是一片二叉「森林」。

第一次合并仍是 (101, 32) 变成 256。原来的 101 和 32 仍可以单独出现，只有紧挨着时才合并；新 token 也可以参与后续合并，比如第 20 次合并是 256 和 259 合成 275。约 2.4 万个字节合并 20 次后剩约 1.9 万个 token，压缩率约 1.27，词表越大压缩率越高。

vocab_size = 276
num_merges = vocab_size - 256
ids = list(tokens)
merges = {}  # (int, int) -> int
for i in range(num_merges):
    stats = get_stats(ids)
    pair = max(stats, key=stats.get)
    idx = 256 + i
    ids = merge(ids, pair, idx)
    merges[pair] = idx

分词器是一个独立的阶段

这一集完全没碰大模型本身。分词器有自己的训练集，用 BPE 训练出词表和合并规则，通常在开头跑一次预处理；训练好之后就是原始文本（Unicode 码位序列）和 token 序列之间的翻译层。大模型是第二步：常见做法是把它所有的训练数据先过一遍分词器，转成一个巨大的 token 序列存到磁盘上，扔掉原始文本，大模型训练时读的就是这些 token。

两者的训练集可以不同。训练分词器时不只关心英语，还关心各种语言和代码，混合比例很重要：某种语言在分词器训练集里越多，它的合并就越多、序列就越短，对上下文有限的大模型越有利。比如加入大量日语，日语就会被切得更紧凑。

解码

先建 vocab：token id 到字节串的映射，0 到 255 是单个字节，然后按合并的顺序，每个新 token 的字节串等于两个子 token 的字节串拼接。要按插入顺序遍历 merges，Python 3.7 起字典保证这一点。decode 把每个 id 查成字节串、拼起来，再用 UTF-8 解码成字符串。

这有个隐患：解码单个 token 128 会报错「invalid start byte」。UTF-8 的多字节编码有固定格式，128 的二进制是 1 后面全是 0，不符合任何一种起始字节的格式。不是任意字节序列都是合法的 UTF-8，模型输出的 token 序列可能解不出来。

标准做法是 decode("utf-8", errors="replace")，非法部分换成替换字符 �，OpenAI 发布的代码也是这样。输出里看到这个字符，就说明模型输出的 token 序列不合法。

vocab = {idx: bytes([idx]) for idx in range(256)}
for (p0, p1), idx in merges.items():
    vocab[idx] = vocab[p0] + vocab[p1]

def decode(ids):
    tokens = b"".join(vocab[idx] for idx in ids)
    return tokens.decode("utf-8", errors="replace")

编码

先把文本编码成 UTF-8 字节，转成整数列表。然后按 merges 合并，而且要按训练时的顺序：后面的合并可能依赖前面合并出来的 token（比如用到 256 的那些）。

做法是循环：用 get_stats 只取出当前序列里所有的相邻对（不关心次数），从中找出在 merges 里序号最小的那一对，min(stats, key=lambda p: merges.get(p, float("inf")))，不在 merges 里的对返回无穷大，不会被选中。

如果所有对都不在 merges 里，min 会随便返回一个对，这时它不在 merges 里，说明没东西可合并了，跳出循环。否则按它的序号合并，继续。另外序列只有 0 或 1 个 token 时 stats 为空会出错，要先判断长度至少为 2。

测试：编码后再解码，应该得到原字符串，训练文本和一段分词器没见过的验证文本都通过了。反过来不成立，因为不是所有 token 序列都是合法的 UTF-8。这就是 BPE 最基本的形式：分词器的参数其实就是 merges 这个字典，它在原始字节之上建起一片二叉森林。

def encode(text):
    tokens = list(text.encode("utf-8"))
    while len(tokens) >= 2:
        stats = get_stats(tokens)
        pair = min(stats, key=lambda p: merges.get(p, float("inf")))
        if pair not in merges:
            break  # 没有可以合并的了
        tokens = merge(tokens, pair, merges[pair])
    return tokens

GPT-2 的正则切分

GPT-2 论文说，不能直接套朴素的 BPE。比如「dog」常和各种标点挨着出现，dog.、dog!、dog?，朴素 BPE 会把它们合成不同的 token，等于把语义和标点混在一起。所以他们自上而下地强制规定某些类别的字符永远不合并。

看 OpenAI GitHub 上 GPT-2 的 encoder.py（他不喜欢这个名字，它其实是分词器）。核心是一个正则表达式（用的是 regex 包，比标准库 re 更强），对文本 findall，先把文本切成一块块，每块独立做 BPE，结果再拼起来。于是合并只会发生在块内部，比如「e」和后面的空格分在两块，就永远不会合成「e 」。

逐段看这个模式：先匹配常见的英文缩写 's、't、're、've、'm、'll、'd；然后是可选空格加一个或多个字母 \p{L}（任何语言的字母）；可选空格加数字 \p{N}；可选空格加既不是字母数字也不是空白的字符，大致就是标点；最后是空白。

效果是字母、数字、标点被分开。毛病也不少：缩写只认 ASCII 的撇号，换成 Unicode 撇号就不行了；没加忽略大小写，大写的 'S 不会被单独切出来，GPT-2 代码注释里也承认「应该加 re.IGNORECASE」；这些缩写规则很依赖语言。

空白那一段用了负向前瞻：连续空格只匹配到倒数第二个，最后一个空格留给后面的单词，这样多个空格后的「 you」仍是常见的「空格+单词」token。GPT-2 分词器一贯把空格放在单词前面。

不过 OpenAI 实际训练时还不只是「切块再做 BPE」：tiktokenizer 里能看到代码缩进的空格全是单独的 220，说明另有不合并空格的规则。GPT-2 分词器的训练代码从未发布，encoder.py 只是推理代码。

tiktoken 和 GPT-4 的改动

tiktoken 是 OpenAI 官方的分词库，也只有推理没有训练。GPT-2 编码时多个空格保持不合并，GPT-4 会合并。tiktoken/tiktoken_ext/openai_public.py 里定义了各个分词器，为了做推理不得不公开切分用的正则：GPT-2 的写法略有不同但等价；GPT-4 的 cl100kbase 改了模式。

主要改动：加了 (?i)，缩写不分大小写了；空白的处理有很多变化；数字只匹配 1 到 3 位，超过三位的数字永远不会被合成一个 token，避免很长的数字 token。为什么这样改没有文档说明，只能看模式本身。词表从约 5 万变成约 10 万。

OpenAI 的 encoder.py

它在最后加载两个文件 encoder.json 和 vocab.bpe，合起来就是保存下来的分词器：encoder 等价于这里的 vocab（方向相反，是字符串到整数），而名字让人困惑的 vocab.bpe 其实等价于这里的 merges。有这两个变量就能编码和解码。

唯一让人困惑的是还多了一层 byte_encoder / byte_decoder，编码前先过一遍、解码后再过一遍，他认为只是无关紧要的实现细节，跳过了。其余部分，核心的 bpe 函数里的循环找下一个要合并的 bigram、再 for 循环合并，直到没得合并，和这里写的在算法上完全一样。

特殊 token

GPT-2 的 encoder 有 50257 项：256 个原始字节，加 5 万次合并，是 50256，第 50257 个是唯一的特殊 token <|endoftext|>。训练数据里文档之间插入这个 token，告诉模型前一个文档结束了，后面的内容和前面无关；但模型得从数据里自己学会看到它时「清空记忆」。

在 tiktokenizer 里打出「<|endoftext|>」，没打完时是一堆普通 token，打完就变成 50256。这不是 BPE 合并出来的，而是 tiktoken（Rust 实现）里有专门处理特殊 token 的代码，看到就直接换上。encoder.py 里没有这部分。

特殊 token 在微调阶段用得更多，不只要分隔文档，还要分隔用户和助手的整段对话。tiktokenizer 里 GPT-3.5-turbo 的例子用了 <|im_start|>、<|im_end|> 这类 token，标出每条消息的开始和结束。

tiktoken 允许在 cl100kbase 的基础上扩展任意特殊 token。GPT-4 除了 endoftext，还有 FIM 的前缀、中间、后缀三个 token（fill in the middle，来自一篇论文）和一个 endofprompt。

加特殊 token 要对 Transformer 做一点模型手术：嵌入表加一行（通常用小随机数初始化），最后输出到词表的投影层也要加一列。从基础模型微调成 ChatGPT 这样的对话模型时这很常见。

minbpe 练习

他把这一集的代码整理成了 minbpe 仓库，并在 exercise.md 里把任务分成四步，最终写出 GPT-4 的分词器；卡住了就看仓库里的代码或测试。写完应该能复现 tiktoken：用 GPT-4 分词器编码一段字符串得到同样的 token，编码再解码能还原；还能写出 tiktoken 没有的训练函数，训练自己的词表。

minbpe 能把合并顺序可视化：GPT-4 的第一次合并是把两个空格合成一个 token（256）；他在泰勒·斯威夫特的维基百科页面上训练（因为它是最长的维基页面之一，「不是因为我是 Swifty」），得到的合并顺序大体相似，比如「in」都很早合并，差别主要来自训练集。GPT-4 早期合并了大量空白，他猜它的分词器训练集里有很多 Python 代码。

SentencePiece

SentencePiece 很常用，因为它既能训练又能推理，而且都很高效，LLaMA、Mistral 系列等都用它。它支持多种训练算法，BPE 是其中之一。

和 tiktoken 的关键区别在运算顺序：tiktoken 先把码位 UTF-8 编码成字节，再合并字节；SentencePiece 直接在码位上做 BPE。

罕见的码位（由 charactercoverage 决定）要么映射成特殊的未知 token <unk>，要么在打开 bytefallback 时用 UTF-8 编成字节，再用专门的字节 token 表示。他觉得 tiktoken 的做法干净得多。

它有大量配置项，历史包袱很重，比如 shrinkingfactor 根本不用于 BPE。他打开 Meta 发布的 LLaMA 2 的 tokenizer.model（protobuf），把看起来相关的选项照抄过来，在一个小文本上训练了一个 400 词的分词器。

他尽量关掉各种规范化（转小写、去重复空白之类），那是机器翻译和文本分类时代的习惯，做深度学习的人更想保留原始数据。SentencePiece 还有「句子」的概念（句子数、最大句长、打乱句子），他认为对大模型来说这个区分很多余，什么算一个句子本来就很难定义，不如把文件当成一整个字节流。

词表的排列顺序是：特殊 token（<unk> 是 0，句首 1，句尾 2，pad 关掉了）、256 个字节 token、合并出来的 token、单个码位的 token。

编码「hello 안녕하세요」：韩文码位没在训练集里出现，因为开着 bytefallback，被编成 UTF-8 字节 token（id 偏移 3）。关掉 bytefallback，这些字节 token 消失、合并 token 变多，但整段韩文都变成 0（<unk>），对模型很不友好，所以 LLaMA 开着它是对的。

解码出的 token 里，空格显示成加粗的下划线「▁」，hello 前面还多了个空格，这来自 adddummyprefix：在文本开头加一个空格，让句首的 world 和句中的 world 都是「▁world」，减轻同词不同 token 的问题，LLaMA 2 也开着。

他的总结：SentencePiece 历史包袱多、有一些坑（比如句子长度上限）、unk 必须存在、bytefallback 不够优雅、文档不太好，但它高效、业界常用。

词表大小怎么定

回到上一集写的 GPT 代码，vocab_size 只出现在两处：token 嵌入表的行数，和最后输出 logits 的 lm_head 线性层。

词表为什么不能无限大：一是嵌入表和输出层都变大，计算更贵；二是参数多了，每个 token 在训练数据里出现得更少，对应的向量可能训练不足；三是序列变短固然能看更多文本，但一个 token 里装了太多信息，Transformer 一次前向可能处理不过来。这主要是个经验超参数，目前的先进模型一般在几万到 10 万左右。

给预训练好的模型扩展词表很常见，比如微调成 ChatGPT 时要加很多维护对话结构的特殊 token，或者调用浏览器等工具的 token。做法就是给嵌入表加行、给线性层加权重，新参数用小随机数初始化，算是轻度的模型手术；常见做法是冻结基础模型，只训练新加的参数。

加新 token 的用途远不止特殊 token。比如 gist token 的论文：长提示让一切变慢，于是加几个新 token，冻结整个模型、只训练这几个 token 的嵌入，用蒸馏让模型带着它们的行为和带着长提示时一样，测试时用这几个 token 代替长提示。这是参数高效微调的一种，训练的只是 token 嵌入。

多模态的分词

录制时很多人在做同时处理文本、图像、视频、音频的 Transformer。逐渐形成的共识是不改架构，而是把各种模态也「分词」，当作文本 token 一样处理。早期有论文把图像切块转成整数 token（向量量化）；token 可以是硬的离散整数，也可以是软的连续表示，但要像自编码器那样经过瓶颈。

OpenAI 的 Sora 也说，大模型有文本 token，Sora 有视觉 patch，可以用自回归模型处理离散 token，也可以用扩散模型处理软 token。

回头解释那些怪现象

拼写：字符被合成了 token，有些 token 很长，比如 GPT-4 词表里「.DefaultCellStyle」是一个 token。问 GPT-4 里面有几个 l，它说 3 个，实际是 4 个；让它直接反转这个字符串，结果是乱的；但让它先把每个字符用空格隔开列出来，再反转，就对了，因为拆开后每个字符是单独的 token。

非英语：除了训练数据少，分词器在非英语上训练得也不够。「hello, how are you」是 5 个 token，韩语翻译是 15 个，膨胀了 3 倍；连「안녕하세요」这么常见的问候都是 3 个 token，而 hello 只有 1 个。

算术：加法是按位进行的算法，先个位、再十位、再百位，要能引用具体的数位，而数字被切成什么完全取决于训练时碰巧合并了什么。有篇博客《Integer tokenization is insane》系统地考察了 GPT-2 对四位数的切分：有的是一个 token，有的是 1+3、2+2、3+1，非常随意。

所以 Meta 训练 LLaMA 2 时用 SentencePiece 把所有数字拆成单个数位。GPT-2 写 Python：每个空格一个 token，大大压缩了能看到的上下文，几乎算是 GPT-2 分词器的一个 bug，GPT-4 修好了。

看到 <|endoftext|> 就停：他让 GPT-4 打印字符串「<|endoftext|>」，它总是好像没看到。他猜 OpenAI 在编码用户输入时可能允许了这个特殊 token，被当成真的特殊 token 解析了。用户输入是攻击者可控的文本，不应该解析出特殊 token，对特殊 token 的了解于是成了一个潜在的攻击面。

末尾空格：在 OpenAI Playground 里用 gpt-3.5-turbo-instruct（补全模型，更接近基础模型）补全「Here is a tag line for an ice cream shop」，末尾多加一个空格就会警告「文本以空格结尾，由于 API 的分词方式会导致效果变差」。

因为 GPT 的 token 总是把空格放在开头，正常应该接着采样「 Oh」这样带空格的 token（8840）；现在空格被单独编码成 220，等于把下一个 token 的一部分先写了出来，模型很少见过这种数据，超出了分布。

同理，「.DefaultCellStyle」在训练数据里总是一个整体，只给前半截让它补全，模型立刻输出了停止序列，或者被标记为违反使用政策，明显很「难受」。tiktoken 的 Rust 代码里有大量处理「unstable tokens」的代码，正是在处理这种不完整 token 的问题，但没有任何文档。

SolidGoldMagikarp

他最喜欢的一个。一篇博客把 token 嵌入做聚类，发现一簇很奇怪的 token：「 petertodd」「 StreamerBot」「 SolidGoldMagikarp」等。问模型这些 token，比如「请重复字符串 SolidGoldMagikarp」，会得到各种崩坏的行为：回避（「抱歉我听不清」）、幻觉、甚至骂人，违反了对齐和安全准则。

原因还是分词。SolidGoldMagikarp 是一个 Reddit 用户名。

一般认为（并未被完全证实）分词器的训练集和语言模型的训练集很不一样：分词器的训练集里有大量 Reddit 数据，这个用户发帖很多，名字反复出现，于是被合并成一个专属 token；但语言模型的训练数据里没有这部分 Reddit 数据，这个 token 从未出现，它在嵌入表里的那一行从初始化起就从未被更新过，完全没训练。

这就像 C 程序里未分配的内存，测试时一旦调用它，就把一行未训练的向量送进 Transformer，产生未定义行为。

格式效率和最后的建议

不同格式、不同语言在分词器下的效率不同。同样的数据，JSON 是 116 个 token，YAML 是 99 个。在按 token 计费、上下文按 token 计的经济里，结构化数据优先用 YAML。要时刻关心分词密度，多在 tiktokenizer 里测各种格式和设置。

他知道这一集很枯燥、很烦人，他自己也很不喜欢这个阶段，但别轻视它：有很多坑、安全问题和 AI 安全问题，比如把「未分配的内存」送进模型。谁要是能彻底去掉这一步，将获得「永恒的荣耀」。

建议：如果能复用 GPT-4 的 token 和词表，就用 tiktoken，它推理高效；他喜欢 tiktoken 和 OpenAI 用的字节级 BPE。

如果要从头训练自己的词表，就用 SentencePiece 的 BPE，但要非常小心它的众多设置，最好照抄 Meta 的；即使设置都对，他仍认为它的算法（在码位上做 BPE、bytefallback）不如字节级 BPE。最理想的是有训练代码的 tiktoken，现在还不存在，minbpe 是一个实现，但还是 Python 写的。

这一集记住这几条

  • 分词是独立于大模型的阶段：有自己的训练集，用 BPE 训练出合并规则，提供 encode、decode；它的训练集里各语言和代码的比例决定了它们在 token 空间里的密度。
  • 字节级 BPE：从 UTF-8 的 256 个字节出发，反复把最常见的相邻对合成新 token；分词器的参数就是 merges 表，编码时按合并顺序反复应用。
  • 不是任意字节序列都是合法 UTF-8，解码要用 errors="replace"；编码再解码能还原，反过来不一定。
  • GPT-2/GPT-4 先用正则把文本按字母、数字、标点、空白切块，块内再做 BPE；GPT-4 忽略大小写、数字最多三位一组、合并空白，词表约 10 万。
  • 特殊 token（<|endoftext|>、对话用的 <|imstart|> 等）由专门的代码处理；加新 token 要给嵌入表和输出层各加一份参数。
  • 拼写、反转字符串、非英语、算术、Python 缩进、末尾空格、SolidGoldMagikarp、JSON 比 YAML 费 token，这些怪现象都能追到分词上。

GPT-2 的结构

GPT-2 是只有解码器的 Transformer：没有编码器，也没有用到编码器的交叉注意力。和原始 Transformer 相比还有两处不同：Layer Normalization 挪到了注意力和多层感知机之前（pre-norm），以及在最后一个块之后、分类器之前多加了一个 Layer Normalization。

模块命名照 Hugging Face 的 schema 来，这样方便加载权重。transformer 是一个 nn.ModuleDict，里面有 wte、wpe 两个 nn.Embedding，h 是 12 个 Block 组成的 nn.ModuleList，ln_f 是最后的 Layer Normalization。

外面还有 lm_head，从 768 投影到 50257，不带偏置。

Block 里：x = x + self.attn(self.ln_1(x))，x = x + self.mlp(self.ln_2(x))。原始论文把 Layer Normalization 放在残差通路里面，这里是一条干净的残差通路，从监督信号一直到输入的 token，梯度经加法原样流下去，各个块逐渐加入贡献。

他还给了一个看法：注意力是 token 之间交换信息的地方，是聚合、加权求和，是 reduce；多层感知机对每个 token 独立计算，是 map。Transformer 就是反复地 map-reduce，每个块不断精炼残差流里的表示。

多层感知机是两个线性层夹一个 GELU，用的是 nn.GELU(approximate="tanh")。GELU 像一个更平滑的 ReLU，在 0 附近没有完全平坦的区域，总有局部梯度，不会出现死 ReLU。

tanh 近似是历史原因：当年 TensorFlow 里计算精确 GELU 要用的 erf 函数很慢，于是 Hendrycks 搞了这个近似，被 BERT、GPT-2 沿用，现在没理由再用近似版，但要复现 GPT-2 就照用。LLaMA 3 这类更新的模型用的是 SwiGLU 等变体。

注意力用的是批量化的多头实现：一个线性层一次算出 q、k、v，再把头数当作和 B 一样的批维度，经过一系列 transpose 和 view，所有头并行计算，最后再拼回去。数学上和上一集分开写的多头注意力等价，只是更高效。整个 GPT-2 实现不到 100 行，Hugging Face 的文件有 2000 行。

class Block(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.ln_1 = nn.LayerNorm(config.n_embd)
        self.attn = CausalSelfAttention(config)
        self.ln_2 = nn.LayerNorm(config.n_embd)
        self.mlp = MLP(config)
    def forward(self, x):
        x = x + self.attn(self.ln_1(x))
        x = x + self.mlp(self.ln_2(x))
        return x

加载权重和前向

配置改成 GPT-2 124M：blocksize 1024、vocabsize 50257（5 万次合并、256 个字节 token、1 个 endoftext）、12 层、12 头、768 维。

from_pretrained 是一个类方法：建好自己的模型，遍历 Hugging Face 模型的 statedict 逐个拷贝张量，跳过注意力掩码这类缓冲区。有个麻烦：因为来自 TensorFlow，有几个权重是转置的，要手动列出来转置再拷。

前向：输入 idx 是 B×T 的 token 下标，T 不能超过 blocksize。

用 torch.arange(T, device=idx.device) 得到位置，查出位置嵌入和 token 嵌入相加（位置嵌入对批里每一行都一样，有广播），过 12 个块、ln_f、lm_head，得到 B×T×50257 的 logits，再 softmax 一下就是下一个 token 的概率。

采样

model.eval()，虽然这个模型里没有 dropout、Batch Normalization 这类训练和评估时行为不同的层。model.to("cuda")：他通过 SSH 连着一台有 8 张 GPU 的云主机，这一步把所有张量送到 GPU 上，那几乎是另一台为并行计算设计的计算机。

用 tiktoken 的 GPT-2 编码把前缀编成 8 个 token，复制成 5 行。

循环里每次前向只取最后一个位置的 logits，softmax 后做 top-k 采样（k = 50，Hugging Face pipeline 的默认值）：只保留概率最高的 50 个 token，其余置 0 再归一化，这样不会采到非常罕见的 token，模型不容易跑偏。

采到的 token 拼到序列后面，直到 30 个，再用 tiktoken 解码。整个循环包在 torch.no_grad() 里。

生成的文本连贯，但和 Hugging Face pipeline 的结果对不上，他也没找出 pipeline 还做了什么；不过用 Hugging Face 的模型配同样的采样代码能得到相同结果，说明权重加载没问题。

把模型换成随机初始化的 GPT(GPTConfig())，生成的就全是乱码。他还加了自动检测设备：优先 CUDA，其次 Apple Silicon 的 MPS，最后 CPU。

数据批次和损失

调试用的数据是 tiny Shakespeare：约 4 万行、20 万词、100 万个字节（全是 ASCII，字节数就是字符数）。GPT-2 分词器的压缩率约 3 比 1，100 万字符约 33.8 万个 token。

他最喜欢的做法：取 B×T + 1 个 token 放进 buf，x = buf[:-1].view(B, T)，y = buf[1:].view(B, T)，y 就是 x 每个位置的目标，多取的一个是为了给最后一个位置也配上标签。

forward 加一个可选的 targets 参数，有就算损失：F.cross_entropy(logits.view(-1, logits.size(-1)), targets.view(-1))，因为它不接受三维输入，要把 B×T×V 摊平。

初始损失约 11，理论值 −ln(1/50257) ≈ 10.82，说明初始化时各 token 的概率大致均匀，没有很自信地错。

先过拟合一个批次，再写数据加载器

优化器用 AdamW，他认为 AdamW 是对 Adam 的一个 bug 修复。它比随机梯度下降多维护两个缓冲区 m 和 v，即一阶矩和二阶矩，类似 momentum 和 RMSprop，对每个梯度元素做归一化，在语言模型上收敛快得多，这里先当黑盒用。学习率 3e−4 是早期调试时不错的默认值。

循环里先 optimizer.zero_grad()（backward 是往梯度上累加的），loss.backward()，optimizer.step()；loss.item() 把 GPU 上的单元素张量拷回 CPU 变成 Python 浮点数。

中间报了「张量在不同设备上」的错：model.to(device) 是原地的，但张量的 .to(device) 不是，返回的是新张量，要写 buf = buf.to(device)。修好后在同一个批次上反复训练，损失从 11 一路降到很低，Transformer 把这个批次记住了，说明代码基本没问题。

然后写 DataLoaderLite：读入整个文本、分词，从位置 0 开始每次取 B×T + 1 个 token，位置前进 B×T，用完了就回到开头。数据放在 CPU 上，每个批次再送到 GPU。

B = 4、T = 32 时一个 epoch 要 2600 个批次。跑 50 步损失降到约 6.6：这时的收益主要来自把数据里从不出现的 token 的概率压下去，比如各种 Unicode 和其他语言的 token。

权重共享

加载权重时漏了一个细节：wte 和 lm_head 形状一样（50257×768），元素完全相同，data_ptr() 也一样，说明它们是同一个张量。这是权重共享（weight tying），来自《Attention Is All You Need》，更早来自 Press 和 Wolf 的论文。

直觉是：语义相近的两个 token（比如大小写不同、或不同语言的同一个词），在底部的嵌入空间里应该接近，在顶部的输出端也应该得到相近的概率，两处都有「相似的 token 应该有相似的权重」这个性质。论文观察到输出嵌入也表现得像词嵌入，共享后效果更好。

OpenAI 的 TensorFlow 代码里确实是用 wte 算 logits 的，反向时两处的梯度会加到同一个张量上。实现就一行：self.transformer.wte.weight = self.lm_head.weight。这还省了大量参数：768×50257 ≈ 3900 万，约占 124M 的 30%，训练不够长时参数少一些效率更高。

GPT-2 的初始化

GPT-2 和 GPT-3 论文都没把初始化说清楚，只能看 OpenAI 发布的代码：线性层权重用标准差 0.02 的正态分布，偏置为 0（PyTorch 默认是均匀分布），token 嵌入 0.02，位置嵌入 0.01（这里也用 0.02）；Layer Normalization 的 γ 为 1、β 为 0，和 PyTorch 默认一样。

用 self.apply(self._init_weights) 遍历所有子模块。0.02 也不离谱：按 1/√dmodel 算，768 是约 0.036，1600 是约 0.025，和它在同一量级，只是没有随模型大小变。

GPT-2 论文还说：考虑到残差通路上的累积，残差层的权重要乘以 1/√N，N 是残差层数。原因是残差流每经过一个块就加上一份贡献，方差会增长：从 0 开始加 100 次标准正态，标准差变成 10；每次的贡献乘以 1/√100 后，标准差回到 1。

实现上给每个块最后投回残差流的线性层（注意力和多层感知机的 c_proj）打个标记 NANOGPT_SCALE_INIT，初始化时标准差乘以 (2·nlayer)−0.5，乘 2 是因为每层有注意力和多层感知机两次加回残差流。共享的 wte 和 lm_head 会被初始化两次，都是 0.02，无所谓。

def _init_weights(self, module):
    if isinstance(module, nn.Linear):
        std = 0.02
        if hasattr(module, 'NANOGPT_SCALE_INIT'):
            std *= (2 * self.config.n_layer) ** -0.5
        torch.nn.init.normal_(module.weight, mean=0.0, std=std)
        if module.bias is not None:
            torch.nn.init.zeros_(module.bias)
    elif isinstance(module, nn.Embedding):
        torch.nn.init.normal_(module.weight, mean=0.0, std=0.02)

硬件和精度

提速先看硬件：8 张 A100 SXM 80GB，从 Lambda Labs 租的（他们赞助了他的项目）。PyTorch 默认所有参数和激活都是 float32，深度学习其实用不了这么高的精度。

A100 的规格表上：FP32 是 19.5 TFLOPS；降到 TF32 可以到 156，约 8 倍；FP16 或 bfloat16 到 312，约 16 倍。带星号的更高数字是在稀疏情况下，一般不用；INT8 更快，但它的取值间隔均匀，适合推理，训练时权重和激活都接近正态分布，需要浮点数。

精度降低还有一个好处：每个数占的位少了，搬运更快。很多深度学习训练是受内存带宽限制的：Tensor Core 做乘法很快，大部分时间却在等数据从显存搬过来。一个调得很好的程序硬件利用率能到 60% 就很好了。

Tensor Core 是 A100 里的一条指令，做 4×4 的小矩阵乘法，矩阵乘都被拆成这种指令。Transformer 的计算几乎全是线性层里的矩阵乘，残差加法、GELU、Layer Normalization 相比之下可以忽略；在 124M 这个规模，最大的矩阵乘是最后从 768 到 50257 的分类层。

TF32

A100 白皮书里讲了 TF32：和 FP32 一样有 1 位符号、8 位指数，只是尾数被截掉 13 位，剩 19 位。这一切发生在指令内部，输入、输出、累加都还是 FP32，PyTorch 代码里看到的数一点没变，只是乘法快了，结果稍微近似一点，实际训练中基本看不出区别。他觉得这几乎是白送的。

先建立基线：批量 16、序列长度 1024（GPT-2 的最大长度），计时要先 torch.cuda.synchronize()，因为 CPU 只是往 GPU 排队派发任务，不等 GPU 做完时间就不准。

批量要尽量大到放得下，并且取有很多因子 2 的「好数」（16、24、32、48），别用 17。用每秒处理的 token 数衡量吞吐，比每步时间更客观。FP32 基线约 1000 毫秒一步，约 1.6 万 token/秒。

开 TF32 只要一行 torch.set_float32_matmul_precision("high")，所有 nn.Linear 里的矩阵乘都会走 TF32 的 Tensor Core。理论上 8 倍，实际降到 333 毫秒，约 3 倍、约 5 万 token/秒。差距来自内存带宽：到处搬运的仍然是 32 位浮点数，乘法本身快了，搬运没快。

torch.set_float32_matmul_precision('high')   # 矩阵乘用 TF32

bfloat16 混合精度

再降到 16 位。bfloat16 保留了完整的 8 位指数，只截尾数，能表示的数值范围和 FP32 一样，只是精度低；FP16 缩小了指数范围，表示不了 FP32 的全部范围，所以要用梯度缩放器（gradient scaler），多了状态和复杂度。

FP16 在 Volta 时代先出现，大家只好用梯度缩放；Ampere 引入 bfloat16 后就简单多了。

PyTorch 的混合精度他推荐那篇专门的文档，忽略所有梯度缩放的部分，只看 torch.autocast：只包住前向和损失计算，不要包反向和优化器步进，也不要手动对张量调 .bfloat16()。包上以后 logits 变成了 bfloat16，参数 wte.weight 仍是 float32。

哪些运算转成 bfloat16 由 PyTorch 决定：矩阵乘这类对精度不敏感的会转，softmax、Layer Normalization、log softmax、损失计算等更敏感的大多保留 float32，文档写得不清楚。结果从 333 毫秒到 300 毫秒，5.5 万 token/秒，提升不大，因为还有很多别的瓶颈。

with torch.autocast(device_type=device, dtype=torch.bfloat16):
    logits, loss = model(x, y)

torch.compile 和 kernel 融合

model = torch.compile(model)，他称之为神经网络的 GCC。编译要花些时间，之后从 300 毫秒降到 129 毫秒，一行代码提速约 2.3 倍，约 12.5 万 token/秒。他认为除非在调试，都应该默认用它。文档里说提速主要来自减少 Python 开销和 GPU 读写。

没有编译时是「eager 模式」：Python 解释器一行行执行，每个运算立刻派发一个 kernel，它不知道后面要做什么。编译器能看到整段代码：一是把 Python 解释器从前向里完全拿掉；二是减少读写。以 GELU 的公式为例，拆开写是先算立方、再乘常数、再加回输入……每一步都要把数据从显存（HBM）搬到芯片上算完再写回去。

他借这个讲了 GPU 的存储层次：芯片上有约 120 个流式多处理器（SM），每个有 Tensor Core 和其他计算单元，还有 L1 缓存和寄存器，加上 L2 缓存，片上存储总共只有几十 MB，但极快；片外的 HBM 有几十 GB，带宽约 2 TB/s，但相对片上慢很多。

编译器发现这一串都是逐元素运算，就把它们合成一个 kernel：数据只搬上芯片一次，在片上做完所有运算再写回一次。这就是kernel 融合。

FlashAttention

有些融合 torch.compile 找不到，FlashAttention 就是一个。它来自斯坦福 2022-05-27 的论文，把注意力的四行（q·k、掩码、softmax、乘 v）融合成一个 kernel，但需要从算法上重写注意力的计算方式，所以编译器发现不了。

按浮点运算次数算，它比原来做得更多，却快得多，论文说可达 7.6 倍，因为它非常在意存储层次，大幅减少了对 HBM 的读写：那个 T×T 的注意力矩阵（单个头、单个样本就有约 100 万个数）从不在显存里实体化。

关键是在线 softmax：用中间变量 m（最大值）和 l（归一化因子）增量地更新，不必先拿到全部输入就能算 softmax。

这个技巧来自 NVIDIA 2018-05-08 的论文《Online normalizer calculation for softmax》，论文里已经推测减少内存访问能提高实际性能，四年后才由斯坦福做成 FlashAttention，他觉得这段历史很有意思。后来还有 FlashAttention-2。

PyTorch 里把那四行换成一行 F.scaled_dot_product_attention(q, k, v, is_causal=True) 就会调用 FlashAttention。

第 49 步的损失和之前几乎一样（6.0566 对 6.058，只差浮点误差），每步从 130 毫秒降到约 96 毫秒，快了约 27%。教训是：浮点运算次数不是关键，整个内存访问模式才是。

y = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # FlashAttention

好数和丑数

他说这是最「蠢」又最妙的优化。CUDA 里很多东西按 2 的幂组织，kernel 按 16、32、64 这样的块来切；输入不能被整除时，先算整齐的部分，剩下的边角再用效率很低的 kernel 补。

所以扫一遍代码找「丑数」：1024、768 都很好；GPT-2 XL 的 25 个头很丑，他们最近优化 kernel 时就被它折腾过；词表 50257 最丑，是奇数。

把 vocabsize 改成 50304（能被 128 整除），相当于加了些永远不会用到的假 token，计算量反而变多了，每步却从约 96.5 毫秒降到 93 毫秒，快了约 4%；用 PyTorch 2.3.1 或更早版本能快约 30%。

功能上不会出错：嵌入表多出的行永远不会被索引；输出层多出的维度，网络会学着把它们的概率压到 0，这和 tiny Shakespeare 里根本不出现的大部分 token 一样。到这里，每步从约 1000 毫秒降到 93 毫秒，约 11 倍。

GPT-3 的优化超参数：AdamW 和梯度裁剪

GPT-2 有权重没细节，GPT-3 有细节没权重。两者架构几乎一样，GPT-3 的上下文从 1024 扩到 2048，训练久得多、数据多得多，最大的有 1750 亿参数（GPT-2 最大 15 亿），评测也更全面。所以照 GPT-3 附录里的设置来。

AdamW 的 β1、β2 设为 0.9、0.95（PyTorch 默认 0.999），ε 为 1e−8。梯度裁剪：loss.backward() 之后用 torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)，把所有参数梯度拼成一个向量，它的长度（平方和再开方）不超过 1。

遇到一个坏批次时损失很高、梯度很大，可能把优化「震」坏，裁剪是一种有点 hacky 的保护。这个函数返回裁剪前的范数，他建议一直打印：平稳就好，持续上升或突然出现尖峰说明训练不稳定。刚开始范数约 30，几步后稳定在 1 以下，开头大是因为模型在快速学习输出 token 的偏置之类简单的东西。

学习率调度

GPT-3 用带预热的余弦衰减：学习率从接近 0 线性升到最大值，再按余弦曲线降到最大值的 10%。论文里预热 3.75 亿 token，在 2600 亿 token 时降到 10%，之后以 10% 继续训练到 3000 亿。PyTorch 有现成的调度器，但他更愿意自己写这五行，清楚里面在干什么。

GPT-3 Small（12 层、768 维，相当于 GPT-2 124M）的最大学习率是 6e−4，最小取 10%。设置学习率要遍历 optimizer.param_groups。

第 0 步用 (it+1)/warmupsteps 避免学习率正好为 0。这里衰减终点和总步数一致，和论文略有不同，他认为影响不大。用什么学习率调度完全看你，余弦是 GPT-2、GPT-3 带火的，还有很多别的，仍是活跃的研究方向。

def get_lr(it):
    if it < warmup_steps:                       # 线性预热
        return max_lr * (it + 1) / warmup_steps
    if it > max_steps:
        return min_lr
    ratio = (it - warmup_steps) / (max_steps - warmup_steps)
    coeff = 0.5 * (1.0 + math.cos(math.pi * ratio))   # 从 1 降到 0
    return min_lr + coeff * (max_lr - min_lr)

批量调度、无放回采样、权重衰减

GPT-3 还线性地逐步增大批量，这里跳过：它让每步处理的 token 数变来变去，算术变复杂，而且主要是系统速度上的改进，不是算法上的。训练初期模型主要在学哪些 token 根本不出现这类简单的偏置，每个样本给出的梯度高度相关，几百万的批量和 3.2 万的批量给出的梯度几乎一样；后期梯度才变得不相关，大批量才真正提供统计上的价值。

数据无放回采样直到 epoch 结束：现在的数据加载器按顺序遍历，已经满足了。

权重衰减 0.1（AdamW 默认是 0.01）。写了一个 configure_optimizers：只对二维参数（参与矩阵乘的权重和嵌入）做衰减，偏置、Layer Normalization 的 γ 和 β 这类一维参数不衰减。衰减相当于给权重加一点往 0 拉的「重力」，防止个别权重太大，迫使网络把工作分散到更多通道上。

打印出来：衰减的有 50 个张量，占绝大多数参数；不衰减的有 98 个张量，只有约 10 万个参数。另外如果有 fused 选项就用 fused AdamW：不再用 for 循环逐个张量更新（那要启动很多 kernel），而是一个 kernel 更新全部参数。

每步从 93 毫秒降到 90 毫秒。他提醒，权重衰减、学习率、批量、Adam 参数之间的关系在优化文献里非常复杂，这里只是照抄 OpenAI 的设置。

梯度累积

GPT-3 表里，小模型用较小的批量、较大的学习率，大模型反之。124M 对应的批量是 50 万 token，按每行 1024 个 token 算要约 488 行，一张 GPU 放不下。但批量和其他超参数相关，要忠实复现就得用约 50 万。办法是梯度累积：串行地做多次前向反向，梯度不断累加，攒够了再更新一次。

总批量取 219 = 524288（一个好数），每次前向反向的微批量是 16×1024 = 16384 个 token，所以要累积 32 步，按每次约 100 毫秒算，每步约 3 秒。

但直接循环 32 次 loss.backward() 是错的。他用一个小例子说明：均方误差损失默认对 4 个样本取平均，有个 1/4 的系数；拆成 4 次批量为 1 的反向时，每次的损失没有这个 1/4，累加梯度等于对损失求和，所以梯度不一致。

交叉熵默认也是对 B×T 个位置取平均，所以每个微步的损失要先除以累积步数。另外要用 loss.detach() 单独累计一个 loss_accum 用来打印，每步处理的 token 数也要乘上累积步数。这样 B 只是一个性能设置，GPU 大可以调大，结果在浮点误差范围内一样。

for micro_step in range(grad_accum_steps):
    x, y = train_loader.next_batch()
    with torch.autocast(device_type=device, dtype=torch.bfloat16):
        logits, loss = model(x, y)
    loss = loss / grad_accum_steps   # 补上取平均的系数
    loss_accum += loss.detach()
    loss.backward()

分布式数据并行

他付钱租了 8 张 GPU，该全用上了。用 PyTorch 的 DistributedDataParallel（别用老的 DataParallel）：启动 8 个进程，每个绑定一张 GPU，各自跑几乎一样的训练循环、处理数据的不同部分，算完梯度后再求平均。

启动命令从 python train_gpt2.py 变成 torchrun --standalone --nproc_per_node=8 train_gpt2.py，torchrun 会设置 RANK、LOCAL_RANK、WORLD_SIZE 环境变量。

WORLDSIZE 是进程总数 8；RANK 是每个进程的编号，代码完全一样，只有它不同；LOCALRANK 是单节点内 GPU 的编号，多节点时才和 RANK 不同。设备设成 cuda:{local_rank}，0 号进程当 master，负责打印、记日志、存检查点。

要时刻想象有 8 个 Python 解释器同时往下执行这段代码。总批量不变，梯度累积步数要除以 worldsize：16×1024×8 = 131072 个 token 一次前向反向，所以只需累积 4 步。

打印要用 if master_process 守住，否则打印 8 遍。数据加载器要知道自己的 rank：起点是 B×T×rank，每次前进 B×T×worldsize，彼此错开。

模型照常建 8 份（种子相同所以完全一样，各自编译），然后包进 DDP(model, device_ids=[ddp_local_rank])（文档里对 deviceids 的说明他觉得几乎看不懂）。

它的前向不变；反向结束时对梯度做 all-reduce，在所有 rank 间求平均并放回每个 rank，而且能在反向还没结束时就开始传已经算好的层的梯度，通信和计算重叠。

梯度累积时不需要每个微步都同步，只在最后一个微步同步。官方做法是 no_sync 上下文管理器，他嫌要复制代码，就直接设 model.require_backward_grad_sync = (micro_step == grad_accum_steps - 1)，承认这有点「顽皮」，以后版本可能失效。

lossaccum 在这个容器外面，没有被平均，所以再用 dist.all_reduce(loss_accum, op=dist.ReduceOp.AVG) 求平均后再打印。

configure_optimizers 要在 raw_model = model.module 上调用；结束时调用 destroy_process_group()。跑起来每秒 150 万 token。和单卡的结果不完全一样，是因为数据加载器到头回绕的边界效应不同；把总批量调小到 32768、单卡累积 8 步，两边的数字就对上了。

数据集：FineWeb-Edu

GPT-2 用的 WebText 没有公开（有人复现了 OpenWebText）：抓取 Reddit 上至少 3 个 karma 的外链，4500 万个链接、约 40 GB 文本。

GPT-3 用了 Common Crawl，它非常嘈杂，是互联网的随机子集，大部分是广告、垃圾、表格、股票代码，所以大家花大力气过滤，再和 WebText2、书籍、维基百科等混合，这个数据集也没公开。现在有代表性的公开数据集比如 RedPajama 及其清洗去重后的 SlimPajama。

他喜欢的是 Hugging Face 最近发布的 FineWeb：从 Common Crawl 精心过滤出 15 万亿 token，页面上详细记录了处理过程，很值得读。

之后又发布了 FineWeb-Edu，过滤出教育内容：1.3 万亿 token 的教育子集和 5.4 万亿 token 的高教育子集，过滤是用 LLaMA 3 70B 判断内容是否有教育价值的。这里用它的 sample-10BT，100 亿 token 的子样本，他之前的实验表明这足以接近 GPT-2 的性能。

写了 fineweb.py 下载、预分词并存成分片：每个文档以 endoftext（50256）开头（虽然叫 end of text，实际作为文档的开始），token 存成 uint16 以省空间（GPT-2 最大 id 远小于 65535）。

每个分片正好 1 亿 token 的 NumPy 文件，第 0 片是验证集，共 100 片。大约跑半小时。数据加载器改成能遍历分片、区分 train 和 val。

步数：100 亿 token 除以 219 约 19073 步；GPT-3 预热 3.75 亿 token，除以 219 是 715 步，他觉得很温和，100 步大概也行，但为了和 GPT-3 一致就用 715。他发现每张卡的微批量能放下 64，64×1024×8 正好是总批量，不需要梯度累积。每步约 330 毫秒，19073 步约 1.7 小时。

验证集和采样

每 100 步（后来改成 250 步）在验证分片上评估一次：model.eval()，重置验证集的加载器，torch.no_grad() 下累积 20 步的损失求平均。

数据几乎无限，训练和验证损失应该差不多，但验证集是判断是否过拟合的标准做法，多 epoch 训练时尤其重要。也可以把 OpenAI 的 GPT-2 124M 在这个验证集上的损失当参照，虽然它训练的数据分布很不一样，不算公平比较。

把最早的采样代码挪进训练循环，定期生成样本。用单独的 torch.Generator 并为每个 rank 设不同种子，不影响训练用的全局随机数状态。

一个问题：开着 torch.compile 时采样和 HellaSwag 评测会报一个吓人的错，他暂时没解决，只好关掉编译，所以后面跑得慢一点。第 1000 步的样本还很乱，学习率才刚升到最大值，「模型还是个小宝宝」。

HellaSwag 评测

HellaSwag 来自 2019-05-19 的论文，是句子补全的四选一题：比如「一个女人在户外拿着桶和狗，狗跑来跑去躲着不想洗澡，她……」，只有一个选项是自然的延续。题目取自 ActivityNet 和 WikiHow，覆盖很多生活领域。错误选项是对抗式生成的：由语言模型生成，模型觉得难、人觉得容易。

当时人类准确率 95%，最好的语言模型只有 48%；现在已经被做到 96% 左右，基本被「攻克」了。GPT-2 论文没用它，GPT-3 用了，并报告了各尺寸的结果。大家喜欢它是因为它平滑，有「早期信号」：小模型从随机的 25% 开始会慢慢地 26%、27% 往上涨。

小模型不会做选择题，不懂把选项和字母 A、B、C、D 对应起来，所以要用它原生的方式，也就是 token 补全：构造 4×T 的批次，每行是共享的上下文接一个选项，短的补齐，用一个掩码标出选项部分的 token；然后算每个选项部分 token 的平均交叉熵损失，选损失最低（平均概率最高）的那个。

据他所知 GPT-3 也是这样评的。有些评测把四个选项一起给模型看，这对模型更容易，但小模型做不到。

hellaswag.py 下载验证集的 1 万道题并渲染成这种格式。GPT-2 124M 是 29.55%，GPT-2 XL 约 49%；EleutherAI 的评测框架给出的数略有不同，可能是做法不同。

要超过的就是 29.55%。集成进训练循环时，让 8 张卡分摊题目（按题号模 worldsize），再用 allreduce 汇总正确数；训练损失、验证损失、HellaSwag 准确率都写进 log.txt。

第二天早上的结果

跑完 19073 步，约 100 亿 token，也就是 FineWeb-Edu sample-10BT 的一个 epoch。验证损失（橙色）低于 OpenAI GPT-2 124M 在同一验证集上的水平（红线），只是如前所说不是公平比较。

更可比的是 HellaSwag：从 25% 一路上升，超过了 GPT-2 124M（红线），GPT-3 124M（训练了 3000 亿 token）是绿线，还没到。

只用 100 亿 token 就超过了 GPT-2（他估计 GPT-2 训练了约 1000 亿 token），可能的原因有几个：GPT-2 的数据分布更广，FineWeb-Edu 全是英语，数学、代码和多语言不多，那些可能占用了原版 GPT-2 的容量。

HellaSwag 已经发布五年，题目可能以某种形式混进了 FineWeb，那看到的其实是训练曲线（Hugging Face 用 HellaSwag 做评测，他希望他们去过重）；也可能现在的数据集更讲究去重和质量过滤，每个 token 的质量更高。

另外损失曲线有奇怪的周期性，他怀疑 FineWeb-Edu 的 10B 样本没有充分打乱，而这里的加载器按顺序读，把原数据的顺序也继承了下来。

他又过夜跑了 4 个 epoch，约 400 亿 token，8 小时。周期性在每个 epoch 都出现；HellaSwag 涨了很多，到了 33.24%，差一点就到 GPT-3 124M，「可惜我没多睡一会儿」，跑 5 个 epoch 可能就到了。GPT-3 用了 3000 亿 token，这里约 10 倍的学习效率。

多 epoch 训练时应该每个 epoch 打乱分片和分片内的文档顺序，因为每行里文档是首尾相接的，现在相接的方式每次都一样，是一种虚假的相关。还有人发现最大学习率能调到约 3 倍，GPT-3 的设置可能很保守。要完全对齐 GPT-3，序列长度改成 2048、每卡批量改成 32，总量仍是 50 万 token。

过夜模型的样本连贯多了，比如「Hello, I'm a language model, and I try to be as accurate as possible」。代码里还加了每 5000 步存一次检查点（模型的 statedict）；想严格续训还要存优化器状态（AdamW 的 m 和 v）和随机数状态。

存下来的模型可以用 EleutherAI 的评测框架做更全面的评估。这些都只是预训练，模型只会「做梦」续写文档；要能对话还需要监督微调：把数据换成用户和助手的对话格式继续训练，采样时只生成助手部分。

llm.c，以及收尾

这一集写出的东西基本就是 nanoGPT。他最近还在做 llm.c：用纯 C/CUDA 实现 GPT-2、GPT-3 的训练，里面的 train_gpt2.py 就是 nanoGPT，作为 C 版本的参考实现，两边要逐步对齐。

单卡并排跑：llm.c 用 nvcc 编译得快，先开始迭代，PyTorch 还在等 torch.compile；llm.c 约 22.3 万 token/秒，PyTorch 约 18.5 万（他不确定 PyTorch 版本是否已经优化到头）；每一步的损失和梯度范数完全一样。

PyTorch 是通用框架，两者不完全可比，但只想训练 GPT-2、GPT-3 的话，llm.c 更快、更省内存、启动更快。

总结：看了 GPT-2、GPT-3 论文，讨论了训练设置的各种考虑，一切从零写起，两小时或一个通宵就能在很大程度上追平 GPT-2 和 GPT-3 的 124M 检查点，有耐心和算力的话同样的代码可以训更大的模型。

遗留问题：损失曲线的周期性、开 torch.compile 时采样和 HellaSwag 会坏、多 epoch 时要打乱数据，这些勘误和后续会记在随视频发布的 build-nanogpt 仓库里，那个仓库每加一个功能就是一个 git 提交。

这一集记住这几条

  • 先加载 OpenAI 的权重证明模型实现正确，再从随机初始化开始训练；GPT-2 相对原始 Transformer 的改动是 pre-norm 和最后多一个 Layer Normalization。
  • 权重共享（wte 与 lmhead 同一张量）省下约 30% 参数；初始化用标准差 0.02，投回残差流的层再乘 (2·nlayer)−0.5。
  • 提速靠理解硬件：TF32（一行代码，约 3 倍）、bfloat16 autocast、torch.compile 的 kernel 融合、FlashAttention（运算更多但读写显存更少）、把 50257 补成 50304，每步从约 1000 毫秒到 93 毫秒。
  • 训练多受内存带宽限制而非算力：GPU 片上 SRAM 只有几十 MB，减少与 HBM 之间的往返比减少浮点运算更重要。
  • GPT-3 的设置：AdamW β=(0.9, 0.95)，梯度裁剪到 1.0，预热加余弦衰减到 10%，只对二维参数做 0.1 的权重衰减，50 万 token 的批量；梯度累积时每个微步的损失要除以累积步数。
  • 分布式数据并行：每张卡一个进程，数据按 rank 错开，反向结束时 all-reduce 平均梯度；在 FineWeb-Edu 上训练 100 亿 token，HellaSwag 超过 GPT-2 124M，400 亿 token 接近 GPT-3 124M。
