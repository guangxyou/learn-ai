第一篇：RetNet —— 给线性注意力加上衰减

对我而言，我们是在 2023 年开始探索线性注意力这个方向的。这篇工作刚开始主要解决了两个问题。

第一个问题是：线性注意力怎么能尽量在一些比较 general 的场景下逼近全注意力的性能。

因为 linear attention 从刚开始提出，主要是为了用一个线性的 kernel、用 kernelize 的方式去拟合二次复杂度的全注意力这样一个 pattern。所以在之前那个时代，对于 linear attention 而言，它对位置信息其实是不够 sensitive 的。当时 linear attention 和 RNN 只是在形式上比较相似，但从建模特性上来讲，RNN 还是比较强调一些 locality 的表示。

所以在那个时代，我们比较早地在递归形式上引入了一个衰减（decay）机制——这样可以让线性注意力在一个有限的状态空间里，尽量去建模那些对最后结果贡献足够大的信息。

这个工作刚开始的 motivation 除了模型性能以外，我们当时也比较早地提出了一种块递归（chunk-recurrent）的计算形式。

对于线性注意力来说，如果把整个状态都展开、在 token 这个维度去做递归计算，从效率上并不是最优的；但如果仿照注意力那种计算方式去建模，它又享受不到整体计算复杂度带来的优势。所以我们当时就是在 parallel representation（像全注意力那样的并行计算形式）和全递归的计算形式之间，找到了一个 trade-off，也就是块递归这样的计算形式。

有了 chunk recurrent，我们既可以拿到整体计算复杂度上的收益，同时在 kernel 层面可以尽量多地去调用 tensor core，把 local 的计算密度都拉满。这是我们提出的一个比较有效的计算范式。

大家其实可以关注到，之后所有线性注意力的改进工作，都是基于这样的 chunk recurrent 计算形式去算的——包括 Mamba2、Gated DeltaNet，包括来到今天的 Kimi Linear、KDA 这样的计算模式。在这个大的计算模式之上，又带来了一些比较细节上的变化，这个后面会更详细地讨论。

纯线性注意力是个失败的尝试，混合注意力不是 trade-off

当然，从现在这个视角看，纯线性注意力无疑是一个比较失败的尝试。因为无论如何，这样一个比较有限的 state，都难以在长上下文中带来和全注意力完全相同的性能——这个在今天这个时间点，我们都知道是不可能的。

我们在 2023 年也注意到了这个现象，所以就尝试从全线性注意力转到 hybrid attention（混合注意力）这样的架构形式。混合注意力顾名思义就很简单——包括 K3 其实也是这样——就是用一些线性注意力和一些全注意力组合起来，作为一个模型的架构。

这本质上听起来像是一个工程上的 trade-off，也是一个比较工程的解法。但虽然如此，我们当时就发现一个现象（这个目前也是大家公认的）：混合注意力虽然从架构上讲是一种 trade-off，但从最后模型本身的表现来说并不是一个 trade-off。大家发现，在保持一定的全注意力比例的基础上，整个模型其实可以获得无损、甚至更好的长上下文表现。

也就是说，在混合注意力的架构中，我们并没有牺牲模型能力来换取工程上的收益。也正是因为这个实验上的结论，混合注意力现在被大规模地利用起来。

第二篇：YOCO —— 所有层共用一份 KV cache

孙宇涛

对，是的。

后来我们会发现，混合注意力在工程上是一个百分百 work 的方法，我觉得其实没有问题，直到今天 work 得也还是不错。但对于一个博士生来讲，这个东西虽然比较 work、大家也愿意用，但从 novelty 上感觉就差点意思，而且感觉也不够有趣。

因为我们当时觉得，如果只是把这两种注意力混合起来的话，它有这么几个问题。我觉得最大的问题是：它在推理上的加速比，永远和混合比是成正比例的。

比如大家现在比较常用的线性注意力比全注意力大概是 3:1，也就是全注意力在整个模型里大概占 1/4。如果我们认为 1/4 是一个比较无损、也比较极限的比例，那我们很难拿到更大的加速比——无论是 prefill 还是 decode，最多的加速比也就是 4 倍。而我们在做纯线性注意力的时候希望的是更高的；混合注意力其实只是一个常数级别的改进。

所以当时觉得可能不是很有意思，我们后来就做了 YOCO 这样一个工作。

当时的 motivation 是从第一性原理去思考：为什么纯线性注意力没有办法获得和全注意力一样的性能？原因也很简单——我们至少期望模型有一些基本能力，比如至少有一个可以获取全文信息的能力。在这个场景下，全上下文的 KV cache 这一点是没有办法省掉的。

既然 KV cache 没法省掉，我们能不能从另一个维度去省呢？既然从 token 长度这个维度没有办法节省，我们就找到了另外一条方向：从层间去节省。

所以 YOCO 当时做的是所有层共用一份 KV cache 这样的架构。

另外一个是从模型的计算角度：每一个 token 在 decode 的过程当中，它的计算密度是没有办法减少的，因为我们希望它保持一定的全注意力计算能力，这样才能达到我们希望的长上下文能力。所以我们提出的另一个东西是：把模型的计算和存储解耦开来。虽然我们只有一份 KV cache，但可以保持一个多层的 full attention 的计算结构。

所以在这个基础上，YOCO 架构只保留一份 KV cache，但可以获得和全注意力、或者混合注意力基本等价的计算结果。

这个架构还有另外一个优势：我们在 prefill 的时候可以直接跳过全注意力的计算。

prefill 就是模型处理用户输入的那个阶段。我们本质上只是希望拿到模型的 KV cache，给后续 decode 用。所以 prefill 的唯一目的就是拿到 KV cache——那么在这种架构上，我们经过前面一些 linear attention 的计算拿到了 KV cache，这就够了。因为 prefill 阶段我们没有必要解码出每一个位置的 next token prediction，所以在 prefill 阶段就可以直接不过 cross attention；但在 decode 阶段，我们可以保持和传统模型一样的计算能力。

这是我相关的第二篇工作。

第三篇：Universal YOCO —— 把 loop 放在线性注意力那一半

然后我个人的第三篇工作是：从一个更通用的角度来考虑问题。

模型的推理开销主要就分为三个部分：prefill 的时间开销、decode 的开销，和 KV cache 的存储开销。这三个是最主要的推理瓶颈，不可能有第四个。

YOCO 这个工作主要解决的是 prefill 和 KV cache，但没有解决 decode。decode 的话，后续大家会尝试用 sparse attention 的方式去解决——但 K3 目前没有用 sparse attention，所以这块今天就先不讲了。

我们后面的一个工作，和另一个赛道比较相似，也就是 looped language model。顾名思义，就是在保持固定的模型参数大小的情况下，通过多次迭代来提升模型的 FLOPs，从而提升模型总的能力。所以 loop 这一系列工作的主要目的，是在保持比较小的模型参数的基础上，取得比同参数模型好得多的效果。

但传统的 looped language model 在 decode 的情况下，成本其实是难以忍受的。因为它只是省了模型参数，并没有省计算；而且在相同计算下，它其实并不如把参数展开、或者用一个更大但不 loop 的模型效果好。比较传统的 looped language model 还有一个问题：它的 KV cache 存储会随着模型推理的深度而增加，所以最后总的算起来，looped language model 带来的总 KV cache 其实是相当大的。

Universal YOCO 这个工作，其实就是在 YOCO 架构的基础上做一个位置上的改变：我们把 loop 的单元变成一个很 efficient 的单元，从而避免推理时那些额外的、或者比较大的成本，同时保持模型效果比较稳定的增长。

解法也很简单。对于 YOCO 而言，它毫无疑问是一个混合注意力架构，但我们混合的方式不是一个交错式的结构，而是一个两段式的结构：模型的前期是全线性注意力，后期是全注意力。

所以我们的选择是：把 loop 只集中在线性注意力那个位置。这样对整体的 KV cache 增长是比较小的，因为 linear attention 本身的 cache 微乎其微。第二，线性注意力不仅省存储，其实也省计算——在长上下文场景下，它带来的额外计算是相当小的。而虽然 linear attention 带来的 decode 计算相当小，但从 in general 的模型能力上——比如从 perplexity、或者从 scaling behavior 上——它是可以获得足够接近全注意力的模型能力的。

所以这个架构可以达到的效果是：用差不多两倍于原模型的计算强度，基本上可以获得两倍左右的性能提升，但模型存储和 KV cache 还是保持和原模型差不多的推理开销。

这是我第三份工作。这份工作是因为去年开始 looped language model 是一个大家比较热议的话题，我们在这方面做了一些探索。

四、K3 导读：三个维度的 scaling

孙宇涛

好。K3 从它的主要卖点来说，我觉得从几个方面有一个比较大的囊括。

首先它说了它的一些结果——这个结果特别好，而且这些数都摆在这里，其实也没有太多可以解读的。然后为什么能达到这样的结果？K3 主要 claim 的是三个维度的 scaling。

当然我觉得最重要的还是模型大小的 scaling：它做到了 2.8T 这样的模型大小，而且是一个比较有效的 scaling 结果。

什么叫无效呢？无效的 scaling 是——我今天就可以给你，我晚上回去搭起一个 2.8T 的模型 init，我跑个 100B 的 token，然后我就可以放出来。这显然是无效的。所以 scaling 永远是要建立在有效的基础上。

K3 就是在 2.8T 这个 scale 上做了一个有效的 scaling，而且这个模型的激活参数来到了 100B 左右这样的量级。在 K3 发布的时间点，这其实是比国内其他几家开源模型要大很多的。

它另一个扩展是模型上下文长度的扩展，做到了 one million 这样的量级。one million 自然可以获得更大的上下文窗口，去解决更复杂的任务。

所以从模型总的来看，我觉得还是遵循一个第一性原理：更大的模型才有更大的智能上限。如果别的东西没有做得太错的话，大家可以看到，模型的参数大小还是解决模型智能最本质的一个参数。当然如果只看 benchmark 的话，你有无数种方式去达到一个对内或者对外满意的结果；但从模型能力的本质上，模型的参数大小还是最有效的方式。而 Kimi K3 是相当早期、或者说相当成功地达到了这样一个量级。

第二部分　模型架构

五、线性注意力的前世今生

孙宇涛

到模型结构这一章。Kimi K3 其实是综合了 Kimi 整个团队、包括整个业界过去一年以来比较重要的一系列创新。

这跟 K2 不一样。K2 当时 Kimi 的发力方向主要是模型 scale 本身，或者说一些非模型架构的创新，所以 K2 当时主要沿用的就是 DeepSeek-V3 的结构。但 K3 这块就跟 K2 大不一样了：K3 本身引入了很多比较新的、比较创新的设计元素——自己的也好、别人的也好，有些比较创新的裁剪也好、比较细节的调优也好，这块做了很多比较充足的准备。所以从观感上看，跟 K2 的感觉是很不一样的。

首先是 hybrid attention。我们可以重新翻回头来，从 Kimi 本身的写作来看起。

这块我会先讲一下线性注意力在过去三四年的历史发展状态。因为你如果直接读 KDA 的公式，会发现它相当复杂——不同的项具体是怎么来的、具体承担什么作用，直接看公式的话你会发现它特别特别长，比经典的 attention 要复杂很多。它每一项背后都有一个历史性的因素，或者说是大家对整个模型结构探索之后得到的结果。所以如果想了解 Kimi Delta Attention 最后是怎么设计出来的，我们还是有必要去看之前的线性注意力经过了怎样的发展阶段。

RetNet：把衰减引进来

让我们再回到 RetNet。这是刚开始必不可少的一个线性注意力发展阶段。

刚开始的线性注意力非常非常简单：我们就是拿 K、V 乘出来得到一个外积，然后把它加起来——刚开始的线性注意力其实比 RetNet 还要更简单。

RetNet 在这个基础上引入了一个衰减项，而且这个衰减是跟 token 的位置有关的。这样就把 linear attention 从一个 position invariant（位置无关）的东西，变成了位置有关的。

让它位置有关，最主要的方式一个是加 RoPE，另一个就是引入衰减项。因为无论如何，语言的特性就是更近的位置有更高的权重，所以如果我们想在一个有限的上下文里达到更好的结果，衰减这一项其实是必不可少的。这是线性注意力比较前期的一个经验，后面所有工作基本上都把衰减保持住了。

另一个主要的影响是：如果我们只是做偏学术性的研究、或者只是发 paper，其实 kernel 层面足够高的效率，大家刚开始不会特别强调。

但我们主要发现：完全用递归形式去计算，它特别慢——在训练过程中甚至直接比 parallel representation（类似全注意力那样的计算方式）还要慢。可如果直接用 parallel representation，又感觉十分离谱：因为训练的时候相当于完全没有享受到线性注意力的收益，它跟全注意力的计算强度是一模一样的，甚至还要更高——因为可能有一些别的处理，或者我们的 kernel 写得没有 FlashAttention 那么好。

所以我们当时觉得，无论如何都要找到一个比较可靠的计算 pattern，让它足够发挥 GPU 的能力的同时，享受到复杂度上的加速。当时我们就做了这样一件事情。

Mamba 与 DeltaNet：两个关键节点

RetNet 之后有两个比较重要的节点。

一个是 Mamba。Mamba 当时是把位置无关的衰减变成了位置有关的衰减。

接下来是 DeltaNet。DeltaNet 这个概念不是杨松琳提的，是之前的一个工作；松琳是在 DeltaNet 的基础上做了一件事，其实一句话就能说清：如何让 DeltaNet 变成一个 GPU 可计算的 chunk recurrent 计算模式。

当时松琳去做这方面工作的时候，我还稍微有点疑惑，我说看上去 DeltaNet 好像不太可以并行啊。她说可以并行，并且她已经搞定了。所以从 GPU efficiency 的角度，DeltaNet 主要解决的是效率上的困难，而且这个解决方式我觉得还是比较本质的。

DeltaNet 刚出来的时候我们当时尝试去解决一个问题：我们知道线性注意力在处理全上下文的能力上不如全注意力。当时就有两个方案。

第一个方案是直接认输——认定现在的线性注意力不可能匹敌全注意力。当时我是这种心态：我意识到从全线性注意力这个视角出发，是很难去匹敌全注意力的。

当然松琳是另一个想法，她当时觉得还可以再努力：我们可以努力去提升线性注意力本身的长上下文容量，从而获得更好的结果。DeltaNet 当时就是这样的目的。通过这种方式，我们可以获得比之前的 RNN 和 Mamba 更好的长上下文容量能力——本质上也就是在相同的 KV cache 大小下，从算法上提高了线性注意力的上下文容量。

Gated DeltaNet：把衰减和容量合起来

当时 DeltaNet 是没有做位置衰减的，从 perplexity 或者 benchmark 上它的结果不是特别好。所以一件比较显然的事情是：既然我们知道位置衰减本身可以帮助模型总的能力，那为什么不把衰减和 DeltaNet 这样一个更高容量的东西结合起来？

Gated DeltaNet 正是这么做的。我们结合 DeltaNet 那种更高的线性注意力计算容量，同时给它带来一个衰减，融合这两个，就可以得到一个更优的线性注意力表达形式。

这里就可以看到：如果没有 α_t 这一项，它其实就是一个比较经典的 DeltaNet；引入衰减之后，我们就得到了 Gated DeltaNet 这样的形式。

大家可以注意到，这个表达形式已经比刚开始的线性注意力复杂很多了：

  • 如果把 S_{t-1} 后面的系数完全消掉，其实就是最经典的 linear attention；
  • 而 RNN 和 Mamba 是把另一项消掉，得到的结果是：对上一个时间点的历史状态进行一个衰减；
  • DeltaNet 则是引入了 delta rule 这样的方案，写成递推形式的话，它其实是额外再增加了一项。

这样复杂度就慢慢地叠加了上去。

KDA：把标量衰减变成 channel-wise

我们再回到 Kimi。它其实在 Gated DeltaNet 的基础上又变了一个东西，大家可以对比一下这个式子是怎么引入的。主要的区别就在衰减项上。

在 RetNet、Mamba2 和 gated delta rule 的情况下——当然线性注意力是分 head 的，一般的线性注意力也分 head，但我们写公式的时候会考虑只有一个 head 的情况——如果只有一个 head，Gated DeltaNet 也好、之前的工作也好，它的衰减是一个标量，也就是说整个一个 head 遵循的衰减系数是一致的。

这样的好处是写 kernel 比较方便。因为如果把 decay 拆成更 refined 的形式，我们再去写 kernel 的话，它其实是一个不太好处理的项——这是出于写 kernel 方面的考虑。

而从模型能力方面，毋庸置疑：把标量的衰减变成 channel-wise 的衰减，严格来说是能力更强的。

Kimi Delta Attention（KDA）其实就是把 Gated DeltaNet 的衰减项从一个标量，变成了一个更 fine-grained 的量。这样每个 channel 的衰减系数可以不一样，带来一个严格更好的能力上限——因为从公式上讲它是严格更好的：无论如何，channel-wise 的 decay 都可以退化到一个比较均匀的 decay。

当然，对 KDA 来说，更强的模型能力是有代价的：写 kernel 会更麻烦。麻烦的点在于，我们不能像标量衰减那样，用一个比较方便的方式去利用 tensor core 进行计算。如果是标量衰减，处理会特别特别容易，一个 tile 里就只有一个变量就完事了；但如果把它从标量变成 channel-wise，处理难度就会增加很多。

这样的处理难度，也带来了 K3 里一个更细节的 co-design 处理。

这样我们就来到了 decay 的 lower bound。为什么有这个东西？两方面的原因。

一方面，从算法层面，我们希望它不要 decay 得太快。但从 paper 本身而言，它其实是为了和 kernel 做 co-design：我们想处理更 fine-grained 的 decay，就需要在数值上做一个比较巧妙的处理——对于 q 和 k，我们会做一个 decay 倒数的变换。

举个最简单的例子：−2 可以表示成 3 − 5。这个其实跟 RoPE 的思想是比较一致的。RoPE 在 infra 上一个特别方便的地方，就是它可以通过绝对位置变换来表示相对位置变换。在这种情况下，整个计算会容易很多。

RoPE 的思路就是用绝对位置来表示相对位置。所以对于衰减而言，它其实也可以用绝对位置来表示相对位置。

比如说我们有一个衰减项，它是 α² ——这个衰减可能是第 0 个 token 对第 2 个 token 的，也可能是第 100 个 token 对第 102 个 token 的。如果想用绝对位置，我们就会让 q 先做一个比较大的衰减，然后让 k 往上提升得比较大：比如让一边做三次方的衰减、另一边做五次方的反衰减，这样通过乘法结合律，就可以得出和原来的递归比较等价的形式。

但这样就带来一个问题：对 KDA 来说，它会对 q、k 其中一边除一个很小的数。乘一个很小的数可能没关系，无非就是 decay 到 0——当然我们也不希望它 decay 到 0，但从数值精度上讲，我们希望把它控制在 BF16 的精度范围内。这样「用绝对位置表示相对位置」的方式才是有效的。

所以为了让衰减在一定的窗口范围内、控制在 BF16 的精度范围内，我们需要从数学上把它控制住。比如 Kimi Linear 这块用的是 16 的 tile，我们就希望衰减在这 16 个 token 的 range 里，不要超出 BF16 的范围。BF16 的精度范围是已知的，我们可以反解出来：在 16 个 token 的区间内，最多可以衰减到多大的量。KDA 就大概选了这样一个量。

这块我们可以证明：在 16 个 token 的 tile 里，衰减是不会超出 BF16 的 dynamic range 的。所以这个 decay 的 lower bound，它更像是一种 co-design——我们通过模型算法层面的一些控制，让它在一定 tile 内部不要出现数值方面的问题，这样整个 kernel 化的方式会更加通畅。

当然，如果不去限制，kernel 肯定也有自己的写法，只是那种写法可能会低效一些。所以为了保证一个高效的实现，KDA 采用了「在一定的 tile 窗口内控制最大衰减程度」这样的方式。

KDA 大概就是这样。总的来说道理也很简单：

  1. KDA 把 Gated DeltaNet 的计算方式扩展了一下，提升了它的计算能力；
  2. 为了这个扩展带来的额外 infra 麻烦，他们在模型的表达范围内采取了一些限制，让它满足 kernel 化的要求。

最后得到了 Kimi K3 采用的形式。

六、Gated MLA：把千问的门控搬到 MLA 上

孙宇涛

下一个环节是 Gated MLA。顾名思义，它就是把两块东西结合了起来。

MLA 大家可能都很熟悉了，是 DeepSeek-V2 刚开始去用的，主要目的是减少 KV cache 的开销。MLA 这个配置后面主要被 DeepSeek-V3 和 Kimi K2 采用——当然 DeepSeek-V4 没有用。

因为 Kimi K2 也用了，Kimi 的同学们认为：MLA 如果在全注意力这个 scope 内部，大家觉得至少还是一个可以接受的形式，或者说没有必要去大动。所以 K3 还是采用了跟 K2 一样的形式，然后在 MLA 的基础上增加了一个 gate 操作。

gated attention 最早应该是通义千问团队开始用的。从千问那个团队的标题也可以看出来 Gated Attention 当时主要解决哪些问题：non-linearity（门控可以带来额外的计算强度）、sparsity、以及 attention-sink-free。后面这个东西可能并不是那么显然，得具体看它的 paper。

但 whatever——我觉得大家最 buy in 的一个点是它的训练稳定性，而且这个稳定性是被广泛验证过的。

大家可以从前面那张训练曲线图看到：我们还是希望它越稳越好。从模型能力上，如果不是最优的也没关系——因为模型能力本质上最主要的因素是参数大小，所以好一点差一点，都不如稳定性重要。

因为稳定性不好会带来很多麻烦。比较大的问题是：整个模型都训崩了，前面整个的 checkpoint 都废掉了。这个对于任何团队而言都是不可以接受的。所以如果一个方法能比较有效地提升稳定性，这还是一个大家比较愿意采用的技术。

千问的 gated attention，千问 3 应该是没有用；后来的千问 Next，包括千问 3.5、3.6 应该都采用了这样的架构。虽然它会带来一定的额外计算开销，但对模型稳定性会带来特别大的好处。

千问是在 GQA 上引入的。但这个设计其实跟 GQA 或者 MLA 本身是正交的。所以 K3 把这块做了一个结合，把 gated attention 这样的稳定性方式引入到 MLA 当中——这样它本身不会破坏 MLA 的推理性质，同时可以提升模型的训练稳定性。

七、Attention Residuals：残差连接的下一步

张小珺

好的，我们现在讲到 2.2 对吧？

孙宇涛

对，2.2 就是 Gated Attention。Gated Attention 当时还挺火的。但如果从它这条研究脉络来讲，我反而会认为 Hyper-Connections 是一个相当好的工作。

Hyper-Connections 是很早以前字节 Seed 团队提出的。这块主要讨论的是：在一个比较深的模型当中，深层到浅层的连接方式。

如果我们再仔细去考虑问题——因为它叫 residual，这个本质上跟 ResNet 有一个比较深刻的连接关系。ResNet 本身解决的就是：在模型参数增长的情况下，模型能力至少可以达到一个不退化的效果；包括从稳定性角度也是。所以无论从模型稳定性还是模型能力上，ResNet 本质上都比之前的一些工作有本质性的提升。

不过这个大家都很熟悉了。大家其实没有注意到的是，ResNet 是有两个版本的——一个是 CVPR 的版本，一个是后来那个版本。其实在 ResNet 那个时代，何恺明就已经讨论过 Pre-Norm、Post-Norm 和训练稳定性的关系了。

这个也可以追溯到 BERT 时代。BERT 时代大家还是更常用 Post-Norm，觉得 Post-Norm 的结果可能会稍微好一些。但在模型逐渐增大的情况下，大家发现 Post-Norm 有梯度消失的问题、或者说训练不够稳定，所以后面就逐渐采取 Pre-Norm 这样的残差连接手段。

苏剑林之前讨论过这样一个观点：它绝对不是「Pre-Norm 挪到 Post-Norm」这种摆放方式的区别——那样风险很大，因为一旦触及 Post-Norm 之前的问题，大的模型大家肯定是不敢上的。所以他当时强调的是：它一定是 Pre-Norm 的一个超集，至少可以退化到 Pre-Norm，是严格比 Pre-Norm 更强的结果。

这块主要是简单讨论一下残差这条研究线之前大概是怎么来的。

Hyper-Connections：给残差分支更大的容量

Hyper-Connections 我觉得是相当有意思的工作。我觉得无论是 DeepSeek 后来做的改进也好、还是别的也好，本质上都是从这篇工作来的。

它主要讨论的点是：在 Pre-Norm 的基础上，如何增加模型残差的容量，从而提升模型的表达能力。

当然，我之前也跟 Hyper-Connections 一作的同学交流过。我说我觉得这个工作从技术上还是很好的，但它最大的问题是 paper 写得太抽象了，不太容易读。

Hyper-Connections 我觉得本质上一句话就能说清：我们在 residual 这个分支上，用比模型 hidden state 更大的容量，来表示模型在推理深度上的状态。如果有更大的容量，它一定会有更好的效果。我觉得它从思想上是相当简洁的，只是 paper 的形式相对复杂了一点。

所以当时这个工作其实没有出圈，可能只是做架构或者技术层面的一些同学去了解。当然后来 mHC 可能就比 HC 本身要火了很多——但我觉得最重要的原因还是当时 mHC 是 DeepSeek 提的，我觉得可能没有别的原因。

为什么这类改动大家愿意上：推理阶段几乎免费

在 Hyper-Connections 之后，大家会尝试从模型本身的连接方式去提升模型能力。

因为从 Hyper-Connections 到 Attention Residuals，有一个比较好的点：它对于推理来说基本是免费的。在 inference 阶段几乎不会增加任何推理开销，就可以拿到更好的模型结果。

这个其实是大家喜闻乐见的。因为一旦涉及到「通过更慢的实现、更慢的架构设计来取得更好的表现」，那就带来一个自然的 trade-off：我为什么不去扩更大的 size，这样还简单一些？所以一切通过更慢的模型实现去提升效果的方法，其实都会被 fully questioned；甚至对于一些比较保守的、或者不是自己提的技术，大家可能就不愿意去用。

而对于这种在推理阶段几乎免费的设计，大家上的时候没有什么压力。

DenseNet：这个问题其实早就被想过一遍

Hyper-Connections 这个维度还有一个绕不过的工作，就是 DenseNet。

DenseNet 是更早的工作，是黄高老师在 ResNet 之后提出的一个连接方式。DenseNet 和 Attention Residuals 在思想上是相当密切的。

只不过在 DenseNet 时代，它只是层和层之间的连接方式——在深层去看所有浅层的状态，然后把它们聚合起来。但那个时代其实没有 attention，或者说大家没有过度重视 attention 本身的能力，所以 DenseNet 里边主要是用一个大的 linear 把之前所有层的表示聚合到一起。

到了 attention 时代，DenseNet 那个实现本身是不快的，因为连接方面会带来大量的额外计算。但到 attention 时代大家会发现：我们可以把 DenseNet 里边一些比较 heavy 的部件，变成更 lightweight 的部件——这样就诞生了 Attention Residuals 这样的工作。

Attention Residuals 最大的优势是：它比 DenseNet 是一个更 efficient 的架构，我们可以通过一些更深层次的 infra design——比如用 block attention 的方式去解耦掉模型的深度。

因为如果只是全注意力的话，上层会跟底下所有层进行交互。这也是之前一个比较大的问题：模型越深，这块的 overhead 越不可忽略。block attention 在这块做了一个解耦。所以整体来说，一方面 attention 本身的计算比较 lightweight，第二方面它解耦了深度——最后看起来，它就是一个比较灵巧、但能结结实实提升模型能力的组件。

这块可以看一些 scaling 的结果。Block Attention Residuals 因为解耦了深度，严格来说表达能力肯定不如 Full Attention Residuals 好；但这块大家 claim 的点是：它并没有损失太多能力，而且相对 baseline 是一个比较显著的提升。

Attention Residuals 这块主要是上一篇技术 paper 里讲的，K3 这块应该没有做太多特殊处理。

张小珺

你刚才讲的这几个，你觉得哪个创新性是最强的？

孙宇涛

其实我更喜欢 DenseNet 和 Hyper-Connections。

为什么？因为 DenseNet 是一个相当早的工作。在那个时代大家考虑连接的问题——我觉得本质上它 research 考虑的问题，DenseNet 其实都考虑到了，只不过当时没有 attention 而已。

而 Hyper-Connections 相当于是在 Transformer 时代重新把这个东西带了回来，让大家在连接方式上重新讨论：如何有一个更强的连接方式，从而提升模型性能。我觉得后面的工作当然会有一些 co-design、或者一些模型稳定性的问题，但大的框架其实是之前的工作已经定好的。

八、LatentMoE：把通信量压下去

孙宇涛

LatentMoE 应该是年初英伟达他们一个团队提出的。

这块一个比较大的好处是——如果熟悉 DeepSeek-V3 的同学都知道——训练 MoE 无论从模型稳定性、训练方式，还是从硬件上，其实都是一个很大的挑战。而最大的挑战就是 MoE 的 all-to-all dispatch：在 EP（专家并行）的情况下，它的 overhead 是相当大的。

为了解决这个问题，我们不得不引入 DeepEP 这样一个高度优化的通信库，来降低 all-to-all 的开销。而且不同的 MoE 设计架构方式，它不仅影响模型架构本身，甚至影响底层不同 infra 的设计选型——这个后面在 infra 那块会做更多讨论。

LatentMoE 本质上的东西在于：我们是否可以把 all-to-all dispatch 这块的开销减小。

因为 dispatch 需要把 hidden state 分发到各个专家卡上，而这个通信量会随着激活的 expert 数量和 hidden state 的大小同步增长。LatentMoE 的思想就是：能不能在减少通信量的同时，保持模型的表达能力。

它的方式是把 dispatch 的 head dim 减小——可能减小 2 倍、4 倍这样的量。当然，如果直接减小 head dim，后面 MoE 的参数量就会随之下降。为了弥补这部分参数量，有两种方式：

  1. 提升 FFN 本身的 intermediate dim，把之前降的那部分弥补回来；
  2. 进一步把模型拆碎，用更多的 expert 和更多的激活来弥补参数量的减少。

最后看下来——当然在英伟达这篇 paper 里它的结果是更好的——总的来说就是一句话：一个恰当设计的 LatentMoE configuration，其实可以完全保持 standard MoE 的结果。也就是说，我们可以在模型能力完全相等、甚至还能好一点的前提下，减小模型的通信开销。

而且通信开销在训练和推理中是不一样的。

训练因为我们主要优化的是 throughput，可以用一些 overlap 的手段把通信这部分弥补掉。但对于推理 latency 来讲，尽管我们可以用一些手段来掩盖通信开销，但这个时间是避免不了的，因为它整体在 critical path 上。所以对于推理 latency 来说，通信开销还是一个相当不可忽略的点。

所以从模型 efficiency 上讲，这里推理的收益其实比训练的收益要大——当然训练也有一定收益。所以如果 LatentMoE 不是一个 trade-off——我们不需要牺牲模型的表达能力来降低通信——那它其实还是一个 free lunch、或者类似 free lunch 的结构。K3 其实就是 follow 了这样的结构。

一条通用的经验：两个矩阵连乘，中间要加 normalization

在 LatentMoE 之上还有一些比较细节的改进。针对这个改进，我们可以讨论一个比较经典的问题——说起来也很简单：两个矩阵连乘。

这是一个非常非常基本的单元。两个矩阵连乘在模型表达能力上其实是没有增益的，因为严格来说它可以合并成一个。但优化性质上并不是这样：两个矩阵连乘经常会出现训练不稳定的问题。所以一般中间会搭配一些稳定性的手段来弥补。

这个思想在 MLA 里也出现过：MLA 本质上就是先做一个低秩投影，再把它打回来——也是两个 linear 连乘的方式。而两个 linear 连乘中间，一般会采取一个 normalization，把中间的 hidden state 控制住，从而提升整体训练的稳定性。

所以这个通行的做法很简单：在模型架构设计当中，如果你不得不把两个矩阵连乘拆开写、而不是合并到一起，中间一定要加一个类似 normalization 的手段。

LatentMoE 也是类似的道理。归根结底，LatentMoE 是先把 hidden state 通过一个 linear projection 压到一个低维状态，再在这个基础上进行后面的计算。而对于 FFN 来说，第一个计算当然也是一个 linear projection——所以这块就出现了两个 linear projection 连乘的情况，需要一个 RMSNorm 去控制它。

九、SiTU-GLU：把激活值的上界钉死

孙宇涛

下面是 SiTU-GLU。这个设计看起来可能没有那么直观，它其实也跟之前的一些设计有关系。

大家会发现，对于大模型训练来说，FFN 这块的 MLP，中间的 activation outlier 是一个特别容易 activation explode 的地方。这个一是跟优化器有关，另一个是跟模型精度有关——在模型精度更低的情况下，中间的 hidden state 更容易出现 outlier。

为了解决这个问题，GPT-OSS 刚开始采用了一个特别简单的做法：把没有 bounded 的那块直接通过一个 clip 控制住——比如设一个 clip 的值，5 到 10，把它 clip 到这样的程度。这样从数学上就可以比较严格地把上限控制住。

clip 是一个比较粗暴的做法。如果你把 hard clip 变成 soft clip，就会比较自然地得到 tanh 这个算子——因为 tanh somehow 就是一个 soft clip：如果你指定一个上下界，它可以用一个比较平滑的方式去逼近你希望的上界。

从这个角度讲，可以把它理解为 clip 的一个升级版。这个升级版具体在模型表达能力上有多大影响，是另一回事，肯定需要具体实验来证明。但 whatever，我觉得 soft clip 还是一个比较安全的做法。

从 SwiGLU 开始，首先把一个比较自由的 linear projection 改成了 tanh 的状态。另一块是 Swish：SwiGLU 前面就是一个 linear 的结果，再加一个 GLU 的结果；而 Swish 又可以拆成 sigmoid 和一个 linear projection，当然这块是共享权重的。

所以 SiTU-GLU 相当于：把所有中间可能出现 unbounded 的环节，都通过 tanh 的上下界放缩绑住。这样就可以给整个 MLP 中间的激活一个严格的数学上界，用来保持模型的训练稳定性。

从 Muon 说到 MuonClip

当然这块我觉得可能还有一些别的 concern。比如说我们发现，如果用 Muon 的话，其实是会更容易出现 outlier 的——控制中间的激活值，总不是一个好做的事情。

当然如果我说 Muon 更容易引来 outlier，苏剑林一定会反对。他肯定会说：对于任何优化器来说，它都一定会出现 outlier，因为你从模型架构上是控制不了的。所以如果想严格控制，方法一定是直接从模型架构下手。

张小珺

为什么苏剑林跟你观点不一样？

孙宇涛

这个他没有说，但我猜到他会这么说。

因为之前在 Kimi K2 的 MuonClip 里也做过类似的讨论。大家如果对 Kimi K2 或者 Moonlight 有印象的话，当时就会说：因为用了 Muon 优化器，所以 QK logits 会更容易爆炸。所以 Moonlight 他们采用了一种对 QK 比较特化的处理方式，来压制模型的 outlier。

在那个时间点大家就问：为什么我们之前用 Adam 训练不需要加这个东西？为什么之前的 QK logits 都很稳，不需要额外处理，现在却要特殊处理？

苏剑林当时是这么回复的：严格来说 Adam 也不是完全稳定，当时 DeepSeek-V3 可能 somehow 也有一些不稳定的现象，只是这并没有影响模型最终的结果。他当时的观点是：如果在训练里有可能出现某个错误现象，严格来说它就是容易出现的，只不过是出现早晚的问题。所以为了严格限制模型的这种行为，还是从模型架构本身去做限制，是一个更本质的方案。

所以这块他肯定也是相同的观点：我们为什么不直接在 architecture 上做一些改变，把幅度限制住就完事了，也不需要去纠结更复杂的优化细节。我觉得是一个道理，所以我觉得他应该还会这么说。

张小珺

这是对 K2 的一个沿用，对吧？

孙宇涛

对，这块相比 K2 没有做太多改变。

当时比较严重的问题是控制不住中间的 activation outlier。更早的一个版本更粗放，当时连 weight decay 都没有加。所以 Moonlight 比较率先地把 weight decay 引入到比较大规模的模型训练里，这样在更长的 run 里边是可以保持住的。

到了 Kimi K2，它就在 weight decay 的基础上，额外搞了一个 QK-Clip 的放缩方式。这两个加起来，就是 Kimi 团队在优化器上一个比较完整的工作。

当然现在大家用的方式比较多了，但解决的方式不太一样。

比如说你用 MLA，就没有办法去加 QK-Norm——因为 QK-Norm 是严格限制 QK 这块边界的。所以为了适配 MLA，Kimi 当时引入了 QK-Clip 这样的操作。

而大家可以注意到，比如 DeepSeek-V4 以及后面那些，他们应该都是用了 Muon；在 Muon 的基础上，因为他们用的不是 MLA，所以直接用 QK-Norm 就行——本质上是一个更简单的办法。

十、Quantile Balancing：把负载均衡从启发式变成推导

孙宇涛

Quantile Balancing 没有发论文，是苏剑林在他自己的博客里讲的。

它主要可以 follow 到之前的 loss-free routing（无辅助损失路由）方式。loss-free 的控制方法是：只通过一个 bias，而不是通过一个偏整体的 loss 控制方式，来解决模型 expert 的负载均衡问题。

当时 loss-free 大家比较奇怪的一个问题是：这个 bias 变量直接决定了每个 token 选哪些 expert，但它的更新方式某种程度上是有些 hard 的——它采取了一个比较启发式的更新方案。

这里的问题一个是：它没有一个比较严格的数学收敛标准；另一个是，它容易让人觉得跟主模型的更新没有那么耦合。

但这个形式本身还是可以 work 的，整体还不错。

不过在整体 work 不错的情况下，loss-free 有几个问题可能是没有完全解决的。最主要的问题是：使用 loss-free 的时候，大家可能会采取「把模型最底下几层——一层或者三层——的 MoE 都去掉」的方案。

主要原因在于：对于 loss-free 这样的控制方案，对底层的模型来说它 work 得不是很好。正是因为 loss-free 整体没有做一个耦合，所以它可能会采取一些别的方式，来弥补模型在大规模训练中碰到的问题。

而 Quantile Balancing 主要是尝试用一个更 principled 的思想，来解决 MoE 负载均衡的问题。

loss-free 的 update 方式肯定是经过大量调整之后得到的一个 work 还不错的方案，本质上也很简单：某个专家激活得多了，就把 bias 往下砍一点；哪个激活得少了，就往上加一点。之前的 loss-free 是用一个比较启发式的方案去做。

而 Kimi 团队用的是更 practical 的方案：我们能不能直接推导出来，这个 bias 应该长什么样？

答案是这是可以被推出来的，而且推出来的具体方式跟之前的 Expert Choice 有一定关系。经过一系列推导，最后得到一个逐 step 的形式：对于一个 step 内部的整体激活，我们可以求一个 bias，而这个 bias 本身就是一个让模型负载均衡的方案。

他博客里也写到：为了避免信息泄露——我们不能让任意一个 token 获得其他 token 的信息——所以这个 bias 并不会在当前 step 使用，而是会在下一步使用。这是中间的一个细节。

苏剑林博客里主要提到的优点，首先是它不需要调参数。因为 loss-free 是有一个类似 learning rate 的更新方式的，这样就少了一个参数，整体看起来会更 principled 一些。

第二个优点是：它对于负载均衡的能力其实是更优的。他博客里贴出了一个图。

就像我刚才提到的，为了兼容 loss-free 的负载均衡，之前大家会把前几层搞成 dense、不用 MoE，把这个问题规避掉。而如果用 Quantile Balancing 这种方式，就没有必要去规避了——它可以直接把第一层也变得 balance。

这其实可以发现：前面底层用 dense，并不是原理上非这么做不可的方式，而是在 loss-free 这个 context 底下不得不采用的方式。如果你不采用 loss-free、直接采用加辅助 loss 的方案——比如千问 MoE 的工作就是直接求 loss 的方案——对第一层也会没有问题。

所以这块主要就是处理掉之前 loss-free 一些比较失效的情况。当然，他也提到：如果本来 loss-free 就比较 work，Quantile Balancing 也是比较 work 的。

而且他博客里也可以证明：在比较正常的情况下，可以推出来——如果 Quantile Balancing 不采用直接去均衡、而是采用一些梯度更新的方案，它其实可以和 loss-free 做到一个相当等价的数学形式。

工程上怎么落地：从按 token 切桶改成按值域切桶

这块还有一个细节是之前那个博客里没有提及的。

简单来说：现在大模型训练一个 batch 会特别大——4 million 可能都算比较小，可能到几十 million 这样的量级。而 Quantile Balancing 需要在几十 million 的 token 之间恰好取到某个比例的分位数。如果要精确计算，我们需要把所有 token 的激活情况都存下来——这是相当 heavy 的，甚至在工程上是不可能的。

博客里当时提出的方案是：每个 GPU 各自做一个 local 的分位数计算，然后把不同 GPU 的分位数汇总起来。（也不一定是不同 GPU，反正就是你得把一个大 batch 切碎，在小 batch 里求分位数，最后再做一个汇总。）

而 K3 这篇 paper 有一些不太一样的变化：它并不是按 token 去切桶的——当然也有可能是我理解错——它是在值域上切桶。

比如对于 sigmoid 的结果，它一定在 0 到 1 之间。所以我们可以在 0 到 1、或者 −1 到 1 这样的区间范围内切成 n 个桶，在桶里进行 histogram 统计。

这样有一个好处：它的存储是常数大小的，计算代价比比较朴素的实现要高效很多，而且可以比较好地处理大规模 EP 分布式架构下的情况，是一个比较容易扩展的状态。

这其实相当于是 K3 放出来的、之前博客里没有详细讨论的一个技术，是 Quantile Balancing 一个比较必要的实践方式。归根结底：naive 的实现基本上是不可行的，所以必须用一些工程上可行的方式，去把这个比较精确的解求出来。

十一、Native Vision：要不要用现成的视觉编码器

孙宇涛

然后到 2.7 了。Native Vision 这块其实没啥好说的，它主要讨论的一个点是：是否有必要用一个已有的 vision encoder 去做初始化。

用已有的 vision encoder，比如用 SigLIP 2 这样也是大规模训练过的，好处是收敛会比较快。

但 Kimi K3 中间讨论的一个问题是：如果直接用 SigLIP 去初始化，模型的不稳定性会比直接 from scratch 训练要来得大。

也不一定叫「模型不稳定性」——因为不稳定是一个比较相对、甚至不是被严格定义的东西，只是大家一般会去看 gradient norm 这样的分布。中间有一些东西是大家比较 concern 的：比如它的尖刺多不多，甚至它本身 norm 大不大。

这个团队会发现：如果直接 from scratch 训练，可能会多用一些算力，但至少最后的结果是不会有损的——如果经过恰当的训练，它不会带来更差的结果，甚至可能带来差不多、甚至更好的结果。

第二个他们主要 claim 的点是：原生的模型会带来更好的兼容性，体现在 gradient norm 会更加稳定。

我觉得这里可能有一个类似的观察：SigLIP 其实是用 Adam 训练的。之前大家也讨论过一个相关的话题——用 Adam 训练的模型，是否能用 Muon 去 finetune；反过来，用 Muon 训练的模型，是否可以用 Adam 去 finetune。

最后的结论是：比较原生的方式肯定是最好的。用别的方式如果想达到一样好，可能就得做一些处理，或者说是有一些限制。

所以对于 K3 而言，他们是希望采用一个全面统一的优化方式，这样对模型整体的训练稳定性也好、兼容性也好，是一个更优的状态。

十二、为什么 K3 没有用 sparse attention

张小珺

说到这里，我们倒回去讲一下最早那个线性注意力机制的问题吧。为什么 K3 用的是线性注意力机制，它没有用任何的 sparse attention？

孙宇涛

就是线性注意力、全注意力和 sparse attention，你可以三选一、三选二。那为什么不用 sparse attention？我们就要问：用了会有什么好处，或者会有什么问题？

这一方面跟模型架构有关，另一方面也跟每一代 GPU 硬件的 feature 有关。

比如 DeepSeek-V3.2 那种 DeepSeek Sparse Attention，以及 GLM 那几代，也用了这样的架构。

但 DeepSeek Sparse 到最后在 decode 里边，加速其实是特别特别小的。原因在于：sparse 求 index 这一步是相当昂贵的。而且在 Blackwell 这样的硬件情况下，越先进的硬件，这个 overhead 反而越大。甚至在 decode 当中，这种 sparse attention 方案跟 full attention 相比，并不会带来显著的加速。

为了解决这个问题，当时 GLM 团队做了一个工作叫 index cache。他们的做法是：把「求解哪些 token 需要算 attention」这个计算操作在不同层之间共享起来——比如每 4 层、每 8 层做一个共享。只有用这样的方法，才可以比较有效地减小 sparse 本身带来的开销。只有 sparse attention 本身开销足够小，才能带来比较可观的算法上的收益。

sparse attention 这块我们也做了一些相关工作，大概是一个类似的结论。当然我们做得更极端：我们在 YOCO 的架构上直接做了跨层的 sparse attention——因为我们之前的 KV cache 就是只算一次的，所以我们当时采取的方式就是把 sparse index 这一步也做成只算一次，把每层的 index 开销直接分摊到所有层上。这样开销就会特别特别小，我们才能吃到 sparse attention 本身的计算收益。

编者注

编者注：指的是讲者本人的 You Only Index Once: Cross-Layer Sparse Attention with Shared Routing（arXiv:2606.06467，2026-06-04），作者 Yutao Sun、Yanqi Zhang、Li Dong、Jianyong Wang、Furu Wei——跟 RetNet、YOCO 是同一批人，也是同一条「只做一次」的思路：YOCO 只算一次 KV cache，这篇只求一次 index。

我们再回到 K3 为什么不采用。

第一，我们认为每层都用 sparse 这样一个比较简易的方案，在 Blackwell 上收益是特别特别小的。为了解决这个问题，无论是 index cache 的解法还是我们的解法，结论都一样：需要把多层的 sparse 结果跨层复用。

而跨层最简单的方式是相邻层去跨。但对于 hybrid attention——线性注意力和全注意力 interleave 的方式——这并不显然：因为不同的 full attention 并不是挨着的，每个 full attention 中间隔了很多个线性注意力。在隔了很多层线性注意力的情况下，这种 index share 是否有效、加速比是否足够高，其实是相当 questionable 的。

第二个问题是：sparse attention 基本上没有办法进行 from scratch 训练。大家现在一般采用的都是 post-train，从 full attention 进行转化的方式。不排除 K3 未来会把已有的 full attention 部分转化成 sparse attention——当然如果他们用了 MLA 的话，这个会更难一些。

所以我觉得主要就两个原因：一个是想拿到实际加速比，对 hybrid attention 来说是一个 non-trivial 的东西；第二个是它跟 pre-train 并不是一个比较兼容的状态。所以这个其实留一个接口之后再做也行。

张小珺

刚才讲的这些，不管是架构创新还是训练还是推理工程，你觉得中间有哪些 trade-off、有哪些取舍？

孙宇涛

我觉得 hybrid attention 主要的 trade-off 就是你要去调节线性注意力和全注意力的比例：线性注意力比例越大，加速比肯定越高；但如果你想在比较无损的同时获得加速，3:1 就是实验上一个比较 work 的方案。这块是主要的 trade-off。

至于 sparse，严格来说它大概率不会带来更强的表达能力，所以这块其实是另一回事——它跟 hybrid 的架构是另一条线。只不过如果你坚持不用 hybrid，那你可能就不得不采取一些别的方案。

十三、忒修斯之船：这还叫 Transformer 吗

张小珺

我听到这里的感受是：现在的模型训练好像没有一个巨大的所谓范式创新，但它把之前很多工作都融合起来，然后再去寻找一个可能的更优解。我不知道这种感受对不对。

孙宇涛

对，我觉得问题不大。但我觉得不完全是技术的原因。

为什么呢？因为大家现在都叫 Transformer，但什么是 Transformer，这其实是没有办法清晰定义的。

这个在哲学上还有一个对应的概念，就是忒修斯之船。2017 年这条船刚开始行驶的时候，它是 Transformer。但这条船刚开始是怎么拼起来的？它是 attention 加 residual 这些东西拼起来的，包括 stack layer 这种方式——在 Transformer 之前，它其实也并不是全新的概念。

所以这条船刚建起来的时候，我们认为 Transformer 就是 MHA。但这条船已经行驶了八九年了，在慢慢行驶的过程中，我们会慢慢地把某些部分换掉、某些部分换掉。到 2026 年再看，其实跟 Transformer 已经……我觉得相似度已经很低很低了。那你是否还把这个东西叫做 Transformer？

这当然是哲学上的一个问题。从现在大家来看，大家还是会这么叫。但我觉得，如果历史的走向有些不同的变化的话——

张小珺

可能也就不叫了。我们上面讲的这些，你觉得它总体来说是一个什么样的工作？

孙宇涛

我觉得这个东西很难定义，因为它本身是一个偏综合性的工作。

严格来说，一般大家会把比较有创意性的单点突破专门拿出来讨论。中间比较大的就几点：第一个是注意力怎么设计；第二个是 MoE 这块有没有更好的设计；第三个是优化器；第四个可能就是中间的一些连接方式。

这些单拿出来，如果放到 ResNet 那个时代，可能每一个就是一个架构了。在那个时代肯定是这样的。但在 Transformer 的时代可能并不是这样——你得把这些东西综合起来，最后再把它跑出来，它才有意义。

因为之前大家做架构，只要在一个规模上跑出足够高的指标，它其实就算数了。但在这个时代，你想把实际的东西跑出来，要做的事情就特别特别多了：你得做 scaling 的验证，得把各个工程的东西搞定，得把 data 搞定。把这些都搞定，然后你把这个 paper、或者说把这个架构卖出来，大家才会 buy in。

当然从研究方面，我 personally 是不会太去关注的，因为我觉得架构的验证是有严格标准的，不需要把这些东西都凑到一起。但我觉得从非技术角度，它现在是这样一个状态。

张小珺

所以上面是 Kimi 这篇论文的一些亮点突破，对吧？接下来他开始讲他的预训练和后训练的工作。

孙宇涛

对。我觉得架构方面这块，相比于 K2 至少是不一样的——也不一定叫创新，有些叫创新，有些叫比较偏调优的部分，但我觉得还是比之前大不一样的。

张小珺

你觉得为什么 K2 到 K3 变化这么大？

孙宇涛

我觉得是个战略的问题。K2 在那个时间点他们其实也可以不一样，只不过他们当时主要的重心是把模型跑出来。

张小珺

所以在 K2 到 K3 中间，他们有更多的时间去做了很多优化调整。

孙宇涛

我觉得主要是 K2 本身做得不错。K2 当时他们主要考虑的问题，比如怎么把 Muon 训出来、怎么有效地把模型 scale 上去。因为当时 K2 就是 1T，1T 还是比之前的 DeepSeek-V3 要大一些的，在那个时间应该也算相当大的模型了。

所以当时他们解决的是这样的问题：先把 base model 整体的盘子做稳，在稳的基础上，后来 K3 再去追求一些更精益求精的优化。

张小珺

从上面这些亮点工作——这是最后的结果——你反推，能看出这个团队整体的状态是什么样的吗？

孙宇涛

我觉得看怎么定义。如果只是 Kimi 的架构团队或者预训练团队，我觉得没什么变化，一直就是一个样；但对整体公司而言，还是有战略性的侧重的。

侧重点就是：K2 当时团队主要的诉求是把 base model 做稳，先把能力做出来，暂时不去考虑更高的 efficiency、更精益求精的创新。当然他们团队内部是一直在做的，只不过什么时候亮出来是另一回事。

张小珺

研究工作是一个更长期的工作，可能要看放在哪个模型里跟它一起结合。

孙宇涛

对。

第三部分　预训练

十四、Scaling Law：为什么 K3 不用 WSD

张小珺

那接下来我们讲预训练。

孙宇涛

对。pre-train 和 post-train 这块，首先 post-train 是一个偏工程、或者说偏具体场景的东西，这块可能不会讲太多，因为论文里也没有写太多。pre-train 和 post-train 我觉得主要是一些经验性、或者说一些 know-how 的东西，主要创新可能是前面（架构）多一些。中间有一些我觉得比较有意思、可以讨论的点，我会专门拿出来讨论。后面主要的风格会是这样。

pre-training 这块，我觉得一个比较值得讨论的点，就是用哪样的 learning rate 策略。

learning rate 策略最早是 MiniCPM 那篇 paper 提出的 WSD。MiniCPM 之后、Kimi K3 之前，我觉得几乎所有团队都在用 WSD。

我们可以去看 MiniCPM 当时是怎么考虑这个问题的。简单来说，WSD 考虑的问题是：如何能把 data schedule 和 learning rate schedule 结合起来。

MiniCPM 刚开始讨论的问题是：WSD 和 cosine decay 是可以取得比较相近的结果的。比如我们从一个更高的学习率降到一个更低的学习率，中间怎么去调配，对最后的结果影响其实没有那么大。

所以在这种情况下，MiniCPM 团队认为：既然中间具体的 decay 方式对结果影响没有那么大，那我们就可以跟 data 排布做一些联动。

因为在实际训练中我们会发现——包括在这个图里也可以看到——在 decay 阶段，模型 loss 的下降速度比用大学习率稳步跑要快很多。所以之前大家会认为，cooldown 这个阶段是模型学习最快的阶段。

所以 MiniCPM 当时采用的策略就是：既然 cooldown 是模型学习最快的状态，那我们为什么不把更多更好的数据放在 cooldown 这个阶段去训练？这样可能会比「所有 data 均匀分布、learning rate schedule 也均匀分布」取得更好的效果。

这是当时 MiniCPM、包括 WSD 提出的背景。我觉得这个还是挺有意思的：一方面他讨论了一个「为什么」的问题——为什么我们要采取不同的 learning rate decay 方式；另一方面，他讨论了 decay 的不同阶段具体承担什么样的角色，然后用不同 decay 阶段的行为去跟 data 的具体策略结合，最后取得更好的结果。

K3 的反问：WSD 那个「自由」其实是有代价的

Kimi K3 这块讨论了一件不太一样的事情：他们为什么不去用 WSD。

WSD 除了可以用更好的 data schedule，还有一个额外的好处：因为前面的 learning rate 是不变化的，既然不变化，它就跟你整体要训练的 FLOPs 和 token 量无关。

因为无关，所以我们可以更自由地在模型训练过程中选取最后实际的 config。比如刚开始预定要跑 17T token，但跑到中间训练策略改变了、或者公司策略改变了、或者要更早发版更晚发版——WSD 可以让我们更自由地在中间切换，而不用在刚开始就把整个模型要训的 token 量定死。

这是它的好处。但它带来的一个问题没有被讨论：虽然我们可以任意选择实际要跑的 token 数，但你实际的 learning rate 是和要跑的 token 数有关系的。

比如你设 6e-4 作为一个比较稳定的 schedule：你跑 10T，可能 6e-4 是最优的；你跑 20T，可能 3e-4 才是最优的。所以从最优的角度考虑，任意去扩展 token 数，可能并没有大家想的那么有效。

Kimi K3 这篇 paper 就讨论了这个问题：WSD 实际 schedule 的调节难度其实和 cosine 是一样的，而且它不一定好调整；而「任意选取最后训练的 token 量」这件事，也不一定只有 WSD 才能做到——用别的方式也是可以做到的。

paper 里写到：就这些原因，他们可以选择一个更简单的方案——cosine decay。他的理由是：cosine 其实更好调，它只有两个变量：一个是你要跑多少 token，另一个是 maximum learning rate 具体设多少。而 WSD 就会多一个变量：你要 decay 的比例具体是多少。

所以从调参角度讲，cosine decay 是一个更容易调参的方案。Kimi K3 在 paper 里就写到，因为发现 cosine decay 更容易找到一个 hyper-parameter setting，所以最后采取了这个也可以算是比较经典的 learning rate decay 方式。而这个其实是在大家都用 WSD 的情况下，一个不太一样的 setting。

K2 到 K3 的 scaling efficiency

Kimi 团队对比了从 K2 到 K3 整体的 scaling efficiency。

首先 K3 比 K2 大了很多：总参数从 1T 左右到 2.8T，大了不到三倍；而激活量是从 32.6B 到 104B，这个比三倍还要更多。从模型参数上，毫无疑问 K3 是比 K2 强很多的模型。

最后他们团队给出了一个 scaling law 的结果：K3 比 K2 在 scaling efficiency 上是 2.5 倍这样一个量。

当然，对于一个简单的 dense model，scaling efficiency 是一个比较经典的讨论问题，之前很多公开的 scaling law 工作都讨论过。

这块比较值得注意的一点是：大家其实也问过，Kimi K2 到 K3 的这个 scaling behavior 是不是固定 data 的。我记得他们的回答是「应该不是」，paper 里应该也没有直接写。

当然这也可以理解——K3 和 K2 用的 data 肯定不可能是一样的，所以这块大概率有一个不一样的 data recipe。所以整体这个 scaling 结果，是综合了模型架构、模型 recipe，再叠加上数据策略之后的总的结果——作为一个大的综合结果，它比 K2 高了很多。

十五、长上下文：把 RoPE 换成 NoPE

孙宇涛

接下来是长上下文。K3 的定位是一个原生支持 1 million 长上下文的模型。这块比较有意思的点是：位置编码如何选取。

如果我们从比较传统的架构来做，大家都会用 RoPE 做位置编码。但用 RoPE 的话，在长文扩展的时候有一个问题：RoPE 的具体参数是需要做调整的，不做调整的话，直接去扩长文就会显得没有那么有效。

这是 RoPE 时代大家一个经典的做法。如果你现在还是用全注意力、或者不引入线性注意力，这个策略不会有太大改变——你还是得在不同长度的 setting 下去调节不同的 RoPE 参数。

但这件事在混合模型里是可以改变的。最早是 Cohere 团队的一个工作讲了这个。

他们的结论也很简单：因为 hybrid attention 的排布方式，对于 linear attention 来说，它已经引入了位置信息——无论你用 RoPE 也好、RoPE 加 sliding window 也好、linear attention 也好，在线性注意力这个阶段，位置信息已经被引入了。

所以在 hybrid attention 的 setting 下，如果我们把 full attention 从 RoPE 改成 NoPE——也就是在全注意力的部分把位置编码去掉——它可以带来两个好处：

  1. 带来更好的模型表现；
  2. 在长上下文上更容易扩展：NoPE 在模型扩长的情况下，不需要调整任何模型架构的参数，就可以达到长上下文的效果。

这个效果无疑是很优雅的。因为我们会觉得，模型架构的参数选择本来就跟具体长度没有关系；也没有任何理论支持「我们为什么要在不同的长度 recipe 下采取不一样的参数」。而这种架构就可以有效避免这一点。

我是比较早看到这篇的，看到第二天我就去复现了一下——因为当时觉得特别有道理。复现之后也很 work，我当时就觉得这肯定是混合注意力里比较好的一个方式。

我在会议里边还审到了这篇文章，当时我直接给了一个 strong accept。我感觉我这几年可能也没有给过几个 strong accept，因为我觉得这确实是一个很有效、也很优雅的解决方案。

这里也可以讨论一个大家之前理解错误的问题：RoPE 本质上带来的是 recent bias。RoPE work 最有效的点是——它对 short context 的建模能力特别有效，但对长文其实是没有帮助的，甚至是有负面影响的。

有一些观点会认为「是 RoPE 带来了长文的表现」——这其实是错误的：RoPE 并不带来任何长文能力，它甚至是损害长文能力的。

所以 Kimi K3 会把 RoPE 在长上下文的那部分全注意力里直接去掉。去掉之后，如果你直接测外推，效果都会好很多。用 RoPE 的话，你扩长度就需要调参数；而如果调了参数又不去训练，结果其实是很差的。用 NoPE 就不用调参数，外推效果也很好，长上下文的效果也没有任何问题，甚至还要更好。

它在混合注意力这个 context 下，是一个相当优美的解决方案。所以 Kimi K3 也用了这个方案。

第四部分　后训练

十六、低精度训练该在哪个阶段引入

孙宇涛

首先可以讨论的一个问题是：低精度训练应该在什么阶段引入。大家采取的策略是不太一样的。

比如 DeepSeek-V3 刚开始就是原生用 FP8 训练；DeepSeek-V4 直接用 W4A8 来做训练。但 Kimi 这块采取的策略不太一样：他们首先用高精度训练，然后在 SFT 阶段再把低精度的 QAT 引入进来。

这至少有两点值得讨论。

第一，抛开技术角度，从项目管理而言：大规模训练采取更高精度肯定是更保险的方案，因为它无论如何也不会错。如果用低精度训练在大规模 scaling 中带来了其他问题，那是一个相当不可控的因素，而且这种东西在更大规模的训练上很难被提前充分、精确地验证。

第二，从技术角度：我们是否有必要从刚开始就用低精度训练？起码从我的实验而言应该是没有必要的，Kimi 可能也发现没有必要。也就是说，对于低精度推理而言，从 from scratch 就引入并不会带来任何模型能力的提升——W4A8 你在什么时候引入，只要过了一定量的训练，最后的结果可能都差不多。所以在 SFT 阶段引入是一个更保险、技术上也不会带来额外损失的方式。

RL 这块，因为 Kimi 从很早以前就比较重视 RL，从 Kimi K1.5 到 K2.5 一直在做一些持续的创新，在 K3 这边也比较充分地引入进来。这些其实都是一些比较成熟的方案了，就不太展开讨论。

十七、On-Policy Distillation：从「老师讲课」到「老师改作业」

孙宇涛

4.3 这块可以讨论一下 OPD（on-policy distillation）。

OPD 刚开始也是董力老师团队这边比较早讨论的方式——微软研究院的董力。MiniLLM 是顾煜贤做的，煜贤去年也是清华特奖，这是他在董老师那边做的工作。

OPD 刚开始大家用起来的方式，和后面大家实际在工程中用的方式不太一样，这个可以讨论一下。

先说 OPD 最初的 motivation

当时 OPD 讨论的 context 是蒸馏。蒸馏有两种：

  • 黑盒蒸馏：这是大家现在比较常采取的方式——拿一个 API，我们不知道模型内部状态，也拿不到推理的 logits。对外界来说这个模型完全是一个黑盒，我们只能拿到它的输入和输出。
  • 白盒蒸馏：我们可以获取到模型本身，也可以任意拿到模型推理过程中我们想要的任何状态。

那么在白盒场景下，我们如何做蒸馏、是否可以获得比黑盒蒸馏更好的表现？

MiniLLM 当时采取的方式是反其道而行之。

之前大家的方案是：让 teacher 去生成答案，然后把生成的答案用 SFT、用 forward KD 的方式引入到 student 模型里。而 MiniLLM 是反过来做的：让学生去生成答案，然后让 teacher 做每一步的纠正。

直观来讲就是两种方式：

  1. 老师讲课——你把老师讲课的结果学进来；
  2. 你自己做题——自己写中间的推理过程，然后老师把你中间推理哪里做得不对给你指出来，告诉你怎么做。

这个叫 reverse KL。后来 Thinking Machines Lab 给它换了个名字，就叫 on-policy distillation。

大家会意识到，从蒸馏的角度这是一个比较有效的方式：我们不直接去学习模型的答案，而是在 student 自己的推理过程中，让教师模型逐步去 verify 或者纠正学生模型的推理。

这个范式刚开始其实是为了蒸馏使用的。无论是做白盒的实验，还是从公司角度——你可以有一个 pro 的版本、一个 flash 的版本，flash 版本可以用 OPD 的方式去蒸馏更大模型的结果，从而获得更好的表现。你如果 from scratch 训练一个 flash 模型，是比不过这样蒸馏出来的，所以可以在比较便宜的模型这一档获得更强的竞争力。

但后来大家用它，不是为了蒸馏

这是 OPD 刚开始的 motivation。但后来大家更常用的方式不是去做蒸馏。

原因在于：如果你想做蒸馏，至少得有一个大模型，再去训练一个小模型。而如果你想蒸馏黑盒模型，这套方案是完全不可用的。

从公司或者项目策略上讲，现在大家一般都不是「基于一个大模型去训练一个更快更小的模型」这个 setting 了——大家一般都是搞一个旗舰模型就完事了，用它作为 inference 服务。在这个场景下，就不存在「大到小」的蒸馏行为了。

于是大家逐渐采用的蒸馏方式是：自己蒸馏自己。

为什么要自己蒸馏自己？我觉得还是两部分。

非技术层面：这个技术可以让整个 post-train team 的管理变得更加简单。post-train 的合版其实是一件比较 heavy 的事——它跟 pre-train 不一样：pre-train 我只要把数据合起来一块去干就完事了；但 post-train 一般会用一些更复杂、更先进的训练策略，这些策略不太容易直接合版，会有一些难度。所以基于项目管理策略，on-policy distillation 可以把整个 post-train team 的管理简化一些。

技术层面：大家做 RL 一般有不同的策略。比如你做 math，可能就是一个规则 reward；如果有一些 preference 的需求，可能就会用 reward model 去做；如果你再想扩展 RL 的别的能力，每个能力对 RL 来说，它的 reward 都是一个独特的 reward。

而 post-train 一般大家都会专项突破。如果你想把不同专项模型的不同 reward 直接拿到一块去调，其实比想象的难度要大——我也不是说完全不可能，反正还是有可能的。

但用 OPD 就会变得很简单：我们可以把不同的 reward model、不同的 RL 范式，简化成不同的模型。简化成不同的模型，这件事就容易很多了。因为对于 RL 策略、对于 data 来说，它是一个高度异构的状态；但对于模型来说，它是一个高度同构的状态——现在我们也不会为了不同任务去专门设计不同的模型架构。如果模型都长一样，那我们再做一个 multi-teacher 的合并，就会容易很多。

不过这个也不是 K3 首先用的，现在这是一个 widely accepted 的做法——我印象里小米、GLM，大家现在应该都是这么做的。

十八、Draft Model：把投机解码这条线补上

孙宇涛

quantization 刚刚讲过了。然后 draft model 这块我觉得还是挺有意思的，这块还可以有一些延伸的工作——因为我觉得 K3 目前优化得不是很完善。

之前小米他们推出了一个能达到 1000 TPS 的方案，主要用了两个技术：

一个是 TileLang 团队做的 TileRT，可以高度融合不同阶段的算子——这样可以获得比传统 vLLM 推理方式强很多的推理效率，大概能达到三四百 TPS。小米是在这个结果的基础上，再加上 DFlash 这个投机推理带来的额外加速比，最后得到一个比原模型强很多的推理速度。

编者注

编者注：两个专名都已核到。融合算子那套是 TileRT（github.com/tile-ai/TileRT），出自维护 TileLang 的同一个组织 tile-ai，靠常驻 GPU 的 Persistent Engine Kernel 与 warp specialization 把各阶段算子压在一起；投机解码那个是 DFlash: Block Diffusion for Flash Speculative Decoding（arXiv:2602.06036），用一个轻量的 block diffusion 草稿模型一次并行吐出整块 token。小米把两者叠在一起，做出 MiMo-V2.5-Pro-UltraSpeed：1T 参数、单机 8 卡、1000+ TPS。TileRT 同期也用在了 Z.ai 的 GLM——对得上讲者上一段说的「小米、GLM，大家现在应该都是这么做的」。

这个主要服务的是愿意付出更高成本、但想拿到更强推理速度的那一波用户。因为如果你是为整体 throughput 服务，收益会小很多；但如果是小 batch size 的场景，这套方案会强很多。

抛开 runtime 那方面的贡献，最后就落到了：如何做更好的 MTP、或者更好的 draft model。

这块有一些有历史脉络的工作。刚开始是 EAGLE-3 或者 MTP。EAGLE-3 和 MTP 主要的方法是——因为刚开始 speculative decoding 提出的时候，大家还是用一个没有关系的小模型去 speculate 一个比较大的模型，这样有一个问题：你无法充分利用大模型中间的 hidden state。

如果你可以利用大模型中间的 hidden state，你其实就可以把小模型做得更小；或者说在相同参数下，把接受率做得更高，最后带来总的更强的推理效率。MTP 和 EAGLE-3 其实都是这样的思想。当然 MTP 如果 from scratch 的话，还有一些别的好处。

DFlash 会更有意思一些，因为它把传统的 language model 和去年比较火的 diffusion language model 这两条脉络结合了起来。

因为 diffusion language model 刚提出的时候，大家主要的 claim 是：它在单用户、或者 batch size 比较小的情况下，可以获得比传统 language model 快很多的推理效率。

但 diffusion language model 之前最大有两个问题：

  1. from scratch 训练效率不够高，整体结果很难和传统的 AR language model 相匹敌；
  2. 它只能打小 batch size 下的速度——如果是多用户、最后追求总 throughput 的场景，diffusion language model 并没有优势。

所以 DFlash 当时主要就是统一了两者：试图利用 diffusion language model 更快的推理方式，进一步去优化 MTP 或 draft model 这块的加速比，最后得到一个更优的单用户 throughput。

当然，MTP 这块我之前跟做 DFlash 的那位同学也交流过，他当时提了一个点，对整个模型是很重要的：即使我们用 DFlash 这种更先进的 draft model 策略，它跟预训练的关系仍然是很大的。也就是说，对 draft model 来说，它需要在利用大模型一定推理能力的基础上，再去进一步扩大。

也就是说，MTP 需要在 pre-train 阶段就给下游留一个接口，这个接口对下游 draft model 的提升会特别有帮助。这部分是需要在 pre-train 阶段就引入的。

当然，draft model 也需要做一些自己特化的处理。比如我们可以用一个 KL loss 来替代比较传统的 next token prediction——这样在跟原模型对齐的过程中可以对得更齐，进一步提升 draft model 的接受率。

我猜这块之后还会有一些更深层次的工作，因为这肯定不是 MTP 的终点。

后面 RL task 那部分比较 specific，对不同任务有不同的具体策略，这块看原文就好了。

第五部分　Infrastructure

十九、线性注意力的 CP：chunk 套 chunk

孙宇涛

接下来一大块是 infra。

现在对于模型架构的设计来说，关键的设计是需要和 infra 做 co-design 的。一个是 co-design，另一个是模型架构本身会影响整体 infra 的设计。这块跟 DeepSeek 那一系列的 infra 有一些设计上的区别，我觉得也是一个比较有意思的点。

首先是 KDA。前面已经讨论过：如果想追求更高的 chunk 效率，我们需要对 KDA 的衰减系数做出一定限制，这样可以用一个更好的 kernel 设计形式，带来更强的 kernel level 效率。

这块另一个点是 KDA 的 CP（context parallel）。我觉得 linear attention 的 CP 是一个可以简单讨论一下的点。

对于 sliding window 或者 full attention 而言，CP 从概念上是相当容易的——比如对 full attention 来说，有一些比较经典的算法（比如 Ring Attention 这类）。因为它本身的计算模式足够简单，而且很多地方是省不了的：我至少得把跨 GPU 的所有 KV cache 都拿到一个 GPU 上去做计算。这是一个相对简单的概念。

但对于 linear attention 的 CP 而言，概念其实更复杂。

这个大的框架我们还是可以回到最经典的 chunk recurrent。

首先我们都同意，chunk recurrent 对 linear attention 来说是一个必备的算法。对于一个正常的单机、不开 CP 的训练场景，chunk recurrent 有两部分：

  • 你可以拆成比较小的 chunk（比如 16 或者 64 的 tile），chunk 之间用递归的方式计算；
  • chunk 内部用比较 parallel 的方式计算。

KDA 也是这么做的，而 KDA 那个 decay 的限制，主要就是为了解决 chunk 内部能用 parallel 计算的高效性。

但对于 CP 来说，就要讨论 linear attention 一个比较有意思的性质：它的 chunk 本身是可以任意拆分的。

也就是说，不同的 chunk 大小——你取 512 个 token 一个 chunk，还是 8K token 一个 chunk——在数学上是完全等价的。

这跟早年一些比较拼接式的方案不一样。比如有些工作会尝试「chunk 之间用 linear attention、chunk 内部用 full attention」，如果用这种策略，chunk 的大小就跟具体的模型 architecture design 有关了。但纯 linear attention 是无关的。既然无关，我们就可以对 chunk 的层次做出比较任意的处理。

对于单机来说，chunk 是拆一次的——拆成 16 的 tile，tile 内部用并行方式计算。但它并没有限制说 chunk 只能拆一次。

思想就是：比如我有一个 one million 特别长的 chunk，我们可以拆成 8K 放一张卡、8K 放一张卡——这样就构建了一个以「大 chunk」为单元、不同 GPU 之间采取递归计算的拆分方式。

拿到 8K 这个拆分之后，我们可以在内部进一步拆分。因为在 linear attention 里，我们没有任何限制说一个 chunk 中间是如何计算的：对于比较小的 chunk 而言，parallel 是比较优的；但如果拆出来的 chunk 足够大，我们就可以采取 chunk 套 chunk 的方式去计算。

也就是说，对于 linear attention 的 CP，我们做的是一个层次性的 chunk：首先在不同机器之间做一个 chunk，然后在一个机器内，再在 kernel level 做一个 chunk。通过这样的双层 chunk 形式，组成 linear attention 一个比较大的 CP。

这个 work 主要还是来源于 linear attention 的 chunk 可以任意拆分这个特性。这跟 full attention 是不太一样的处理方式。

二十、完美均衡的专家并行：用少量冗余专家换对齐

孙宇涛

上面是 CP、或者说 kernel 化这一层的 infra 方案。接下来讨论的是：从分布式训练的角度，我们如何去优化它。

这块后面可以发现，它跟 DeepSeek 的方案是稍微有些区别的，而这个区别主要来源于不同 MoE 架构的方式。

首先，Kimi 团队带来了一个 EP 的计算方案。他们主要 claim 的一点是：对于传统的 EP，我们现在都用 dropless EP——对每一个 token 而言，我选哪个专家是不受整体约束的，我想选哪个选哪个。

这样带来一个结果：汇总起来之后会发现，不同专家的负载是不一样的。而负载不一样就会带来两个问题：

  1. 对于 EP 而言，每个 GPU 分到的 token 数不一样，整体的执行时间就不一样。执行时间一旦不一样，它们就会互相等——互相等就会浪费 GPU 的算力。
  2. 如果不同卡上的 token 数是不确定的，GPU 通信就会额外多一个阶段：我们首先需要告诉所有 GPU「你要接收多少 token」，然后再把 token 发过去。

所以传统的 EP 严格来说不是一个最优方案。如果完全为了 infra，最优的方案其实是带 drop 的 EP：每个 token 受到全局的影响，通过一系列 allocate 的方式，从模型角度让每个 expert 都收到完全均匀的 token，达到完全的 balance——完全理想的情况其实就是这样。

所以如果说「在 infra 层面完全均衡」是最优的，那策略就是：努力让它从不均衡走向均衡，同时保持模型能力不下降。因为 drop token 大家现在都不会用了，它对模型能力的损失还是相当明显的。

而 Kimi 的这套 EP 采取了一个我觉得比较高明的方案：把 EP 的方式变成了一个更动态的方式。

之前一个经典的方案是：比如我有 128 个专家，如果我们 EP8，可能每张卡放 16 个专家——这是一个比较静态的方式。

而 K3 采取的是动态的方式：它有一些冗余的专家。通过额外的冗余专家，从数学上可以证明：存在一个策略，使得我们只需要增加一个小比例的冗余专家，就可以保证 token 数的完全对齐。

我感觉这像是一个比较经典的数据结构与算法问题，这是可以证明的。证明了这一点之后，就可以得到一个结论：通过少量的冗余专家，就可以达到所有卡上都均衡的效果。

具体如何达到？他们采取了 online planning 的方式：提前规划哪些卡应该有哪些冗余专家，这样就可以达到不同卡上 token 数的完全均衡。

当然，即使从卡的角度是均衡的，也不代表专家层面是均衡的。因为这个算法只保证每张卡的总 token 数是一定的，并不保证每个专家是一定的——一张卡里有多个专家。如果你还想保证每个专家也一定，那就没有办法了，只能采取有损的策略去优化。如果大家不希望有损，上限可能就卡到这里。所以我们可以在这两者之间找一些更优的处理方式。

这块是 Kimi 团队带来的一个比较有意思的创新。

二十一、显存：把中间结果 offload 到 CPU

孙宇涛

接下来是 Memory-Efficient Training，我觉得这块比较有意思。

首先他们带来了一个软件工程层面比较简单的方案：更细粒度地控制每个部件应该采取重计算还是 offloading。

这块不一样的一点是：Kimi K3 采取了大规模的 offloading——把中间计算得到的结果 offload 到 CPU 上。

这其实是一个 non-trivial 的东西。因为理论上，如果想让 offloading 不拖慢模型训练，是有一定条件的：你得保证 CPU 和 GPU 之间的通信满足某个不等式，这样才有可能用计算完全 overlap 掉通信。

为了达到可以做 offloading，K3 把所有可以 offload 的东西都用 FP8 去存——这样可以省一倍，省一倍它可能才能从一个边界跨到另一个边界。而具体这个边界怎么算，跟具体的卡、具体的集群环境，也跟具体的模型 config 有关系。

后面他们还需要去优化 attention 本身的一些关系，这个在之前的 paper 里也讨论过。

二十二、跟 DeepSeek 不一样的地方：通信怎么藏

孙宇涛

我觉得 PP 这块，一个是 PP，一个是通信 overlap 的手段——这跟 DeepSeek 是不太一样的方案。

从 DeepSeek-V3 的角度而言，它采取了两个 non-trivial 的方式。

第一个是比较细粒度的 MoE overlap。

MoE 中间有两个通信：一个是 dispatch，一个是 combine。这两个通信的 overhead 是比较大的——在 Blackwell 上又不太一样，但无论如何是一个比较大的开销。

DeepSeek-V3 在 MoE overlap 这块拆得特别细：把上一个 batch 的 MoE forward、backward 和下一个 MoE 的 forward 融合起来，通过重排计算的先后顺序，把所有大的 dispatch 和 combine 通信都藏起来。

想达到这一点，需要特别精细、也特别复杂的软件工程优化。因为如果想做得足够好，我们需要把所有 forward 和 backward 的计算从原子计算的层面拆开，然后手工重新排布。我觉得这还是有一定难度的。

另一个是 DeepSeek 采用的 DualPipe 策略——为了缓解 PP 的气泡和不同 activation 不均匀的问题，他们采取了 DualPipe 这样的 pipeline 排布方式。当然后面除了 DualPipe 还有 DualPipe-V，但它们达到的效果是一样的，只是逻辑上会更简单一些。

而起码从公开写到的内容来看，Kimi K3 没有采用这两个优化方式，他们采用的是一些别的方式。

第一个就是如何去隐藏通信——这跟实际的模型架构选型有关系。因为 Kimi K3 采用了 LatentMoE，而 LatentMoE 本身极大地降低了通信开销，所以它在整个计算开销里边——

——因为它的通信开销减小了特别多，所以想把它 overlap 掉就容易很多：我们没有必要再去跟另一个 batch 的计算做 overlap，可以采取一个 batch 内部更简单的 overlap 手段，就可以把通信很好地隐藏掉。

Kimi K3 具体采用的方式是：把 MoE 前向和后向的通信，跟 shared expert 的计算 overlap 在一起。因为 shared expert 现在绝大多数模型都有，而且它是有一定计算量的。

正是因为通信开销减小了，才能被 shared expert 这样一个比较简单的方式 overlap 掉。如果你用传统的 MoE，通信开销特别大，用 shared expert 就很难 overlap 掉——overlap 不掉，你就必须把另一个 batch 拿进来，才能完美地把通信隐藏掉。

不一样的 MoE 架构，带来了不一样的 overlap 策略。这个策略带来的好处是：推理 critical path 上的 latency 是免费的。从训练架构上，因为通信量更小，我们可以采取更简单的策略去排布通信的气泡。

还有另一个问题：即使我们通过更复杂的方法完美地把通信藏掉，它其实也不是完全无损的——即使完美地把通信和计算重叠，计算也会相对慢一些。针对这个问题，DeepEP 也做了类似的优化：用足够少的 SM 占用来获得更大的整体通信带宽，这样 overlap 才能跑得更快。

所以这块是一个很不一样的设计方式。

另一个不同是 PP 的处理。

如果用 DualPipe 或者 DualPipe-V 这样的 PP 排布方式，不同 PP rank 之间相对还是一个比较对称的状态。而如果你用单向的 PP，就不太对称。不对称有两种解决方式：第一种是让它变得对称；第二种就是 Kimi 这篇 paper 里讨论的：我们可以把不均衡 transfer 掉。

因为比较朴素的 PP，前面的 PP rank 会进入得更早、积累的 batch 更多，activation 的压力就越大。Kimi K3 采用的方式是：把 memory 占用比较大的那些 PP rank 的东西，直接让它存到比较空闲的 PP rank 上——通过这种比较 lightweight 的方式，避开了更复杂的 DualPipe 设计。

后面是 Muon 的一些优化。因为 Muon 需要对全矩阵做牛顿迭代，所以如果用传统的 Adam——Adam 相当于把所有参数摊平之后再去切，因为 Adam 是 element-wise 的优化，你怎么切都不会影响优化结果。但对 Muon 来说是有影响的：在某个 rank 上，我需要把一个矩阵所有的参数都保存下来。所以这块需要做一些处理，才能让 Muon 在 optimizer 这个角度比较好地切开。

二十三、多模态的 infra：每加一项，难度直线上升

多模态的 infra 也是一个比较有意思的点。

从 infra 的角度，纯的 language model 想优化得足够好，也需要相当多的 effort（刚刚讨论了很多）。但对于多模态而言，你每引入多模态的一项功能，infra 难度其实都是直线提升的。

这块的问题就是：如何把 vision encoder 做好。论文提出了两个问题。

第一个：现在大家会对 vision token 做一定的压缩。比如 vision token 最后输入到大模型里可能是 8K token，但输入之前可能是 32K token——也就是说，vision encoder 接入模型的过程中是做了压缩的。

但这个压缩在 vision encoder 内部是没有做的，所以 vision encoder 内部计算的时候序列会更长。为了解决这个问题：可能模型主干不需要开 CP，但 vision encoder 就需要开 CP。所以这块需要做一些额外的 infra 处理。

PP 这个就更有意思了。

大家注意到一个问题：我们做 VL native training 的时候，VL 的 token 只占一个比例。比如对某些卡来说是纯文本的状态；对另一张卡，可能 VL 比例相当大。这种情况下，就会出现不同卡不均匀的现象。

这个现象不仅会影响 DP，PP 也会受影响。因为 PP 首先要保证不同 PP 之间是比较均匀的状态，流水线才能打得足够满。不然的话，如果我们在第一个 PP 引入了一个新的 vision encoder，它的计算强度就会显著增强，破坏整体流水线打满的状态。

为了规避这个行为，Kimi K3 采用的方式是：不把 vision encoder 放在 PP 的最开头，而是放在中间或者尾巴上。这样在前面的 vision encoder、或者说比较浅层的 language model 计算的过程中，中间的 PP 是闲置的——就把中间闲置的这部分利用上，提前把 vision encoder 后面的一些步骤算出来，通过这种方式规避掉第一个 PP 带来的足够大的气泡。

这是在 PP 层面需要做的一个优化。

二十四、RL 与推理侧：省一个 gradient buffer

孙宇涛

前面主要是 infra，大家主要分为三部分。

一个是 pre-train——前面主要讨论了大规模分布式情况下一些比较复杂的优化方式。后面是两部分：一个是 RL，还有一个是 inference。而 RL 本身就涉及大量的 inference，所以这两个中间是有一些 overlap 的。

RL 不太一样的一点是：它对大规模 sandbox 会有一些比较细的要求。这个其实算是一个更工程的东西——如何去处理不同的 sandbox。对于 RL 的 task 来说，每一个 trajectory 可能都对应一个自己的 Docker，所以如何管理大规模 Docker 是这块比较麻烦的问题。

K3 比较有意思的是，它会时不时给你蹦出来一些有意思的东西。比如这块提到：可以省一个 gradient buffer。这算是一个比较 tricky 的东西。

对于一个完整的 RL 来说，它有好几部分的 model：至少有一个主 model（policy），还有一个 reference model，然后主 model 还有对应的 gradient 和 optimizer；如果你还想做 reward model，还会再多一个 model。这块就会多出特别特别多的 model。

而放一个 model，对 GPU 来说还是很大的一块 memory。所以 K3 这块相当于把两部分 memory 拖到一块了：他们发现 reference model 可以跟 generative reward 合起来。

因为 reference model 是没有梯度的——在你求 objective 的过程中是没有 gradient 的；等你有了 gradient 之后，reference model 就不会再用了。所以这块用了一个 gradient buffer reuse for non-policy models，是一个比较有意思的东西。剩下的我感觉就是一些比较常规的处理方式了。

我觉得 inference 这块不会有太多东西，因为主体的 inference optimization 其实是 vLLM 或者 SGLang 这些专门讨论的内容。这块讲的是：K3 架构所带来的增量，在现代推理引擎中是如何处理的。

linear attention 的 prefix cache 是个麻烦

首先，linear attention 在现代 inference engine 里有一个麻烦，就是 prefix cache。

对于全注意力来说，相当于每个位置都有一个 cache，下一个位置的 cache 一定是上一个 cache 的简单增量，所以 prefix cache 会简单很多。

但 linear attention 有一个比较麻烦的特性：它每一步是在上一步的 state 基础上做一个复写的——也就是说对每一步而言，它的 prefix state 其实都不一样。所以如果我们把每一步都存起来，linear attention 的好处就完全没有了；但如果完全不存，又完全没有办法享受 prefix cache 带来的好处。

目前 Kimi Linear 采用的策略是：按 block 去切，每个 block 做一个 prefix cache。

同样还有一个 non-trivial 的点：vLLM 那种 paged KV 的实现方式。

从工程上、从概念上，最简单的分布方式是不考虑层和层之间的异质性的。所以从前年、去年开始，如果想直接在 vLLM 里引入混合架构，在 infra 上并不是一件容易的事。而且现在 vLLM 这些越来越 heavy 了，如果用简单的改法，会把整个东西搞得特别特别乱。

当然现在可能都有一些比较先进的管理方式了。但这需要特殊处理一下——把不同的 attention pattern 结合起来：对于 full attention 来说是按 page 管理的，但对于 linear attention 或者 sliding window，它是不能按 page 管理的，因为它并不存在一个 token-wise 的、长久的 KV cache 产生方式。这本身对 vLLM 的设计来说，是需要做一些兼容性处理的。

后面就是一些适配性的优化。因为 decode 的优化跟 prefill、跟 training 不太一样，所以每个环节都需要做一些额外的 kernel 配置。但我觉得这块都是可以做的，而且应该是一个确定性比较高的事情。

后面就是 evaluation 了，我觉得这个没啥好讲的——就是好，特别好，每个环节都好。后面主要就是这样，应该就没啥了。
